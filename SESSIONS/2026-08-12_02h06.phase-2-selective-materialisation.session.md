## 1. The API surface

### 1.1 The policy is a predicate

Per §2.2 of the plan, the engine stores nothing:

```ts
export interface VFSNodeOptions {
  /** Bytes this node keeps on disk. Everything else: the entry yes, the bytes no. */
  materialize?: (entry: VFSEntry) => boolean;
}
```

Absent predicate = materialise everything, which is today's behaviour and the default.

It takes the **whole entry**, not the path (§10.1 of the plan). The asymmetry with `ignore`, which
takes a path, is accepted deliberately and for a reason that is not just convenience: `ignore` is
consulted about paths the walk returns, where no entry need exist yet; `materialize` is only ever
consulted about entries that already exist in the tree. The two predicates are asked different
questions at different moments, so giving them the same shape would be a false symmetry. And `size`
and `kind` are exactly what a device-capacity policy wants to read.

### 1.2 Two names, and the collision to avoid

The plan uses `materialize` for both the policy and the on-demand fetch. They live in different
namespaces (`VFSNodeOptions.materialize` vs `VFSNode.materialize()`) so it compiles, but sync.ts
needs to *ask* the predicate too, and a third name in the same family invites a typo whose two
meanings are both plausible. Proposed split:

| Name | What it is |
| --- | --- |
| `VFSNodeOptions.materialize` | the policy, supplied by the app |
| `node.wants(entry): boolean` | public query — "do I keep this entry's bytes?" |
| `node.materialize(path, from)` | fetch the bytes now, regardless of the policy |

`wants()` has to be public because `planChanges()` is a free function that today receives only
`nodeId` ([sync.ts:437](../src/sync.ts#L437)) and will need to consult the destination node's policy.
This mirrors the `ignore` / `excluded()` pair phase 1 established, with the difference that this one
crosses a module boundary.

### 1.3 The source for `materialize()` is an explicit peer

§10.2 of the plan, resolved as it recommends: `node.materialize(path, from: VFSNode)`. A provider
held by the node would invent a lifecycle — when is it set, what happens when the peer goes away,
what does it mean for it to be stale — for a convenience the consumer can wrap in three lines.

## 2. The hole the plan does not mention

§2.3 of the plan says the change is "a condition alongside the `held` one" in two places. Written
literally, that is:

```ts
if (entry.held && entry.held !== this.id) continue;
if (!this.wants(entry)) continue;              // ← wrong
```

and it corrupts the mirror. The sequence:

1. This node holds `song.flac` on disk — materialised, `mtime` stamped, hash `X`.
2. The app's policy changes, or the file grows past a size threshold, and the predicate now says
   `false` for that entry.
3. A peer updates the file to hash `Y`. `apply()` skips the write.
4. `adopt()` records hash `Y`. **The disk still holds `X`.**
5. The next `scan()` compares `mtime`, finds it unchanged, and takes the fast path: the file is
   assumed to match its entry. The divergence is never noticed.

The entry claims `Y`, the bytes are `X`, and nothing in the engine will ever disagree with itself
about it. That is worse than the false tombstone of phase 1, which at least announced itself as a
deletion.

**The fix is the phase 1 invariant again.** The predicate decides what this node *fetches*, never
what it *abandons*:

```ts
// A policy that turns false does not orphan bytes this node already holds:
// `mtime` present means the file is here, and a file that is here stays
// current. The predicate governs what arrives, not what is already on disk.
if (!this.wants(entry) && before?.mtime === undefined) continue;
```

`before?.mtime === undefined` is *"this node has never seen this file on disk"*, the same invariant
phase 1 leaned on and for the same reason — `adopt()` deletes `mtime` on every entry and only re-sets
it from a real `stat()`. Twice now this property has answered a question it was not written for,
which is a reasonable sign it is the right primitive.

**What this rules out**: there is no dematerialisation by predicate. Making the policy return `false`
for something already on disk does not free the space. Freeing it is a deliberate operation
(`node.dematerialize(path)` — delete the bytes, keep the entry, drop the `mtime`), and it is **not in
this phase**: it needs the predicate to have settled first, and the plan does not ask for it. It is
the exact counterpart of §1.4's "there is no way to untrack without deleting", and it should be
documented as a known gap rather than half-built.

Two notes on the edges of that table.

**`fileHashes()` only affects a count.** It builds the set of hashes a peer can serve, which feeds
`countTransfers()` and therefore the dry run's estimate. Getting it wrong does not lose data; it
reports a transfer that will not happen. It still has to take the node, for the same reason
`planChanges` does.

**`chain()` needs nothing.** It skips `entry.held` explicitly, and for an unmaterialised entry it
simply `stat`s, finds no file, and moves to the next candidate path — correct already, thanks to the
phase 1 fix. Consulting the candidate's predicate would save a round trip per miss, which on Drive is
not nothing, but it is an optimisation and it belongs with phase 5, not here. Recorded so the
omission is visibly deliberate.

**The verified write has to be extracted, not copied.** `apply()`'s write loop hashes on the way in,
streams above the threshold, and refuses content that does not match what `vfs.json` declares. The
comment above `apply()` explains why that check is not optional — without it a truncated upload lands
as "the newest version". `materialize()` needs identical behaviour, and a second copy of it is a
second place for the two to drift apart.

## 4. What other peers see

Nothing. This is the property that makes the design cheap, and it is worth stating as a rule:
**nothing about materialisation is stored, so nothing about it can travel.** A peer does not know
which of its neighbours hold which bytes, and does not need to — the content search already asks each
candidate and moves on when the file is not there.

The alternative the plan rules out (§2.2) is a per-entry field like `mtime`/`native`. It would ride
in `canonicalEntry`, and a stale marker from another peer is actively harmful: B would adopt A's mark
and stop syncing a file it does have. That is the same class of bug as §2 above, arriving over the
wire instead of from a policy change.

## 5. Tests

New file `test/materialize.test.ts`:

1. **The entry travels, the bytes do not** — B's predicate rejects a file; after sync B has the entry
   live and no file on disk.
2. **No tombstone follows** — the next `scan()` on B leaves it live and emits no `delete` row. (Half
   of this is phase 1's, but the pairing is the actual feature.)
3. **The staleness regression of §2** — B materialised the file, then the predicate turns false, then
   A updates it. B's disk must hold the new bytes. *This is the test that fails against the literal
   reading of the plan*, and the one to write first.
4. **Deletion still reaches an unmaterialised entry** — A deletes, B tombstones it without ever
   having had the file.
5. **Rename of an unmaterialised entry** — B records the new path and attempts no rename on disk.
6. **`materialize(path, from)` fetches and verifies** — the bytes land, the hash is checked, and the
   next scan stamps the `mtime` so the entry becomes ordinary.
7. **`materialize()` rejects corrupt content** — a source serving bytes that do not match the
   declared hash throws and leaves no file behind.
8. **A conflict copy on an unmaterialised entry** resolves through `retire()`, which is the path
   phase 1 already opened.

**And one existing test has to be qualified.** The property test asserts that `vfs.json`'s live file
entries are exactly what is on disk ([convergence.test.ts:113-119](../test/convergence.test.ts#L113-L119)) —
the check that exposed all four bugs in the phase 1 walkthrough §3. With a `materialize` predicate in
play that is no longer an equality: the disk is a *subset*. It becomes

> every live file entry has a file behind it **unless** it is held elsewhere or this node's policy
> declines it — and nothing is on disk that is not a live entry.

The walkthrough §7.2 predicted exactly this and recommended settling the invariant before phase 2
landed. Since the phase-2 form is strictly more general, it gets written once, here, and extended to
the two property tests that never had it — the rotation one
([:141](../test/convergence.test.ts#L141)) and the two-peer mesh one
([:161](../test/convergence.test.ts#L161)).

## 10. Decision — `dematerialize()` is in this phase

§2 above documented "no dematerialisation by predicate" as a known gap. It stops being a gap: the
operation exists, it is just not the predicate's job. The rule §2 established is untouched and is
what makes this coherent — **the policy governs what arrives; releasing what is already here is
stated, never inferred.** That is the same sentence phase 1's walkthrough §4 arrived at for
`retire()`, applied to bytes instead of entries.

```ts
/** Releases the bytes, keeps the entry. The mesh does not notice. */
async dematerialize(path: string, from: VFSNode): Promise<void>
```

### 10.1 The order of the two writes is load-bearing

The operation is two steps — drop the `mtime` from `vfs.json`, delete the file — and **the order is
not a preference.** Written the other way round it reintroduces B.1 exactly:

| Order | Crash window leaves | Next `scan()` |
| --- | --- | --- |
| header first, then delete | entry says "not here", file still on disk | re-stamps the `mtime`, back to materialised |
| delete first, then header | entry says "seen on disk", file absent, no rule covering it | **tombstone → deleted on every peer** |

The first row self-heals for a reason worth spelling out, because it is not obvious that it heals
*silently*: `scan()` finds the file, matches `prior` by path, computes `changed` from the hash — which
is unchanged — and so emits no log row and re-stamps neither `updated` nor `peer`
([vfs-node.ts:414-425](../src/vfs-node.ts#L414-L425)). It stamps `mtime` unconditionally. A failed
dematerialisation is therefore indistinguishable from one never attempted, which is the right
outcome for a half-finished local operation.

The second row is the phase 1 bug with a new cause. It is worth stating in the spec as a general
rule, since it will come up again: **the record that this node no longer holds the bytes has to land
before the bytes go.**

### 10.2 It does not travel, and it cannot

`mtime` is outside the `state` digest but survives the round trip
([vfs-file.ts:50-53](../src/vfs-file.ts#L50-L53)). Three consequences, all of them the ones we want:

- `state` does not change, so dematerialising does not make a peer think there is anything to sync.
- No log row, no `updated`, no `peer`. It is a local storage decision, not a mesh operation — the
  same argument phase 1 used for preserving.
- The entry stays out of `vanishedByHash`, so a new file with the same content elsewhere cannot claim
  its uuid ([vfs-node.ts:365-368](../src/vfs-node.ts#L365-L368)).

### 10.3 Why `from` is required

The hazard is real and the library cannot see it: dematerialising the **last** copy of a file leaves
the entry alive across the mesh with the bytes nowhere. Nothing about materialisation travels (§4),
so no peer can be asked "does anyone still have this?" in general.

What *can* be done is the specific check: `from` must be able to serve the entry's hash, verified
through the same lookup `chain()` uses, before anything is deleted here. It is a sanity check and not
a guarantee — the peer could lose the bytes a second later — but the case it catches is the realistic
one (nobody has it), not the race.

The argument for making it required rather than optional: **if no peer holds the bytes, what the
caller wants is a deletion, and it should look like one.** `delete` already exists, it emits a
tombstone, and it travels. Letting `dematerialize()` quietly become a deletion-without-a-tombstone is
the one shape this operation must not have.

The cost is ergonomic: a phone freeing space needs a live handle to a peer that has the file. The
consumer wraps it. If that turns out to bite in practice, the escape hatch is a second signature
taking a hash the caller has verified elsewhere — not a nullable `from`.

### 10.4 What happens next is the predicate's call

After `dematerialize()`, `mtime` is gone, so the guarded condition of §2 —
`!wants(entry) && before?.mtime === undefined` — now skips the entry, and it stays unmaterialised.

But if the policy says `true` for that entry, the next sync fetches it straight back. That is not a
bug, it is what "the engine stores nothing" means: **the predicate is the steady state, and
`materialize()`/`dematerialize()` are manual moves the predicate is free to undo.** A consumer that
wants a dematerialisation to stick changes the policy, which is the thing that expresses intent.
Documented next to the method, because it is the second assumption a reader will make after §2's.

### 10.5 Additional tests

9. **`dematerialize()` frees the bytes and keeps the entry** — file gone from disk, entry live, no
   log row, `state` unchanged on both peers.
10. **The freed entry is not tombstoned** — the next `scan()` preserves it, which is phase 1's rule
    doing the work.
11. **The crash window heals in the safe direction** — an entry whose `mtime` was dropped while the
    file is still on disk comes back as materialised on the next scan, with no row and no `updated`
    bump.
12. **`dematerialize()` refuses a peer that cannot serve the hash** — nothing is deleted.
13. **A policy that still wants it re-fetches on the next sync** — §10.4, pinned so the behaviour is
    a decision and not an accident.

## 11. Decision — recovery from B.1, as a documented procedure

No engine code. The reason it can be a procedure at all is the asymmetry the plan found in §0: **the
peer that applied the rule kept its bytes.** Its walk stopped returning the path, so nothing ever
deleted the file; it is an orphan on disk with a tombstone in the tree. The bytes exist. What is
needed is a way to re-adopt them.

The procedure, on the peer that has the rule and the orphaned bytes, running phase-1 code:

1. **Upgrade first.** On pre-phase-1 code every step below is done next to the bug that caused this.
2. **Remove the rule** and `scan()`. The walk returns the path again. The old entry is a tombstone,
   and `byPath`/`byNative` are built from live entries only
   ([vfs-node.ts:320-324](../src/vfs-node.ts#L320-L324)), so no prior is found and the file is
   adopted as new.
3. **Sync.** The file propagates to the peers that lost it.
4. **Put the rule back.** With phase 1 in place the entry is now *preserved*, not tombstoned — which
   is the same procedure serving as a demonstration that the fix works.

What it costs, stated plainly so nobody is surprised: **a new `uuid`**. The recovered file is a new
identity, the old tombstone stays in the log as history, and the file's ancestry starts over. Content
is recovered; provenance is not.

**The case this does not cover**: no peer still has the bytes on disk — the file was deleted on the
ignoring peer as well, after the tombstone. Then it is gone and the answer is a backup. The library
has nothing to offer there and should say so rather than implying otherwise.

**Why not an engine-side `rescue()`**: it would have to distinguish a tombstone caused by the bug
from a legitimate one, and the evidence to do that does not exist — both look identical in the tree.
Guessing would resurrect files a user deliberately deleted, which is the mirror image of the bug we
just fixed. The version that guesses in the safe direction is the manual procedure, driven by a
person who knows which rule they added.

This goes in `docs/recipes.md` next to the `ignore` semantics phase 1 corrected, and it is the last
thing blocking a release of phase 1.

## 13. Correction to the plan: the predicate has to pull, not only filter

§2.3 of the plan lists two sites and says the change is a condition at each. That is the *filter*
half, and on its own it makes the policy a one-way door: `apply()` decides what to write by diffing
the tree, so it only ever writes when a **hash changes**. Widen the predicate — pin a folder, raise
a size threshold — and nothing happens. The content arrives if and only if somebody happens to edit
it afterwards.

That cannot be right. It would leave two unrelated ways to ask for the same content: a predicate
that only ever declines, and a per-path `materialize()` call for everything you actually want. So
the write condition gains a third clause:

```ts
if (!wasLive || before.hash !== entry.hash || !materialised(before)) writes.push(entry);
```

An entry this node wants and has no bytes for is a write, even though nothing about it changed.
Reaching that line already implies the policy wants it — the skip above returned otherwise — so the
clause reads exactly as "fill in what is missing".

This is what makes the predicate the *interface* rather than a filter bolted onto one: pinning is
widening it, unpinning is narrowing it plus `dematerialize()`. §10.4 above described that behaviour
as if it already fell out of the design. It did not; it needed this.

### 13.1 And the fast path had to learn about it

The refill exposed a second-order problem, and it is the more interesting one because it is a direct
consequence of a decision made two sections earlier.

`sync()` short-circuits on one comparison: same `state`, same log digest, nothing to do
([sync.ts:141](../src/sync.ts#L141)). But **`state` deliberately does not describe materialisation**
— §10.2 argued for exactly that, and phase 1 §1.4 argued the same for `ignore`: a digest that
reflected local policy would never agree between two peers with different policies, and they would
sync forever. The consequence had not been drawn: two peers can agree on the tree while one is still
missing bytes it wants, and the fast path skips the transfer that fixes it. Dematerialise a file and
sync — nothing happens, for a reason nothing reports.

The fix is a local check next to the digest comparison, `refillable()`
([sync.ts:546](../src/sync.ts#L546)), and its shape matters more than its existence:

> It asks whether the **other side looks able to serve** what this side is missing, not merely
> whether something is missing.

Asking only "am I missing anything?" would put a mesh where nobody holds the bytes onto the slow
path on every pass, re-planning a transfer that cannot happen and never reaching a fixed point.
Asking about the far side keeps that mesh on the fast path — incomplete, but stable and honest.
Entry inspection only, no I/O, and the common case never looks at the far side because it exits on
an empty `missing`.

The general rule, which belongs in the spec: **`state` answers "do we agree?", not "am I done?".**
Anything deliberately outside the digest needs its own reason to keep working.

## 14. What the feature uncovered

Four places assumed a live entry implies a file on disk. Phase 1 made that assumption false; phase 2
made it false as a matter of routine. Two of these were latent from phase 1 and were only reachable
through the new API, which is why they surfaced now and not in `f3acd3f`.

### 14.1 `adopt()` would have lost the stamp it had just earned

`adopt()` skips the `stat` for an entry whose path and hash are unchanged, carrying the previous
`mtime` over — a deliberate optimisation, because on Drive re-statting every untouched entry is a
round trip per file. But after a refill the path and hash are *also* unchanged: the bytes arrived to
match what the tree already said. The fast branch would carry over the absent `mtime`, the entry
would stay "not materialised here", and the next sync would fetch the same bytes again. Forever.

The condition now requires the previous entry to have been materialised, and the `stat` branch is
gated on whether this node will have the file at all — `wants(entry) || materialised(before)`, the
same predicate `apply()` uses. That keeps the optimisation exactly where it was worth having (a
catalogue of entries whose bytes are elsewhere is never stat'ed) and pays for the one case that
needs it.

### 14.2 `commit()` discarded the record of having the bytes

`sameEntries()` compares path, hash, size and deleted — deliberately not `mtime`, since a touched
file with identical content is not worth a write. But that also meant *acquiring or losing the bytes*
was not worth a write, and `commit()` returned early without persisting it.

The consequence was the interrupted `dematerialize()` of §10.1 not actually healing: the scan
re-stamped the `mtime`, `commit()` threw the result away, and the entry claimed forever that the
bytes were not here while the file sat on disk. Stable, no tombstone — but permanently wrong, and
with §13's refill it meant re-fetching bytes already on disk on every sync.

The comparison now includes `materialised(held) === materialised(entry)`. Not the `mtime` value —
the distinction is the point: *whether there is one* is a fact about this node's storage, and the
value is not.

### 14.3 `apply()` would copy from a path holding nothing

`apply()` builds a map of content it already has, to avoid pulling over the wire what is sitting
somewhere else in the folder. It was built from every live file entry with a hash. An unmaterialised
entry put a path in that map with no file behind it, and the copy read it: `ENOENT`, mid-apply, with
some writes already done.

This is §3.2 of [phase 1's walkthrough](./2026-08-12_01h47.v2-implementation-plan.walkthrough.md) —
`chain()`'s bug — on the receiving side. The same confusion, that an entry is not a file, in the one
place phase 1 did not look, because nothing could reach it then.

### 14.4 A conflict copy without bytes was immortal

Phase 1 gave `resolve()` a special case: a copy `held` on another peer has no file here, so removing
it proves nothing and the tombstone is written outright by `retire()`. Phase 2 adds a second way to
have no file — the policy declined it — and the `held` check does not see it. `resolve('mine')` then
deleted nothing, inferred nothing, and the conflict never went away.

The condition is now `materialised(copy)`, which subsumes the `held` case rather than sitting beside
it. The phase 1 walkthrough §4 predicted the shape of this ("the primitive phase 2 will need for the
same reason at a larger scale") and it turned out to be one condition, not a new mechanism.

## 15. Tests

[`test/materialize.test.ts`](../test/materialize.test.ts), 15 tests — the 13 planned plus two the
work produced. Every test in §5 and §10.5 is there.

Two are worth calling out because they encode decisions rather than behaviour:

- **"keeps bytes it already holds current when the policy turns against them"** is §2's regression,
  the one that fails against the literal reading of the plan. It was written first.
- **"stays freed when the policy declines it"** pins the two-move idiom for unpinning. It exists
  because §13 makes either move alone incomplete, and that is a property a consumer will otherwise
  discover by being surprised.

**Honesty about what these prove**: unlike phase 1's, none of them is a regression against `main` —
they all exercise an API that did not exist. The four bugs in §14 are real and pre-existing in shape,
but each was found *by* a test that could only be written after the feature, so each has teeth by
construction rather than by the stash-and-run check phase 1 used.

**The property test invariant is settled**, which was the item phase 1 left open. It is now a shared
`mirrors()` helper asserted by all three property tests, where before only the first had it. The
phrasing moved from "live file entries == what is on disk" to "the entries this node **claims to
hold** == what is on disk", which is the general form: it degrades to the old equality when no policy
is in play, and it is the check that would catch a `materialised()` that lies in either direction.

## 16. What this changes upstream

**For the spec** (§8 of the plan, §4 of the requirements document). The *Absence* row gains a
second clause and there is a new row:

| Rule | Where it came from |
| --- | --- |
| A node's materialisation policy is never evidence about anything, and never travels | §4 |
| `state` answers "do we agree?", not "am I done?" — anything outside the digest needs its own reason to keep working | §13.1 |
| Content is refilled when the tree is agreed but the bytes are absent, decided against what the far side holds | §13 |

The second is the one a second implementation would most plausibly get wrong, and the failure is
silent: it would agree on every digest and quietly never transfer anything.

**For the plan.** §2 is done. `dematerialize()` was not in it and is (§10). The `materialize()`
source question (§10.2 of the plan) is closed in favour of the explicit peer, and `dematerialize()`
inherited the same shape for a stronger reason — there it is a safety check, not just ergonomics.

**For phase 5** (native fast path). `fetchContent()` is now the single place a transfer is decided,
which is the seam §6 of the plan asked to keep clean for a possible delta transfer. It is cleaner
than it was: one method, one hash check, one call site pair.

## 17. Left open

1. **Release of phase 1.** §11's recovery procedure is written into `docs/recipes.md`; publishing
   0.1.25 is a decision, not a task.
2. **`refillable()` is O(n) on the sync fast path.** One pass over the local entries per sync, no
   I/O, exiting before touching the far side in the common case. Fine at catalogue scale, but it is
   new work on the path that exists to do none, and worth remembering if the fast path is ever
   measured.
3. **No `dematerialize()` for a whole subtree.** One path at a time, one verification each. A phone
   unpinning an album makes one call per file. Nobody has asked for the batch form, and inventing it
   before the shape of the ask is known would be guessing.
