## 1. Why the wipe is the entire mechanism

§16 of the previous session already landed the rule that makes this cheap:

> a uuid inside a mesh is minted once and never rewritten; matching by path may only make two entries
> one file where the answer cannot be wrong — and one of those cases is **a folder that has never
> synced**.

That case is `MergeSide.joining`, computed in [sync.ts:618](../src/sync.ts#L618) as
`fileA.syncId === null`, and consumed by `samePath` at [merge.ts:225](../src/merge.ts#L225).

So a folder that has just discarded its store *is* a joining side, by construction. **`merge.ts` needs
no change at all** — §13 of the previous plan wanted `pairEntries` to take "which side is virgin", and
it already does. What is left is making a losing folder genuinely virgin, and making that decision
travel.

## 2. The contract change, stated plainly

`adopt` stops meaning "authorise" and starts meaning "choose". This is a **breaking change of
meaning with no change of shape**: same action, same `side`, same `options.adopt: { syncId }`, and a
caller that keeps passing the same thing now gets a different outcome.

It has to be this way. The moment the outcome is "one mesh's store survives", `min(syncId)` is no
longer available: it would let a rule nobody chose decide which folder loses its tombstones and its
merge bases. The doc comment on `ConflictAnswer` ([sync.ts:133](../src/sync.ts#L133)) says the
opposite today and is rewritten with the reason inverted — *naming a side does choose the outcome,
because there is an outcome now.*

Two existing tests assert the old rule by name and are rewritten, not deleted:

- `the pairing guard > merges when the caller names one of the reported ids` — "the smaller of the
  two survives" ([pairing.test.ts:220](../test/pairing.test.ts#L220))
- `answering the pairing question > adopts one of the two groups when told which one stays`
  ([pairing.test.ts:258](../test/pairing.test.ts#L258))

`docs/conflicts.yaml` carries the same claim in a comment under `foreign-mesh.returns` and is the
other copy of it; `test/decisions.test.ts` already checks the catalogue against `legalAnswers()`, so
the vocabulary itself does not move — `['adopt', 'abort']` stays.

## 3. `absorbed` — where the decision lives, and how it reaches everyone

One header field, not one per file:

```jsonc
"absorbed": ["<syncId of every mesh this one has taken in>"]
```

**It converges by union, in `convergeConfig()`**, beside `text`
([sync.ts:1073](../src/sync.ts#L1073)). That is the whole of its propagation: nothing new plumbed,
and it reaches every peer of the winning mesh at the pace of syncing.

The union is what makes it chain: when the winner absorbs the loser it takes
`winner.absorbed ∪ loser.absorbed ∪ { loser.syncId }`, so a mesh that had itself absorbed another one
does not strand *that* mesh's stragglers. And a peer that gets wiped joins with `absorbed: []`, then
unions the winner's list on the very pass that admits it — so the wiped folder carries the record of
its own absorption forward and can answer for the mesh it came from.

Out of `DIGEST_FIELDS` (it is a header field; the digest is over entries), so two peers that disagree
about `absorbed` still agree on `state`, and disagree for at most one pass.

### The sharp edge, taken deliberately

**One person's answer discards the `.vfs` of every straggler of the losing mesh, whenever they turn
up, with nobody present.** This was §12 of the previous plan, offered for veto and not vetoed; it is
taken as decided here.

The reason it is right: the answer is already forced. Adopting in the other direction would undo a
decision the winning mesh has recorded and would re-split the mesh that has since converged. Asking
each straggler is theatre with a destructive default. What the alternative buys — a second human
confirmation — it buys at the price of a mesh that never finishes merging.

## 4. The discard, and a correction to the order §13 proposed

§13 said: *delete `vfs.json`, `commits`, every `commits-*`, every snapshot and the base copies, in
that order, so a crash halfway leaves a folder that reads as virgin rather than as a mesh member with
no log.*

**That order is the dangerous one.** `vfs.json` gone and `commits` still present is not a virgin
folder: `store.init()` lays down a fresh empty header, and then `logRows()` reads the leftover
segment off disk and hands back the *old mesh's rows*. Worse, `append()` compares the file's size
against `log.size` (now 0), decides the segment "grew underneath us", and folds those rows into the
new log ([store.ts:190](../src/store.ts#L190)). A folder that reads as a newcomer while quietly
carrying the history of the mesh it left is the one state this whole design exists to prevent.

So: **delete what the header points at first, and replace the header last.**

```
discard():
  1. base/*                          — merge bases, local scratch, referenced by nothing
  2. every vfs-<ts>.json snapshot, every commits-<ts> archive   (named in log.snapshot / log.archives)
  3. commits                         — the active segment
  4. write a fresh vfs.json          — replaces, never absent: syncId null, new peerId, empty log
  5. invalidate()
```

A crash at any point before 4 leaves a folder that still claims the losing `syncId` with a log that
is partly gone. That state is **self-healing**: the next pass reads it as a member of the losing mesh,
finds its `syncId` in the winner's `absorbed`, and discards again — this time to completion. The
degraded reads in between (`readSnapshot` → `[]`, `readArchive` → `[]`, `logRows` → `[]`) cost
conflict copies, never state.

`vfs.json` is never absent at any point, so there is no window in which `init()` can mint a fresh
store over a live log. The only torn-write hazard left is the one every `store.write()` already
carries.

## 5. `local` survives the wipe — a hazard §11 did not list

`LocalState.ignore` ([types.ts:300](../src/types.ts#L300)) is **this node's exclusion patterns**, set
through `setLocalIgnore()` and deliberately not shared. Wiping it would silently change *what the
folder synchronises*: files a person excluded on this device would start travelling on the next pass.
That is not history being given up — it is a setting being lost, and nobody outside this folder holds
a copy to restore it from.

So `discard()` carries `local.ignore` onto the fresh file and drops everything else in `local`:

| field | fate | why |
| --- | --- | --- |
| `ignore` | **kept** | node-local configuration, held nowhere else |
| `driveChangeToken` | dropped | a cursor into a change feed, meaningful only against the scan state that is gone |
| `verifiedAt` | dropped | a claim about a mirror that no longer exists |
| `pendingRenames` | dropped | names uuids that no longer exist |

`text` is wiped with the rest and comes straight back: it converges by union from the winner on the
same pass.

## 6. A fresh `peerId`, and why it is not optional

The winner holds `peers[loser.peerId] = { segment, offset, digest }` — an offset into a log that has
just been deleted. Keeping the id would leave the winner reading a tail that is not there
(`readPeerLog` against a segment stamp that no longer exists) and comparing a digest that can never
match again.

Minting a fresh one makes the stale mark simply unreferenced instead of misleading. `VFSNode.discard()`
therefore moves `this.id` the way `reidentify()` already does
([vfs-node.ts:252](../src/vfs-node.ts#L252)) — same pattern, same reason.

Accepted cost: the winner keeps a dead peer mark for the old id. It is a few dozen bytes and it is
never read; pruning it would need "has everyone stopped using this id?", which a mesh cannot answer.

## 7. The real pass plans twice; the dry run stops at the seam

**The real pass.** A discard changes the inputs to the merge — new uuids, no tombstones, no
ancestry — so the merge must be computed *after* it. `sync()` therefore plans, and if planning
performed a discard, plans once more:

```
plan = planSync(...)          → settlePairing discards, signals it
if (plan.discarded && !dry) plan = planSync(...)   → the loser is virgin now; pair() is benign, nobody is asked again
```

At most twice, only when a human authorised a wipe, and the second pass re-scans the folder whose
mirror was just deleted — which is exactly the input the pass needs.

**The dry run models nothing and discards nothing.** It reports the discard and stops:

```ts
preview.discarded  // { side: 'b', syncId: 'g-…' }  — what this pass would delete
preview.applied    // false
preview.actions    // { toA: [], toB: [] }
```

The temptation is to force `joining: true` on the loser and preview the merge anyway. It would lie,
and it would lie in precisely the cases §11 lists as the accepted damage: the preview still holds the
loser's tombstones (so a file the loser deleted looks like it stays deleted, when the real pass brings
it back) and still holds the loser's log (so divergences the real pass will park as conflict copies
resolve by ancestry in the preview). A preview computed from inputs the real pass destroys is a
preview of nothing in particular — the same argument
[`planSync`'s own doc comment](../src/sync.ts#L483) already makes about having one implementation.

So the rule, and it goes in the doc comment: **a preview cannot describe a merge whose inputs it
refuses to create.** The consumer's loop is unchanged in shape — preview, show the person what is
about to be deleted, sync for real.

## 8. Order of writes when the decision lands

Two destructive-ish operations, and the order between them is decided by which half-done state is
recoverable:

1. **the winner records `absorbed` and writes** — `winner.store.write(file)`
2. **the loser discards** — §4

Crash between them: the loser still carries the losing `syncId`, the winner says it is absorbed, and
the next pass discards it with no question. Recovers by itself.

The reverse order does not: the loser is virgin and joins fine, but nothing anywhere records that the
mesh was taken in, and every straggler asks again.

Both land **before the merge is computed**, and both survive a file conflict stopping the pass a
moment later. That is the precedent `settlePairing` already sets for `reidentify`
([sync.ts:1000](../src/sync.ts#L1000)): *the identity was broken, the caller said which side fixes it,
and retrying the pass is free.*

One ordering that is not negotiable: the **version check stays first**
([sync.ts:951](../src/sync.ts#L951)). A folder this engine cannot interpret must never be discarded —
it might be readable by the engine that wrote it, and the bytes of `.vfs` are the only copy of its
history.

## 10. What has to hold

1. Two established meshes, each with files the other has never seen: one answer, **no per-file
   question**, and every file from both folders present on both sides afterwards.
2. **An established peer's uuid for a file never changes** — asserted directly on the winner's side,
   in every topology this session touches. It is the invariant §16 landed and the thing most likely to
   be broken by accident here.
3. The loser keeps **every byte of content**, including files the winning mesh has never seen, which
   enter it as ordinary creates.
4. A straggler whose `syncId` is in `absorbed` joins with **no `ConflictError`** and no `decide` call.
5. `absorbed` chains: a mesh that absorbed X then loses to Y leaves X's stragglers able to join Y.
6. `dryRun` on a `foreign-mesh` pair leaves **both `.vfs` folders byte-identical**, reports
   `discarded`, and writes nothing — including in the answered case.
7. A version-unreconcilable folder is **never** discarded, even with an answer naming the other side.
8. `local.ignore` survives the discard; a path excluded on the loser is still excluded afterwards.
9. Delete-then-recreate at the same path still does not pair, and `path-collision` between two
   established peers still fires — the previous session's tests stay green untouched.
10. A discard interrupted after step 3 of §4 heals on the next pass rather than joining the mesh with
    its old log.

## 12. Risks and accepted consequences

Written down so nobody rediscovers them as bugs — §11 of the previous plan, plus what this pass
found:

- **Deletions the loser made come back** if the winning mesh still holds the file. A tombstone is the
  only record that a deletion was deliberate, and the wipe takes it.
- **Text-merge bases go**, so the first conflict on those paths refuses with `no-base` and parks a
  copy. It recovers once both sides have written.
- **Conflict copies parked on the loser stop being pending.** The bytes stay as ordinary files under
  their conflict names; `node.conflicts()` will not list them. This is the consequence most likely to
  reach a person, and it goes in the changelog in those words.
- **The loser re-hashes its whole folder** on the next scan: `mtime` lives on the entries, and they
  are gone. Correct, and expensive exactly once.
- **A dead peer mark on the winner**, per §6.
- **`absorbed` grows** by one id per mesh ever taken in, never pruned — "every straggler has arrived"
  is not knowable. Bounded by how many separate meshes a folder joins, which is a number in the
  single digits or there is a bigger problem.

## 16. What landed, against what was planned

The plan held. Three things it predicted are worth confirming because each was the reason for a
decision:

- **`merge.ts` was not touched.** §1 said the wipe would make the entry rule fall out of what §16 of
  the previous session already landed, and it did: a discarded folder has `syncId === null`, which is
  `MergeSide.joining`, which is `samePath`. The whole entry-level half of this work is a consequence.
- **The delete order of §4** is in `VFSStore.discard()` with its argument in the doc comment, and the
  guard that makes it real is one `stat`: the header is never replaced while `commits` is still on
  disk. A backend that refuses that one delete makes `discard()` throw, and the folder is left
  declaring the mesh it was leaving — which the next pass discards again.
- **§5 (`local.ignore` survives)** is in the store, in the node, and in two tests.

## 17. What the plan got wrong, found while writing it

**§10.2's first test was the trap this repo keeps paying for.** "An established peer's uuid never
changes" was written over two meshes that both held `shared.txt` with *identical bytes* — and
identical bytes pair by hash on their own, under a rule that has nothing to do with this session. The
test passed. It also passed under the mutant that removes the discard entirely, about half the time:
the surviving uuid was then `min(uuid)`, which is the winner's on a coin flip.

It is now written over two versions that differ, so the only mechanism that can pair them is the one
under test. That mutant now kills it every run.

**`absorbed` is eventually consistent, and a test found it before a person did.** The chain test
failed on its first run for a reason that is not a defect: the record travels *by syncing*, like
`text`. A straggler that meets a peer which has not yet heard about the absorption is still asked. The
test now syncs the record forward first, and says so in a comment. Answering twice is harmless — the
second answer either agrees, or lands in the mutual-absorption case below — but it is worth knowing
that "with nobody present" (§3) means "with any peer that has heard", not "with any peer".

**Mutual absorption needed a rule the plan did not have.** Two people answering opposite ways on two
edges leave each mesh recording that it absorbed the other. `pair()` resolves it with `min(syncId)` —
deterministic and transitive, so every edge of the contradiction resolves the same way. That is the
old rule kept for exactly the case it is right for: a tiebreak between two recorded decisions, rather
than a stand-in for a decision nobody made.

## 19. What a consumer sees that the plan understated

The README's todo said two established meshes "ask once per file". What replaces it is better than
"they do not":

- **identical bytes on a path both groups created** — settled silently, no question at all. This is
  the case that was unanswerable before: two files, one name, and the same content on both sides.
- **different bytes on that path** — one file with two versions, so `keep`, `keep-both`, `replace`
  and the text auto-merge all mean something. Before it was a `path-collision`, where the only
  vocabulary was which of the two keeps the name.

That distinction is now a test of its own (`turns one name claimed by two groups into one file with
two versions`), because it is the difference the change actually buys.
