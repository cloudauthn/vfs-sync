Two facts make the rest cheap, both verified in the source rather than assumed:

- **`explorer/src/model.ts` touches no browser global.** `window`, `document`, `localStorage` and
  `navigator` appear in it exactly once, inside a comment. The globals live in
  [`src/adapters/fsa.ts`](../src/adapters/fsa.ts) and [`explorer/src/gis.ts`](../explorer/src/gis.ts),

  ([gdrive.ts:138](../src/adapters/gdrive.ts#L138)), so a fake Drive installed on the global before
  the model builds its adapter is picked up with **no seam added to production code**.
  `addGDriveSource` constructs the adapter itself and has nowhere to inject one, which is exactly why
  this matters.

## 2. Why it is worth doing, beyond the number

These are the four paths where a person **grants something**: read/write access to a folder on their
own disk, and an OAuth token for their Drive. Two things in them are not ordinary coverage:

- **A token in `localStorage`.** `gis.ts` caches an access token so a reload keeps browsing without a
  popup, and its own header calls that a deliberate XSS trade-off. The expiry logic — treat as
  expired a minute early, never race the edge — is 80 uncovered statements of arithmetic on a
  credential.
- **Silence is a feature in one place and a bug in every other.** Both pickers swallow `AbortError`
  on purpose, because a person who closed the folder chooser does not want a warning in the log. That
  same `catch` swallows everything else if the name check ever changes.

## 4. What has to hold

Twenty properties, one test each unless noted.

**Picking a filesystem to browse** — `pickFsaSource`

1. The picked folder joins the switcher: key, label from the handle, backend `local folder`,
   `removable`, `activeSource` naming it, `browseSel` cleared, and the log saying so.
2. Permission denied adds nothing and says so.
3. **A person who closed the chooser is not warned.** `AbortError` leaves the log exactly as it was —
   asserted as an absence, since that is the whole behaviour.
4. Any other failure *is* logged. §3 and §4 are the two arms of one `if`, and only having both makes
   either worth writing.

**Opening a folder as a tab** — `pickFsaVfs`

5. A folder that already holds a `.vfs` store opens straight as a tab, asking nobody
   (`refusingToAnswer`).
6. A plain folder is asked about first, the confirm names it, and answering yes initialises it and
   opens the tab.
7. Cancelling the confirm opens no tab and writes no `.vfs` — asserted on the handle, not on the log.
8. Permission denied opens no tab.

**Connecting Drive** — `connectGDrive`, `addGDriveSource`

9. With no client id configured: warns, adds nothing, and `canGDrive` is false.
10. The first connect asks GIS for a token **with `prompt: ''`**, adds one source labelled
    `Google Drive`, logs `connected Google Drive`, and flips `gdriveConnected`.
11. A second connect with a source already there **reuses the provider and adds no second source** —
    the log says `refreshed Google Drive`.
12. Google refusing the token leaves the switcher untouched and puts the refusal in the log.
13. The adapter it built is usable: one listing through `makeFakeDrive` over the stubbed global
    `fetch`. Without this the other four assert bookkeeping and not a working source.

**Re-attaching on boot** — `restoreGDrive`

14. A still-valid cached token restores the source **with no call to GIS at all** — the popup is what
    this feature exists to avoid, so the assertion is that `initTokenClient` was never reached.
15. An expired cached token restores nothing, silently.

**The token itself** — `gis.ts`

16. `googleTokenProvider` serves a cached token without touching GIS, and refreshes when it is inside
    the one-minute margin. Two assertions, one test.
17. What a refresh stores round-trips through `hasCachedGoogleToken` and `googleTokenExpiry`, and
    `clearGoogleToken` removes it.
18. A corrupt or half-written entry reads as *absent* rather than throwing — the `catch` in
    `loadStored` is the difference between a bad byte in web storage and an explorer that cannot boot.
19. Storage that throws on write (private mode) leaves the provider working; the session simply does
    not survive a reload.
20. A token response carrying `error` rejects with what Google said, not a generic message.

**Left out, and said so rather than forgotten**: `loadGis`'s script injection needs a `document`
stub and only runs when `window.google` is *absent*, which is the one case a stub cannot honestly
simulate — the assertion would be that we appended a `<script>` we then have to pretend loaded. If it
goes in at all it goes in last, and the walkthrough says whether it did.

## 11. Two of these tests proved nothing, and the mutants are what said so

Both passed on their first run. Neither would have noticed the thing it was written for.

**§4.11's first version** asserted that reconnecting asks Google twice from one client. It passed —
but instrumenting it showed the two token requests came from the **first** connect alone: a token
minted with 30 s of life is already inside the provider's one-minute margin, so the render that
follows the connect refreshes it immediately. The second connect asked for nothing, and the mutant
*"always mint a fresh provider"* killed nothing.

Rewritten to the thing that actually separates the two branches: connect, **clear web storage**, and
reconnect. The live token lives in the provider the drive is holding, so the correct code asks Google
for nothing; a provider minted afresh from storage would have to send the person back for a token
they had already granted. That is also a better property than the one it replaced.

**Three tests had no mutant at all** after the first round — the `pickFsaVfs` permission check, the
cached-token path, and the storage round-trip. Two of them survived a mutant that *should* have been
theirs, and the reason is worth keeping: `loadStored`'s expiry check and the provider's own margin
**overlap**, so removing either one leaves the other to compensate. A mutant that deletes one is
absorbed. Mutants 21–24 target each check where it is the only thing standing.

**And two statements the plan did not notice**: `pickFsaVfs` has its own `catch`, a copy of
`pickFsaSource`'s, separately unreached. One of them swallowing every failure would have been
invisible from the other's tests. A twenty-third test and two more mutants close it, and that is what
took cluster A to zero rather than two.

## 12. A flake in the convergence property test — reported, not fixed

`convergence > reaches one state from a random history (seed 7)` failed **three times**, always
during a mutation batch (twenty-odd vitest processes back to back), each time under a mutation in
`pickFsaSource`, `clearGoogleToken` or the like — code the engine cannot reach. It has not failed
once in five isolated runs of that suite, four instrumented full runs, or the four verification runs
of this session.

What the numbers say: the test is deterministic (fixed seeds, an injected clock, a hand-rolled PRNG),
and its duration across four consecutive full runs was **124 ms, 211 ms, 264 ms, 965 ms** — an eight-
fold spread on identical input, against vitest's default **5 000 ms** timeout, which
`convergence.test.ts` does not override.

The best-supported explanation is a timeout under load, and the fix would be one argument —
`it(..., fn, 20_000)` on the property tests. **Not applied**: I did not capture the failure message,
so "timeout" is inference rather than evidence, and raising the limit would also hide a real
slowdown if one ever arrived. It belongs to you, and it is two lines whenever you want it.
