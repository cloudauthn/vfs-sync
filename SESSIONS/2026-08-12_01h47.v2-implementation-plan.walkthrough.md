The core is what §1.3 specified, unchanged:

```ts
const absent = live.filter((entry) => !alive.has(entry.path));
const preserved = absent.filter((entry) => this.excluded(entry.path) || entry.mtime === undefined);
const kept = new Set(preserved.map((entry) => entry.uuid));
const vanished = absent.filter((entry) => !kept.has(entry.uuid));
```

The three details the plan marked as not optional are all there: `preserved` never reaches
`vanishedByHash`, because that map is now built from `vanished`; their uuids go into `used` before
the tombstone loop, which is what keeps both the loop and the rename claim off them; and the entry
is pushed verbatim, with no re-stamping of `updated` or `peer`. No log rows — preserving is the
absence of an operation, and the test asserts it.

`entry.mtime === undefined` needed no new state, exactly as §1.2 argued. It is worth restating why,
because it is the load-bearing part: `adopt()` deletes `mtime` on every entry and only ever re-sets
it from a real `stat()`, and it skips the `stat` entirely for an entry whose bytes deliberately did
not travel. The invariant *"`mtime` present ⟺ this node has seen the file on disk"* was already
upheld by code written for another purpose.

## 2. Correction to the plan: the predicate is not enough

§1.3 proposed `this.ignore?.(entry.path)`. That is wrong, and it fails in the case the feature
exists for.

**The walk prunes at the directory and never descends** ([walk.ts:33](../src/walk.ts#L33)). A rule
written as `(path) => path === '.cache'` stops the walk from entering `.cache`, so `.cache/deep/blob.bin`
never comes back either — but the predicate, asked about that child directly, says `false`. The
child would fall through to `vanished` and be tombstoned, with the parent preserved next to it.

So the check has to ask about the ancestors too:

```ts
private excluded(path: string): boolean {
  if (!this.ignore) return false;
  if (this.ignore(path)) return true;
  for (let cut = path.lastIndexOf('/'); cut > 0; cut = path.lastIndexOf('/', cut - 1)) {
    if (this.ignore(path.slice(0, cut))) return true;
  }
  return false;
}
```

The rule that generalises: **the preservation check has to mirror what the walk actually does, not
what the predicate literally says.** Any future divergence between the two — a rule form the walk
interprets and this does not — reopens the same hole. Worth a line in the spec (§8 of the plan),
because a second implementation could easily get the leaf case right and the subtree case wrong, and
nothing would report it.

`.vfsignore` in phase 3 makes directory-prefix rules the common form, so this is not an edge.

## 3. What the false tombstone was hiding

With the change in, **six convergence tests and one conflict test failed**. None of them were caused
by the new code. All of them were pre-existing bugs that the old behaviour had been covering.

The mechanism is worth stating plainly, because it says something uncomfortable about the property
test:

> The engine would fail to put a file on disk. The next scan found the path missing and declared the
> file deleted. The tombstone travelled, every peer applied it, and the convergence assertion — all
> peers agree — held. **They agreed on having lost the file.**

The property test was never wrong; it was asking whether the peers converge, and they did. What it
could not see was that one of the paths to convergence was destroying data. Removing the false
tombstone removed the cover, and the failures were the bugs becoming visible for the first time.

That is the argument for the ordering in §9 of the plan being right for a second reason than the one
given. Phase 1 was placed first because it is data loss and because A and B.1 both fall out of it.
It also turns out to be the phase that makes the test suite able to see this whole class of bug.

### 3.1 `apply()` deleted a directory before emptying it

The clearest one, and pure data loss on its own terms.

```
deletes = [{ path: "roms", kind: "directory" }]
renames = ["roms/game.bin -> moved/0/game.bin"]
```

`apply()` ran deletes first. Deleting `roms` is recursive, so it took `roms/game.bin` with it, and
the rename then found nothing to move. On the peer that originated the change the file was fine; on
every peer that applied it, it was gone — and gone in a way the next scan reported as an ordinary
deletion.

The two constraints are in tension and both are real:

- a doomed path must be deleted **before** a rename whose destination is that path;
- a doomed directory must be deleted **after** a rename whose source is inside it.

The order that satisfies both, using the parking mechanism that already existed for swaps:

1. delete doomed **files** — frees destinations
2. renames, parking any whose destination is still occupied
3. delete doomed **directories**, deepest first — now empty of whatever was leaving
4. land the parked renames — onto ground the deletes have cleared
5. mkdirs, then writes

### 3.2 `chain()` asked only about the first path

```ts
const entry = candidate.entries.find((item) => /* …hash === hash… */);
if (!entry) continue;
const stat = await candidate.node.stat(entry.path);
if (!stat || stat.kind !== 'file') continue;   // ← next *candidate*, not next entry
```

One `find` per candidate. If that entry had no file behind it, the loop moved to the next peer
instead of to the next path the same peer claimed to hold those bytes at. Duplicate content is
ordinary, so a peer that could serve the file answered "I do not have it".

This one only becomes reachable **because of** phase 1: before, an entry with no file was tombstoned
within one scan, so it was never around long enough to be asked. After phase 1 those entries persist
by design — that is the entire point — and phase 2 will make them the normal case. The fix is to
iterate every matching entry per candidate.

Filed under "uncovered", but it is really "phase 1 created the precondition and phase 2 would have
been the first to hit it".

### 3.3 A collision resolved into another collision

`resolvePathCollisions` grouped entries by path **once**, moved each loser aside, and returned. But
the aside name and the conflict-copy name come from the same formula — path, peer, hash
([merge.ts:82](../src/merge.ts#L82)) — so a version parked aside and a copy made of that same version
land on the identical name, and the second collision was never looked at.

The result was two live entries on one path. That is the one thing the tree must not contain:
whichever is written second wins on disk and the other is silently gone, which then feeds §3.1 and
§3.2 with phantom entries.

It now runs to a fixed point. Two properties matter and both should go in the spec:

- **It terminates.** Every aside name is strictly longer than the name it was derived from, so
  rounds cannot cycle.
- **It is deterministic across peers.** Collided paths are processed in **sorted** order, not in the
  Map's insertion order — insertion order follows how the merge happened to build the array, which
  is not something two implementations can be relied on to match.

### 3.4 `MemoryAdapter.rename` left empty folders behind

It moved the files under a renamed directory but not the `dirs` set, so an empty folder stayed at
the old path and the new path stat'd as missing. v2 syncs empty directories, so this is a real
adapter bug and not just a test artefact — though it is confined to the memory adapter, and the node
and Drive adapters were not affected.

## 4. The deletion that has to be said, not shown

`resolve(uuid, 'mine')` deleted the conflict copy from disk and let the next scan infer the
tombstone. For a copy that is `held` on another peer there are no bytes here to delete, so after
phase 1 the inference correctly refuses to happen — and the copy would never go away.

This is not a wrinkle in phase 1; it is its exact complement:

> **Absence is evidence only for content this node holds. Deleting anything else has to be stated.**

Hence [`retire()`](../src/vfs-node.ts#L857), which writes the tombstone and its log row outright.

It is a small method, but it is the primitive phase 2 will need for the same reason at a larger
scale: a peer holding a catalogue it has not materialised cannot express *any* deletion by removing
files that were never there. Worth remembering when §2.4 of the plan settles the `materialize()`
API — the counterpart operation already exists and should not be invented twice.

Note what this does **not** do: it is not the `forget()` that §1.4 rules out. `retire()` deletes
from the mesh, deliberately and visibly. §1.4's argument stands untouched — there is still no way to
untrack without deleting.

## 5. Tests

[`test/absence.test.ts`](../test/absence.test.ts), 9 tests, plus one in
[`test/merge.test.ts`](../test/merge.test.ts) for §3.3. Every test from §1.5 of the plan is there.

**Seven of the ten fail on `main`.** Verified by stashing `src/` and running them against the
unchanged engine. Which three do not, and why, is the part worth recording:

| Test | On `main` | Why |
| --- | --- | --- |
| *still tombstones a real deletion* | passes | It is the safety net against overcorrecting. It **must** pass on both sides — that is its job |
| *resolves a conflict copy whose bytes never travelled* | passes | `main` tombstones the copy via the bug. It guards §4, which only exists in the new regime |
| *serves content from any path…* | passes | `main` clears the phantom before anyone asks for it (§3.2). A forward guard, not a regression |

Saying which tests are regressions and which are forward guards is not pedantry: a test that passes
before and after the change it claims to cover proves nothing about that change, and three of these
would have been quietly miscounted as proof.

**A trap worth recording.** The first draft of these tests asserted through the wrong node. A rule
arrives by reopening the folder (`VFSNode.open(fs, { ignore })`), which gives a second `VFSNode` over
the same adapter — and `VFSStore` caches the decoded file in memory
([store.ts:100](../src/store.ts#L100)). The two nodes do not share that cache, so assertions made
through the original node read pre-change state and passed against `main`. Every assertion now goes
through the node that did the work. Anything testing a reopened folder has to do the same.

## 6. What this changes upstream

**For the plan.** Phase 1 is done, so the strict ordering constraint (1 before 3) is discharged and
phase 3 is unblocked. B.1 in the requirements document is closed. §2 (selective materialisation) is
in the state the plan predicted: the first row of its table in §2.3 — reconciliation does not
tombstone a dematerialised entry — is already true, for free, and there is a test pinning it.

**For the spec (§8 of the plan, §4 of the requirements document).** The row it adds for *Absence* is
right but underspecified. Three rules belong in it, and each of them is a place where two
implementations could differ without any error being raised:

| Rule | Where it came from |
| --- | --- |
| Exclusion is evaluated over the path **and its ancestors**, matching the walk's pruning | §2 |
| A doomed directory is removed **after** the renames leaving it, and before the parked ones land | §3.1 |
| Path collisions resolve to a **fixed point**, processed in sorted-path order | §3.3 |

The second and third are new rows, not refinements: neither `apply()`'s operation order nor the
collision fixed point appears anywhere in the plan's table, and both are exactly the kind of rule
whose divergence gives silent data loss rather than an error.

**For the property test.** It should be strengthened with an invariant it currently does not assert:
*every live file entry has a file behind it, on every peer, after every sync*. That is the check
that found all four bugs in §3, and it catches the "converged on losing the file" case that pure
convergence cannot see. Small, cheap, and it belongs in the conformance suite too.
