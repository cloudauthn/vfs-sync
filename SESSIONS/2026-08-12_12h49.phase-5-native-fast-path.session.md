## 0. Why it is worth more now than when it was written

The plan gives the reason in one line: §9 gave up deduplication, so there will be more real transfers.
The other half is topology. The case this exists for is not "laptop syncing with Drive" — those are
two different backends and nothing here applies. It is **two folders inside one backend**: two
`ScopedAdapter`s over a single Drive, a server reconciling two roots on one filesystem. There, every
byte currently makes a round trip out of the backend and back into it, through the process, for
nothing.

## 1. The plan says one site. There are two

```ts
const handle = await source.open(hash, entry);   // vfs-node.ts:1003, in fetchContent()
await this.copy(from, to, size);                 // vfs-node.ts:1023, called at :932 and :985
```

The first is the cross-node transfer the plan describes. The second is **intra-adapter already**: it
stages a conflict copy inside one folder, reading the whole file out and writing it back in. Same
backend by construction, so it needs no identity question, no verification argument and no new
interface beyond the copy operation itself. It is the cheap half and it lands in the same session.

## 2. What "the same backend" means (question 4)

**An opaque string the adapter declares. Equal and non-null means the same backend; anything else
means pump the bytes.**

```ts
/**
 * Identity of the *backend instance* — the account, the filesystem, the store —
 * not the kind of backend. `null` when the adapter cannot tell.
 */
backendId?(): Promise<string | null>;
```

Async because Drive may need a request to answer, and cached by the adapter because the engine will
ask on every pass.

The asymmetry of the two errors is what settles the shape:

| | Cost |
| --- | --- |
| False negative (same backend, reported different) | one ordinary transfer — exactly today's behaviour |
| False positive (different backends, reported equal) | a copy from the wrong account, or a copy that cannot happen and fails mid-sync |

So the burden of proof is on *equality*, and an adapter that is unsure answers `null`. What each one
answers:

| Adapter | `backendId()` | Native copy |
| --- | --- | --- |
| `node-fs` | a constant | `fs.copyFile` |
| `gdrive` | `${space}:${root fileId}` | `files.copy` |
| `scoped` | the base adapter's answer | delegates to the base, re-rooted |
| `memory` | per instance | a map write |
| `opfs`, `fsa`, `handle` | undefined | none — the API has no copy |

**`node-fs` answering a constant looks like it breaks the rule and does not.** Two `NodeFsAdapter`s in
one process are reachable through the same `fs` module by construction; there is no such thing as two
node-fs backends that cannot copy between each other, even across devices or mounts — `copyFile` still
works, and it still keeps the bytes out of the process. "Different accounts" is a Drive problem, not a
filesystem one.

**Drive is the one that has to be careful.** The identity is the account, and the cheapest thing that
identifies it without extra scopes is the *resolved* root fileId: globally unique, and already needed
by everything the adapter does. When the caller gave an explicit `rootFolderId` that is the answer
directly. When it is `'root'`/`'appDataFolder'` it takes one `files/root?fields=id` request, cached
forever after — and if that request is refused, `null`, no fast path. Two Drive adapters on the same
account but *different* root folders will disagree and lose the fast path. That is a false negative,
which is free.

## 3. What the fast path gives up, which is not what the plan says

The plan says hash verification cannot be skipped. Look at what today's check actually proves:

```ts
const data = await handle.read();
const actual = await sha256(data);
if (actual !== hash) throw ...        // vfs-node.ts:1014-1018
```

The bytes are hashed **as they leave the source**, not as they land. So the invariant is not "the write
succeeded" — nothing re-reads the destination, then or now. It is *"the source served what the tree
says it holds"*. Two different guarantees hide in one check:

- **copy fidelity** — the destination gets what the source has. A native copy gives this by
  construction: it is the backend copying its own object.
- **tree fidelity** — what the source has is what `vfs.json` says it has. This is what the re-hash is
  really buying, and the fast path is where it is lost.

Tree fidelity breaks when a file changed behind the engine's back since the last scan. Today that is a
loud error mid-sync. With a native copy it would be silent, and worse than silent: the destination
would record the tree's hash over content that does not match it.

**So the fast path is allowed, and it is bounded three ways:**

1. `sync()` commits both sides before anything moves, so the window for drift is one pass, not "since
   whenever".
2. **The copy reports the size it wrote, and it is checked against the entry.** A mismatch deletes the
   copy and falls back to pumping — which then hits the existing hash check and fails loudly, exactly
   as today. This is what makes the common case (a file truncated or rewritten underneath us) still
   fail rather than propagate. Free on Drive, where `files.copy` returns the size in the response the
   call already makes; one `stat` locally.
3. **Implementing `copyFrom` is a statement about the backend**, and the doc comment says so: the
   engine will not re-verify the content. A backend that "copies" by proxying bytes through something
   lossy must not implement it.

A full re-hash after the copy is the one thing that would restore both guarantees, and it costs the
entire saving — it reads back every byte. That is not a trade worth taking; it is the fast path with
extra steps.

## 4. Shape

Three small pieces. Two on the adapter interface, one on the handle.

```ts
// types.ts, alongside append?/changes?
backendId?(): Promise<string | null>;
/**
 * Copies within this backend. Returns the size that landed, or `null` when it
 * cannot — the caller then pumps the bytes, which always works.
 */
copyFrom?(source: VFSAdapter, from: string, to: string): Promise<number | null>;
```

```ts
// vfs-node.ts — where the bytes are, for a caller that may not need to read them
export interface ContentHandle {
  size: number;
  read(): Promise<Uint8Array>;
  stream(): Promise<ReadableStream<Uint8Array>>;
  /** The backend and path the bytes are at, when the holder is willing to say. */
  origin?: { adapter: VFSAdapter; path: string };
}
```

`holds()` fills `origin` — it already has the node and the path it settled on. The in-memory overlay
handle in `sync.ts` does not, which is right: a merged text version exists nowhere but in this
process, and there is nothing to copy from.

`fetchContent()` then branches before it reads anything, and `copy()` gains the same branch against
its own adapter. Both fall through to what they do today, so every path this touches keeps its current
behaviour when any piece is missing.

## 5. What it does not do

- **No delta transfer.** Still out of scope by §6 of the plan: a native copy is whole-object.
- **No deduplication.** Two entries with one hash still cost two copies; §9 decided that and this does
  not reopen it.
- **Nothing for `.vfs/` itself.** The log and the header are small and already written directly.

## 6. Tests

The topology under test is the realistic one: **two `ScopedAdapter`s over one `MemoryAdapter`**, which
is a Drive with two folders in it, without a Drive.

- The bytes never pass through the process: the counting adapter records no `read` of the source path
  and no `write` of the destination path, and the file is there afterwards with the right content.
- Two separate `MemoryAdapter`s do not take the fast path — different `backendId`, ordinary transfer,
  same result.
- An adapter with no `copyFrom` syncs identically. This is the one that pins "every piece is
  optional".
- A size that disagrees after the copy falls back to pumping, and the pump's hash check throws — the
  loud failure of §3.2, driven by an adapter stubbed to copy the wrong thing.
- A conflict copy inside one folder uses the native path (site two of §1).
- `null` from `backendId()` means no fast path, whatever the other side says.

Drive's `files.copy` gets the same treatment as the rest of that adapter: a request-level test against
the fake in `gdrive.test.ts`, asserting one `copy` call and no upload.

## 10. §3.2 does not cover the case it sounds like it covers

The scan reuses a recorded hash whenever `mtime` and `size` both match
([vfs-node.ts:581](../src/vfs-node.ts#L581)). So the drift that matters looks like this:

> `gamelist.xml` is recorded as H1. A backup restore (`cp -p`, `rsync -t`, a tar with timestamps)
> puts different content there — H2, **same size**, mtime restored. `commit()` does not read the file.
> The tree still says H1.

The size check of §3.2 sees nothing wrong, because nothing about the size is wrong. It catches a
truncated copy and that is all. §3 should not have been written as if it closed this.

## 11. What is actually lost, which is less than §3 claimed

Tree fidelity was never an engine guarantee: it rests on mtime+size at scan time, everywhere. The
re-hash inside `fetchContent` is a **second look that happens by accident** — only over files that
happen to be transferred, only on the pass that transfers them.

| | Today | With the fast path |
| --- | --- | --- |
| The drift above, file never transferred | nobody notices | nobody notices |
| The drift above, file transferred | `arrived as H2` throws, **the pass aborts**, nothing repaired | B stores H2 recorded as H1; B's next scan matches mtime+size and keeps H1. Silent, and consistent across the mesh |

So the fast path does not break an invariant; it stops producing a diagnostic. That the diagnostic is
a hard error which aborts a sync without fixing anything is worth weighing on its own.

**Decision needed** — one of:

- **(a)** Accept and document: the fast path trusts the recorded hash exactly as the scan does.
- **(b)** (a) plus a `stat` of the source immediately before copying, compared against the entry's
  mtime+size. Closes only the in-pass race (something writes between `commit()` and the transfer),
  not the case above — where the commit was fooled too. Free locally, one request on Drive.
- **(c)** Re-hash after copying, which costs the entire saving.

## 12. The portability rule, stated because it was asked

Nothing in this phase is written to `.vfs`. `backendId()` is a question asked of the live adapter
object during a pass; it is not persisted, does not travel, and takes no part in the digest — the same
contract as `materialize` and the `text` policy of phase 4.

This is load-bearing, not incidental: **a `.vfs` folder copied to another filesystem must keep
working**, and it does. The precedent is `entry.native`, the one backend-specific field that *is*
persisted: outside the digest ([vfs-file.ts:31](../src/vfs-file.ts#L31)), deleted on every adopt
([vfs-node.ts:1041](../src/vfs-node.ts#L1041)), re-stamped by the scan. Move the folder to another
backend and the native ids resolve to nothing, the scan falls back to path continuity, and `changed`
is decided by hash ([vfs-node.ts:658](../src/vfs-node.ts#L658)) — so the content matches, no log row
is written and no version is minted. It costs one full re-hash and heals itself.

The fast path inherits the rule it implies: it is an optimisation that must be invisible in the
outcome. Same tree, same hashes, same digest, whether it fired or not.

## 13. §11 is decided: (b)

**The fast path stats the source immediately before copying and compares against what the tree
recorded. A disagreement means no fast path — the bytes get pumped, and the pump's hash check then
fails as loudly as it does today.**

What it buys and what it does not is already tabulated in §11 and does not change: it closes the
in-pass race, and it does not close the case where `commit()` was fooled by matching mtime+size. That
case is the scan's standing trade everywhere in the engine, not something this phase introduces.

The cost argument that decided it, checked against the code rather than assumed:

- **Locally** a `stat` is free, as §11 said.
- **On Drive** it is free *too*, which §11 did not claim. `stat()` serves from the metadata the path
  resolve already fetched ([gdrive.ts:403-419](../src/adapters/gdrive.ts#L403-L419) — `locate()`
  returns `file` whenever the lookup had to query), and `files.copy` needs that same resolve. So the
  guard rides on a request the fast path was making anyway.

Being free on both backends is what makes (b) beat (a). It is not a trade; it is a check nobody pays
for.

## 14. The guard belongs in `holds()`, not in `fetchContent()`

The obvious placement is wrong, and the reason is worth writing down because it is a real trap.

`fetchContent()` holds the **target** entry — the merged one, destined for *this* node. Its `mtime` is
node-local by construction ([types.ts:183-192](../src/types.ts#L183-L192), dropped on every adopt at
[vfs-node.ts:1042](../src/vfs-node.ts#L1042)): it describes this node's disk, not the source's.
Comparing a stat of the *source* against it would be comparing two unrelated clocks.

The recorded mtime that means something about the source lives in the source node's entry, and there
is exactly one place holding both that entry and a fresh stat of the file — `holds()`, which already
stats ([vfs-node.ts:132](../src/vfs-node.ts#L132)) to build the handle.

So the guard is a condition on **publishing `origin` at all**:

```ts
// origin is a claim, not a coordinate: "these bytes are where the tree says
// they are, and nothing has touched them since the scan recorded them."
if (stat.size === entry.size && entry.mtime !== undefined && stat.mtime === entry.mtime) {
  handle.origin = { adapter: node.adapter, path };
}
```

This turns out to be the better contract anyway. `origin` stops meaning "here is a path you could
copy from" and starts meaning "the holder vouches for these bytes" — which is exactly the promise a
caller that skips the hash check needs. A holder that cannot vouch omits `origin` and the caller pumps,
which always works. No `entry.mtime` (never scanned, never materialised) is the same free false
negative.

## 15. Unwrapping the scope, which the plan's table understates

The plan's adapter table says `scoped` "delegates to the base, re-rooted". That is right for the
**destination** and silent about the **source** — and the topology this whole phase exists for has a
`ScopedAdapter` on *both* sides.

A concrete adapter's `copyFrom` needs a concrete source: `NodeFsAdapter` needs the source's `root` to
resolve a path, `GDriveAdapter` needs to resolve a fileId. Handed a `ScopedAdapter`, it can do neither
and must answer `null`. Destination-side delegation alone therefore leaves the *main* case pumping.

**One exported helper in `scoped.ts`, used by every concrete `copyFrom`:**

```ts
/** Follows a chain of views down to the adapter that really holds the bytes. */
export function unscope(adapter: VFSAdapter, path: string): { adapter: VFSAdapter; path: string };
```

`ScopedAdapter.copyFrom` re-roots `to` and delegates to its base with the source untouched; the base
calls `unscope` on the source. Nested scopes fall out by recursion. The interface stays at the three
pieces of §4 — no fourth optional method — and each concrete `copyFrom` opens with a two-line guard.

The cost is an `adapters/*.ts → adapters/scoped.ts` import in node-fs, memory and gdrive. `scoped.ts`
imports only `path.js` and `types.js`, so there is no cycle, and the class is ~100 lines.

## 16. Site two gives up nothing, so it takes no guard

§1 calls the conflict-copy `copy()` the cheap half. It is cheaper than that: **it loses no
verification, because it performs none today** — it pumps or reads-and-writes
([vfs-node.ts:1023-1029](../src/vfs-node.ts#L1023-L1029)) with no hash anywhere.

So site two needs no `backendId` question (same adapter object by construction), no stat guard, and
nothing from §13. It keeps only the written-size check, which is strictly more checking than it does
now. A pure win, and the reason it lands in the same session.

## 17. Revised shape

Unchanged from §4 except as noted:

```ts
// types.ts
backendId?(): Promise<string | null>;
copyFrom?(source: VFSAdapter, from: string, to: string): Promise<number | null>;

// vfs-node.ts
export interface ContentHandle {
  size: number;
  read(): Promise<Uint8Array>;
  stream(): Promise<ReadableStream<Uint8Array>>;
  /** Set only when the holder vouches for the bytes — see §14. */
  origin?: { adapter: VFSAdapter; path: string };
}

// adapters/scoped.ts
export function unscope(adapter: VFSAdapter, path: string): { adapter: VFSAdapter; path: string };
```

`fetchContent()` branches on `handle.origin`, both `backendId()`s being equal and non-null, and the
returned size matching `entry.size`; a mismatch deletes the copy and falls through to the pump, which
re-hashes and throws. `copy()` branches on `copyFrom` alone. Every branch falls through to today's
behaviour when any piece is missing.

The overlay handle in [sync.ts:1672-1680](../src/sync.ts#L1672-L1680) sets no `origin` and needs no
change: a merged text version exists nowhere but in this process, exactly as §4 said.

- A source entry with no `mtime` gets no `origin`. Pins "cannot vouch means pump".

## 20. What landed

**Interface** — three pieces, as §17 said, plus the helper of §15:

- [`types.ts`](../src/types.ts): `backendId?()` and `copyFrom?()` on `VFSAdapter`, under a
  `native transfers` heading, with the asymmetry-of-errors table in the doc comment.
- [`vfs-node.ts`](../src/vfs-node.ts): `ContentHandle.origin`, published by `holds()` only when a

**Adapters** — `memory` (per-instance id, a map write), `node-fs` (a constant, `fs.copyFile`),

## 21. The plan was wrong about two costs, both in its own favour

**§11 said the stat guard costs "one request on Drive". It costs none.** `stat()` serves from the
metadata the path resolve already fetched, and `files.copy` needs that same resolve. Free on both
backends is what turned (b) from a trade into a check nobody pays for.

**§4's "three small pieces" understated the scoping problem**, which §15 corrects: destination-side
delegation alone leaves the *main* topology pumping, because a concrete adapter cannot resolve a path
handed to it through a wrapper. One exported helper fixed it without a fourth optional method.

## 22. What the tests caught, which is the point of writing them

Four failures on the first run, and **three were the fixture lying rather than the code being
wrong** — the same lesson as §6 of the backlog, arriving by the same route:

1. **The spy caught the scan, not the transfer.** `sync()` commits first, and the scan reads the file
   to hash it. Every "the bytes never moved" assertion was measuring that read. Fixed by committing
   before the tallies start; without it the whole file was theatre.
2. **`ScopedAdapter` binds its base's optional methods in its constructor**, so a spy installed after
   the view is built is bound around and never fires. This reported the fast path as never firing
   when it was firing every time. The fixture now installs spies first, and says why.
3. **The end-to-end drift test could not reach the guard at all.** Tampering with a file before
   `sync()` is seen by the commit and adopted as an ordinary edit. The drift the guard exists for
   only opens *after* the commit, inside one pass — so those tests now drive `holds()` directly,
   which is where the decision is made and the only place it can be observed honestly.
4. The Drive assertion failed on a real upload that was not the transfer: a text file also has its
   base kept in `.vfs` for a future three-way merge. The payload is binary now, so the assertion
   means what it says.

**Then the tests were mutation-checked**, because a passing test proves nothing about what it would
catch:

| Mutation | Result |
| --- | --- |
| `copyNative` returns false; `copy()`'s native branch disabled | exactly 4 fail — one per site per backend — and **567 pass** |
| the `written !== size` check removed | exactly the 2 fallback tests fail |

The second column of the first row is the more interesting number: with the fast path fully disabled
every other test still passes, which is §12's portability rule demonstrated rather than asserted —
same tree, same hashes, same digest, whether it fired or not.

## 23. What is deliberately still open

The gap of §11 — a file rewritten to the same size with its mtime restored — is **tested and pinned**
(`is fooled by exactly what the scan is fooled by`), not left implicit. It is the scan's standing
trade reaching one place further, and closing it costs the entire saving.

`opfs`, `fsa` and `handle` implement neither method: those APIs have no copy. They pump, which is
covered by the contract suite.
