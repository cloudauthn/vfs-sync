## 0. What this session is for, in one sentence

`syncAll` is covered and everything beside it is not: the footer's single-edge sync, the confirm
preview, the retry loop that re-asks, the auto-sync timer, and the button that settles a parked
conflict. **Those are the paths a person actually presses**, and they are the last place in this repo
where a wrong answer can reach `sync()` with nobody watching.

Not a coverage exercise. The number moves as a side effect; what is being bought is the same thing
the last three sessions bought — defects found by writing the thing that uses the feature.

## 1. What is uncovered, and which of it this session takes

`model.ts` runs 67 of its 104 functions today. This session takes four clusters:

## 2. The fixture

One new module, `test/explorer-model.ts`, holding what `explorer.test.ts` already invented and this
file needs verbatim:

```ts
twoRoots(options?)   // two vFS roots on MemFS, agreeing on one file, synced once
disagree(model)      // both roots edit the same file, so the next pass must stop
answering(model, pick) // subscribe, answer every `decide` row with `pick`, return what was asked
```

`explorer.test.ts` moves to importing the first two. It is the only edit to an existing test file,
and it is a move, not a rewrite — **if it needs any change beyond the import, the extraction was
wrong and I will keep the local copy instead**.

`answering()` is new and is the piece this session leans on: the re-entrancy guard in the existing
test (answer inside the emit, set a flag) is boilerplate that every new test would otherwise copy,
and copying it four times is how one of them ends up subtly different and green for the wrong reason.

The model needs no DOM, `sources` is plain data, and `autoSyncMs` is a constructor option — so the
timer tests set it to 5ms and `vi.waitFor`, rather than faking timers around async work.

## 3. The tests, and what each one is for

### 3.1 The footer's single edge (`syncTarget`)

1. **Routes by target.** `setSyncTarget(other.key)` syncs exactly that pair; `ALL_ROOTS` and "the
   target is the open root" both fall through to `syncAll`. Asserted on the log line, which names
   both labels, and on a third root that must *not* move in the single-edge case.
2. **The three outcomes each say the right thing**: `already in sync`, `merged, N blob(s) moved` with
   N matching `transferred.toA + toB`, and `nothing written` when every row is answered *Leave it for
   now*. That last one is not the existing "Not now" test — cancelling the dialog and choosing
   `abort` are different paths through the engine (`declined` vs no answer at all) and only the first
   is covered today.
3. **A stopped single edge asks, and the answer lands on both roots** — the `syncAll` guarantee, on
   the path the footer actually uses.

### 3.2 The confirm preview (`syncTargetWithConfirm` → `confirmPreview`)

4. **The preview is a `dryRun` and writes nothing.** Cancel at the confirm dialog and both folders
   are byte-for-byte what they were, including `vfs.json`'s `state`.
5. **The sections say what will happen.** A pair contrived to produce one create, one overwrite, one
   text merge and one delete, asserted against the five `sections` — this is the one place the
   explorer restates the engine's plan in its own words, so it is the one place that restatement can
   drift.
6. **Confirm, then the edge stops anyway.** Approving the preview on a disputed pair must still reach
   the decide dialog. Two modals in a row is the intended flow; what is being pinned is that the
   second one appears at all.

### 3.3 The retry loop (`syncAnswering`) — and the one hypothesis worth writing

7. **An answer that surfaces a new conflict is asked in a second round**, and the pass settles.
8. **`decisions = answers` looks wrong and this test says so.** Both `syncAnswering` (`model.ts:1887`)
   and `syncAll` (`model.ts:2021`) *replace* the accumulated decisions with the latest dialog's
   answers. Nothing was written when the pass threw, so round 3 carries round 2's answers and has
   **dropped round 1's** — the conflicts a person already settled become pending again and are
   re-asked, and a case that should settle in two rounds can walk to the 8-round cap and give up with
   `still unsettled after 8 rounds`.

   **This is a hypothesis, not a finding.** It is written as a test that answers each conflict exactly
   once and asserts no `id` is asked twice. If it passes, the loop is fine and the test is worth
   keeping anyway. If it fails, the fix is accumulation with later-answer-wins by `id`, which is
   three lines in each of the two loops.
9. **The cap is a stated behaviour, not a hang.** A `decide` subscriber that always answers *Leave it
   for now*'s neighbour — i.e. an answer that keeps re-raising — logs `still unsettled after 8
   rounds` and writes nothing, in bounded time.

### 3.4 The timer (`setAutoSync`, `syncTargetQuietly`, `destroy`)

10. **The tick syncs and never opens a dialog** — the existing test drives `syncAll(false)` by hand;
    this drives the actual timer, which is what ships.
11. **`reportStopped` says it once per distinct set, per edge**, across several ticks — and says it
    *again* when the set changes. The keying differs between the two callers (`a.key:b.key` in
    `syncAnswering`, `all:${index}` in `syncAll`), and an index-keyed signature is only stable while
    the edge list is; a test that settles one edge and leaves another stopped will show whether that
    matters. Same footing as §3.3's hypothesis: pin the behaviour, then decide.
12. **`destroy()` stops the clock.** Count passes after `destroy()`, wait past two intervals, and the
    count must not move — a timer surviving teardown writes to folders after the page thinks it is
    gone.

### 3.5 Settling a parked conflict (`resolveConflict`)

13. **`mine` and `theirs`** each leave the right bytes and remove the parked copy, and the answer
    travels on the next sync like any edit.
14. **The `held` guard.** A copy whose content stayed on another peer cannot be resolved as `theirs`
    from here: it logs `sync with it first` and **changes nothing**. This is the one uncovered branch
    that stands between a click and a resolve that cannot fetch its own bytes.

### 3.6 The dialogs, reached through the above

15. **`newFile`**: `askPrompt` → `setDialogValue` → `acceptDialog` creates it; `cancelDialog` creates
    nothing; a name under `.vfs` is refused with the read-only warning.

## 4. What this does not claim

- **No coverage threshold is added.** `vitest.config.ts` gates `src/**` at 95/90/95/95 and the
  explorer is not in it. The browser-API cluster of §1 cannot be exercised without fakes that do not
  exist yet, so a threshold now would either be set below what the file deserves or would block on
  work this session is explicitly not doing. The number goes in the walkthrough instead — expected
  around 75–80% of functions, from 64%.
- **No production code changes**, unless §3.3 or §3.11 turns up a real defect. If either does, the
  fix lands in the same session with the test that found it, and is called out in the walkthrough.

## 5. Risks

- **Contriving one create + one overwrite + one merge + one delete in a single preview** is the
  fiddliest fixture here. If it costs more than the test is worth, it splits into two smaller
  previews rather than growing a mesh of setup nobody can read.
- **The 5ms timer tests are the only wall-clock-dependent thing in the suite.** They use `vi.waitFor`
  with an explicit timeout, and if they flake under load they become fake-timer tests instead.

## 8. The defect §3.3 predicted, confirmed and fixed

`decisions = answers` **was** wrong, in both loops, and the failure is worse than re-asking:

> Two conflicts and a slow hand. Round 1 asks about `notes.txt`; while the dialog is open, a second
> file falls out of step. Round 2 carries the answer to `notes.txt`, settles it, and stops on
> `second.txt`. Round 3 carries the answer to `second.txt` **and nothing else** — and because the
> pass that asked wrote nothing, `notes.txt` is outstanding again. It is asked a second time, its
> answer displaces the other, and the two trade places until the cap gives up: **eight dialogs, and
> not one byte written.**

The test that found it answers each conflict exactly once and asserts no id is asked twice. Before
the fix: 8 rows shown, 2 distinct. After: 2 and 2, and the pass settles.

The fix is `withAnswers(previous, answers)` — accumulate, later answer wins per id — and it is safe
by the engine's own rule, which the model already relied on elsewhere: *a decision naming no live
conflict is ignored*.

## 9. The defect this session did not go looking for

**Three peers that each create the same path independently can end up asking a person which of two
identical files keeps the name — and whether they do depends on the random order of their uuids.**

It surfaced as a fixture that hung roughly half the time. `roots(['left','middle','right'])` wrote
`notes.txt` into each folder before syncing, and `pairEntries` unified them pairwise; the mechanism
is deterministic once the uuids are fixed, and reproduces in three calls:

```
left ⇄ middle       → adopt min(b-left, c-middle) = b-left; middle now knows c-middle
middle ⇄ right      → adopt min(b-left, a-right)  = a-right; middle now knows b-left too
left ⇄ middle again → left is on b-left, which middle *knows*, so it is not a stranger:
                      no pairing, two uuids on one path, path-collision
```

The guard doing this is deliberate and correct in general — a uuid the other side has heard of before
must not be re-paired, or a delete-and-recreate at one path would merge with its own ghost. What is
missing is that **adoption is not a delete**: when a peer gives up its uuid for a smaller one, the
peers still holding the old one have no way to learn that it became the new one.

**Why the suite never noticed**: `convergence.test.ts` does create the same path on different peers,
but `stabilise()` answers every conflict with `keep-both` automatically, so a mesh that had to ask a
person converges exactly like one that did not.

**Left for a decision, not fixed here.** The remedy is an alias — the adopted uuid recorded against
the one it replaced, so a late peer re-pairs instead of colliding — which touches identity, the log
and the convergence property, and is a session of its own. Nothing is pinned in the suite either way:
a passing test asserting today's behaviour would be the "test that holds a bug in place" this repo
already paid to learn about. The fixture now seeds the first root and lets the file propagate, which
is both how a person gets a second device in step and a starting state with one identity in it.

## 10. Four fixtures that lied, and one assertion that was simply wrong

Same score as the last two sessions, and the same lesson from the other side:

1. **My own `prompting` helper released its re-entrancy guard too early**, so `setDialogValue` emitted
   and re-entered it — stack overflow, in the helper, before any test could be trusted.
2. **The hang looked like slowness.** A pass that opens a dialog with nobody subscribed waits
   forever, and vitest reports the 5-second timeout against whichever test was unlucky. That is now
   `refusingToAnswer(model, what)`, used by the fixture itself: a question nobody expected fails
   loudly and names what was asked. It is what turned §9 from a flake into a mechanism.
3. **`live()` is the store's record, not the folder.** `newFile` writes through the adapter and the
   entry only lands at the next commit, so the first version of that test asserted a file was missing
   when it was on disk. The assertion is now the model's own rendered snapshot — what the person is
   looking at — plus a `stat`.
4. **The cap test could not reach the cap.** Answering settles what was asked, so a world that stops
   manufacturing new disputes settles in two rounds; it needed a fresh conflict per dialog to get
   there. Written the first way it would have passed for the wrong reason once §8 was fixed.
5. **A settled text merge is still reported as a conflict** — the preview lists `shared.md` under both
   *Files updated via text merge* and *Conflicts*. That is the engine keeping the report so a caller
   can see what happened, and the test says so rather than asserting the empty list I expected.

## 11. Two behaviours pinned on the way past, neither a defect

- **`destroy()` does not abandon a pass in flight.** The interval is cleared, but a `syncAll` already
  running finishes and logs — and finishing is right, because a plan abandoned half-applied is worse
  than one that completes. The test asserts the real property: no *new* pass starts, measured once
  the last one has landed.
- **Teardown notifies once on its way out**, turning the auto-sync box off like any other change,
  before dropping every listener.
