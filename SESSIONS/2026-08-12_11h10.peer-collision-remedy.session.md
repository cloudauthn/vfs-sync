## 0. Why this is small and still worth doing now

Phase 6 shipped `peer-collision` as **deliberately not authorisable**: merging two nodes with one
identity is not a decision anyone can make well, so `{ adopt }` does not cover it. That was right,
and it left the caller with an error and no exit the library supports. **We shipped the diagnosis
without the remedy**, and it is published — the one part of phase 6 a consumer can actually hit and
then be stuck on.

The plan's §7.5 already settled the shape: the library exposes the operation and lets the caller
decide, because it cannot tell the two causes apart.

## 1. What a collision actually is, and why one fix covers only half

| Cause | Probability | Does regenerating the `peerId` fix it? |
| --- | --- | --- |
| random collision | ~0 (`crypto.randomUUID()`) | n/a — it does not happen |
| the `.vfs` folder was copied | **100%** between the copies | **yes** |
| the caller passes a non-unique `options.id` | **100%** between installations | **no** — the next `open()` imposes it again |

The library cannot distinguish these: a clone predating the first sync and an imposed id present
identically. So `reidentify()` fixes one of them and is inert against the other, and **saying so is
part of the API**, not a caveat to bury. A caller who hits `peer-collision`, calls `reidentify()`,
and hits it again has learned exactly which case they are in — which is more than the library can
tell them on its own.

## 2. What it changes, and what it must not

```ts
/** Mints a fresh identity for this node. Returns the new `peerId`. */
async reidentify(): Promise<string>
```

**Changes**: the `peerId` in the header, and the node's own view of it.

**Does not change** — and each of these is load-bearing:

- **`syncId` stays.** Reidentifying is not leaving the group. For the case it actually fixes — a
  copied `.vfs` — both copies are replicas of one mesh, and the wanted outcome is two peers with
  distinct identities inside the same group. Clearing it would turn a fixable collision into a
  `foreign-mesh`.
- **Entries and log rows keep their old `peerId`.** Those are attributions of who changed what, and
  they are history. The log is immutable anyway; rewriting the entries would rewrite the past to say
  a node that did not exist made those edits.
- **`peers` marks stay.** They are keyed by the *other* side's id and remain valid.

## 3. The one consequence worth stating

Every peer that has synced with this node holds a mark keyed by the **old** id. After reidentifying,
that mark is orphaned: the next sync finds no mark for the new id and falls back to reading the
whole log ([sync.ts:696-701](../src/sync.ts#L696-L701)) instead of the tail since an offset.

That is correct, not a bug — one full log read, once, and then the new mark takes over. It is worth
documenting because on a large log it is a visible cost exactly once, and someone will notice.

The stale slot itself is inert: a `peers` entry nobody looks up again.

## 4. Shape

`peerId` is `readonly` today. It becomes a getter over a private field, so the public surface stays
read-only and the node stops being stale after the call — the alternative, returning a new node,
would leave the old one in the caller's hands still claiming an identity it no longer has.

## 5. Tests

- The header carries the new id, and it is not the old one.
- `syncId` survives, and two folders that collided sync normally once one has reidentified.
- Entries written before the call keep the old `peerId` — history is not rewritten.
- `node.peerId` reflects the change without reopening.
- Reopening with `options.id` set puts the imposed id back, which is the case this does not fix,
  pinned so the limit is a decision rather than a surprise.

## 6. Documentation

`docs/api.md` under Pairing: `peer-collision` gains its remedy, with the table from §1 — including
that it is inert against an imposed id.

## 7. What landed

public surface stays read-only while the node stops being stale after the call. Returning a new node
was the alternative and it is worse: it leaves the old one in the caller's hands still claiming an

Everything in §2 held. `syncId` survives, entries and log rows keep their old attribution, `peers`
marks are untouched.

## 8. The test that is really documentation

*"is undone by an imposed id, which is the case it cannot fix"* asserts that the remedy **does not
work**, and it is the most useful of the four. Without it, the limit lives only in a doc comment, and
the first person to hit it reads the comment as a caveat rather than as the designed behaviour.

It also pins something the library genuinely cannot do: `options.id` overwrites the stored id on
every `open()`, so a caller deriving it from a hostname gets the collision straight back. The failure
is in the caller's code and no library operation reaches it — which is exactly why phase 6 refused to
authorise the merge instead of guessing.
