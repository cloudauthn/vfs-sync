## 0. The defect, in three lines

Three peers each create `notes.txt` on their own. `pairEntries` unifies two independently-created
entries by `kind:path` and keeps the **smaller** uuid, so a chain adopts twice:

```
left ⇄ middle        adopt min(b-left, c-middle) = b-left    middle now knows c-middle
middle ⇄ right       adopt min(b-left, a-right)  = a-right   middle now knows b-left too
left ⇄ middle again  left is on b-left, which middle *knows* — not a stranger, so no pairing:
                     two uuids on one path → path-collision, which stops the pass and asks
```

The person is asked which of two **byte-identical** files keeps the name. There is no right answer
and no wrong one, and whether it happens at all depends on the order the uuids sorted in.

## 1. The detector comes first, and it is expected to go red

`settle()` in [`test/helpers.ts`](../test/helpers.ts) answers every conflict with `keep-both`, so a
mesh that stopped to ask a person converges exactly like one that never did — which is why
`convergence.test.ts` has been driving this defect over a hundred random histories without noticing.

The check is two lines in that helper, and it is the invariant this session is really about:

> **A conflict whose two sides carry the same hash is one the engine should have settled itself.**
> Nobody can answer it: both answers produce the same bytes.

`ConflictPayload.ctxA/ctxB` are `VersionContext`s and carry `hash` ([sync.ts:78](../src/sync.ts#L78)),
so this needs no new plumbing. Every suite that uses `settle()`/`stabilise()` inherits it.

**It will fail on some seeds and pass on others until §3 lands**, because the uuid order is random per
run. That is the point of writing it first: the red is the defect becoming visible for the first time.
If it turns out to be red for a *second* reason, that is a finding and it goes in the walkthrough
before anything is fixed.

## 2. What must not break

The guard causing this is deliberate and right: pairing by path is only allowed between entries whose
uuid the other side has **never heard of**, by entry or by log ([merge.ts:164](../src/merge.ts#L164)).
Without it, a file deleted on one peer and recreated at the same path on another would merge with its
own ghost, and v1's base tree is gone, so `knows()` is the only thing standing there.

So this is not "relax the stranger test". It is: **a uuid that was adopted away is not a uuid that was
deleted**, and nothing in the format currently tells them apart. Two files that genuinely are two
files must still raise `path-collision` — that entry stays in the catalogue and its tests stay green.

## 3. Where the alias lives — the one decision to take before writing

| | Travels | Survives log pruning | Cost |
| --- | --- | --- | --- |
| **(a) a log row** `type: 'adopt'` | with the log, on the next exchange | **no** — segments rotate and prune, and an alias must outlive every peer still holding the old uuid | one row per adoption |
| **(b) on the entry**, `was?: string[]` | with `vfs.json`, which both sides exchange anyway | yes — it rides the live entry | a few bytes per absorbed identity |
| (c) derived from history | — | — | nothing records the adoption today, so there is nothing to derive from |

**Recommendation: (b).** The surviving entry lists the uuids it absorbed; `pairEntries` canonicalises
both sides' uuids through the union of those lists before it pairs anything, which also handles the
chain in §0 (`c-middle → b-left → a-right`). It converges by construction — the merged entry's `was`
is the **union** of both sides', which is order-independent — and `was` is not in `DIGEST_FIELDS`
([vfs-file.ts:31](../src/vfs-file.ts#L31)), so a peer that has never heard of the field still agrees
on `state`.

The one thing (b) buys that (a) cannot: a peer that has been offline for months, holding the old
uuid, still re-pairs when it comes back — long after the log segment naming the adoption was pruned.

## 4. The changes

- [`types.ts`](../src/types.ts): `VFSEntry.was?: string[]` — "identities this entry absorbed", with
  the reason it is not a log row in the doc comment.
- [`merge.ts`](../src/merge.ts): `pairEntries` builds the alias map from both sides' entries and
  canonicalises before matching; the adopted-away uuid is added to the survivor's `was`;
  `mergeEntries` unions `was` on every merged entry.
- [`vfs-file.ts`](../src/vfs-file.ts): carry the field through read/write, out of the digest.
- Nothing in `sync.ts`: the pairing is where identity is decided, and it stays that way.

## 5. What has to hold afterwards

1. Three peers, one path, any uuid order, any edge order: **no question**, one entry, one uuid.
2. Delete-then-recreate at the same path still does **not** pair (§2), and its tests stay green.
3. Two genuinely different files on one path still raise `path-collision`.
4. Two peers that disagree about `was` still agree on `state` — the field is outside the digest, and
   the union makes them agree on the field too by the next pass.
5. The detector of §1 is green across every seed, run repeatedly.

## 6. Risks

- **`was` grows.** Bounded by how many peers created the same path independently — small in practice,
  and never pruned, because "every peer has adopted" is not knowable in a mesh. If it ever matters,
  that is a separate decision with a real number attached.
- **Tombstones carry aliases too.** A deleted entry's `was` must survive, or a peer holding the old
  uuid re-pairs with a ghost — the exact case §2 protects. This needs a test of its own.
- **Chains longer than two.** Canonicalising through a map that itself contains chains needs to
  resolve to a fixed point, not one hop.

## 7. Tests

- The §0 reproduction, deterministic, at the `pairEntries` level with fixed uuids — three calls, no
  clocks, no adapters. It is the fastest possible statement of the bug and it goes in first, red.
- End to end: three `VFSNode`s in a ring, each creating the same path, synced to a standstill with a
  `settle()` that now refuses to answer an unanswerable question.
- The §5 list, one test each, in `merge.test.ts` beside the pairing tests that already exist.
- A convergence run with more seeds than usual, once, to see whether anything else the detector finds
  has been hiding behind `keep-both`.

## 8. Order of work

1. The detector in `settle()`, and a full-suite run to see exactly what it lights up.
2. The deterministic `pairEntries` reproduction, red.
3. `was` end to end, until 2 and 1 are green.
4. §5's four other properties, then the repeat runs.

## 9. For review before I start

  living as one assertion inside `convergence.test.ts`. It makes the shared helper opinionated: a
  test that *wants* to answer an unanswerable question would have to say so explicitly.

# Revision — 2026-08-14 20h08

**Summary**: the review replaced the mechanism. `was` is dropped. Identity is settled by **who has
something to lose**, at both levels, and the answer to a `foreign-mesh` starts choosing the outcome.
§1 (the detector) and §2 (what must not break) stand; §3–§8 are superseded by what follows.

## 10. The rule, in one sentence

**A folder that has never synced has no identity to lose, so it takes the other's — and a folder that
loses a mesh vote stops being one that has synced.**

Two levels, one principle:

| Level | Today | After |
| --- | --- | --- |
| **mesh** (`syncId`) | the answer *authorises* the merge; `min(syncId)` survives either way and both trees merge normally ([sync.ts:978](../src/sync.ts#L978)) | the answer **names the winner**; the loser discards `.vfs` outright and rejoins as a folder that has never synced |
| **entries** (`uuid`) | `min(uuid)` between two strangers on one path, whoever they are ([merge.ts:181](../src/merge.ts#L181)) | the side with `syncId === null` adopts the established side's uuids by path; **an established identity never changes** |

That closes §0 without a per-file alias, and the reason is worth stating precisely: after this, *every*
identity rewrite happens on a side whose old uuids nobody else is holding — a virgin folder, or one
that just discarded its store. There is no third party left carrying a stale uuid, which is the whole
of the defect.

The asymmetry is not new. `pair()` already treats it as authority for the mesh id: *"one set against
one `null` — a folder joining a group: it has no affiliation to lose, so no tiebreak is needed"*
([sync.ts:921](../src/sync.ts#L921)). The entries below simply never got the memo.

## 11. What "loses" means — decided in review

**A clean wipe of `.vfs`.** Not a re-keying: the losing folder discards its store, its log and
segments, its snapshots, its text-merge bases and its peer marks, then rejoins with `syncId: null`
and a freshly minted `peerId`. The files themselves are never touched.

Accepted consequences, written down so nobody rediscovers them as bugs:

- **Deletions the loser made come back** if the winning mesh still has the file. A tombstone is the
  only record that a deletion was deliberate, and the wipe takes it.
- **Text-merge bases go**, so the next conflict on those files refuses with `no-base` and parks a copy
  instead of merging. It recovers on its own once both sides have written once.
- **Conflict copies parked on the loser stop being pending.** The bytes stay as ordinary files with
  the conflict name; `node.conflicts()` will not list them. Worth a line in the release notes.
- **The loser's local edits are not lost**: they are files, and they enter the winning mesh as
  ordinary creates and updates on the next pass.

## 12. The choice has to travel — `absorbed`

The moment the answer chooses a winner instead of authorising a deterministic rule, two people
answering on two different edges can choose opposite winners, and the mesh identity oscillates. That
is the same defect as §0 one floor up, so the decision is recorded where the next peer will read it:

```
"absorbed": ["<syncId of every mesh this one has taken in>"]
```

One header field, not one per file. A straggler of the losing mesh — offline for months, still
carrying the old `syncId` — meets any peer of the winner, finds its own id in `absorbed`, and joins
**without asking again**.

**This is the sharp edge of the design and it is deliberate: one person's answer wipes the `.vfs` of
every straggler of that mesh, whenever they turn up, with nobody present.** The alternative is to ask
each of them, which is theatre — the answer is already forced, since adopting the other direction
would undo a decision the mesh has recorded. Veto this line if you disagree; everything else stands
without it.

## 13. The changes

- [`types.ts`](../src/types.ts) / [`vfs-file.ts`](../src/vfs-file.ts): `absorbed?: string[]` on the
  header, carried through encode/decode, out of the digest.
- [`store.ts`](../src/store.ts): `discard()` — delete `vfs.json`, `commits`, every `commits-*`,
  every `vfs-*.json` snapshot and the base copies, in that order, so a crash halfway leaves a folder
  that reads as virgin rather than as a mesh member with no log.
- [`sync.ts`](../src/sync.ts): `pair()` returns the winner rather than `min` when a decision names a
  side; the loser is discarded and reopened before the merge is computed; `absorbed` gains the loser's
  id on the winner; a `syncId` found in the other side's `absorbed` is benign and triggers the same
  discard without a question. **`dryRun` discards nothing** and reports it as part of the plan.
- [`merge.ts`](../src/merge.ts): `pairEntries` takes "which side is virgin" and, when exactly one is,
  pairs its live entries against the established side's **live** entries by `kind:path`, adopting the
  established uuid. A tombstone on the established side does not pair — a joiner's file at a path the
  mesh deleted is a new file, which is §2's hazard handled by construction.

## 14. What has to hold

1. §5's list, minus the alias: three peers, one path, any order → one uuid, no question.
2. An established peer's uuid for a file **never changes**, in any topology. This is the invariant to
   assert directly, not a consequence to hope for.
3. A folder that discards and rejoins keeps every byte it had; only `.vfs` is gone.
4. Two virgin folders still settle by `min(uuid)` — nothing to adopt from.
5. A straggler whose `syncId` is in `absorbed` joins with no `ConflictError` raised.
6. `dryRun` on a foreign-mesh pair leaves both folders untouched, including `.vfs`.

## 15. Order of work

1. The detector in `settle()` (§1), and a full-suite run to see what it lights up.
2. The deterministic `pairEntries` reproduction of §0, red.
3. The entry-level rule (§13, `merge.ts`) — this alone turns §0 green.
4. The mesh-level wipe, `absorbed`, and the `dryRun` guarantee.
5. §14, one test each, plus repeated convergence runs.

Steps 1–3 are self-contained and could ship on their own; 4 is a format change and a destructive
operation, and wants its own review of the walkthrough before it is called done.

# Walkthrough — 2026-08-15 00h15

**Summary**: steps 1–3 are written, and the rule they landed is simpler than either draft. No format
change, no alias, no wipe. Step 4 (the mesh-level wipe and `absorbed`) is untouched and still open.

**Status: Completed** for steps 1–3.

## 16. The rule that landed

Review replaced the mechanism a second time, and this one is smaller than both drafts:

> **A uuid inside a mesh is minted once and never rewritten.** Matching by path may only make two
> entries one file where the answer cannot be wrong: a folder that has never synced (it has no
> identities to lose), two directories (a directory is nothing but its path), or two files with the
> **same hash** (identical content proves they are one file). Everything else is two files claiming
> one name — a `path-collision`, and a person's to answer.

Twenty-two lines in [`merge.ts`](../src/merge.ts) (`samePath`, plus the joining side yielding its
uuid) and a `joining: fileX.syncId === null` on each side in [`sync.ts`](../src/sync.ts). That is all.

**`was` is dropped.** Nothing needs to remember an adoption, because no established peer ever adopts:
the only side that changes identity is one with no history for anyone else to be holding.

**The user-visible change**: two peers *already in one mesh* that each create `notes.txt` on their own
now get a `path-collision` — two files, one name, one keeps it — where before they were silently
paired into one file and then, if their contents differed, asked as a `content` conflict. Two folders
that have never synced still pair, which is the case that matters for a person adding a device.

## 17. What the detector caught, which is the whole reason it went first

`settle()` refuses a conflict whose two sides carry the same hash ([helpers.ts](../test/helpers.ts)).
With it in and no fix, **`convergence.test.ts` failed 1–3 of its 16 seeds on every run**, differently
each time — the property test had been driving this defect over a hundred random histories, and
`stabilise()`'s automatic `keep-both` had been converting every one of them into a silent duplicate
file.

The dump that settled the diagnosis, from seed 23:

```
p0:  "b.txt"                        uuid=f9b4668d…  hash=09f1695e
p1:  "b.txt"                        uuid=a69a1216…  hash=0d7022b1
     "b (conflict p0 09f1695e).txt" uuid=conflict:a69a1216:09f1695e   ← p0's version, parked
p2:  same as p1
```

p0 says `b.txt` is `f9b4668d`; p1 and p2 say `a69a1216`. The identity split, reached **between two
established peers** — not by a folder joining, which is what §10's draft covered. That is what forced
the third design and is why the plan's §14.2 invariant became the mechanism rather than a hoped-for
consequence.

After the fix: 8 consecutive full-suite runs green, and 6 more with the builds. 597 tests across 31
files; `lint`, `tsc --noEmit`, library, explorer and demo builds clean.

## 18. The test that looked like proof and was not

An end-to-end test was written first — three peers, one path, each creating it independently, assert
one uuid and no question. It passed. **It also passed with the fix mutated out, twelve times out of
twelve**, and a scratch harness over twenty fresh worlds put the stranding rate of that exact
scenario at 0.

So it was deleted rather than kept. A green test that cannot fail for the reason it claims is the
"test that holds a bug in place" this repo already paid to learn about, and keeping it would have
made every future reader believe the case was covered.

What is kept instead, all three mutation-checked:

| Test | Catches |
| --- | --- |
| `pairEntries > does not pair two files on one path when their content differs` | the rule itself — fails the moment `samePath` returns `true` unconditionally |
| `pairEntries > pairs them when the bytes are identical` / `two directories` / `gives the mesh identity to the side that has never synced` | the three cases where pairing must still happen |
| `the payload carries what the decision needs > treats one name claimed by two established peers as two files` | the same rule at `sync()` level, through the payload a consumer sees |
| `convergence.test.ts` + the detector in `settle()` | the real end-to-end signal, and the only one that ever reproduced this |

## 19. What is still open

- **Step 4 of §15**: the `foreign-mesh` answer choosing the winner, the losing folder discarding
  `.vfs`, and `absorbed` in the header. Untouched. It is worth noting that §16 removes the urgency:
  the identity split it was going to prevent is now prevented at the entry level, for joins *and* for
  concurrent creation.
- **Two established meshes merging** still pairs nothing by path unless the bytes match, so files
  each mesh created independently will collide by name and be asked. Under step 4's semantics the
  loser arrives virgin and the question disappears; without step 4, a person answers once per file.
