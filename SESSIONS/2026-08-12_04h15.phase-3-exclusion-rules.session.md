## 0. What publishing v0.2.0 changed about this

The scoping decision that made v2 → v3 a hard cut is spent. §7.9 of the plan closed `PeerMark.version`
and the two-step release "until the first installation outside your control", and a published package
is that. From here, an incompatible format change cannot ship in one go: on shared storage the old
engine **is** going to read what the new one writes.

This phase is unaffected, and deliberately so. It adds one key to `local` in the header, which is
`additive` in the sense the registry now defines: **an old engine reading a new file simply ignores
the extra key.** No version bump, no migration, no two-step. It is worth noting explicitly because it
is the first change since the cut, and "is this additive?" is now a question every change has to
answer before it is written rather than after.

## 1. Three sources, one union

| Source | Travels? | Set by | Shape |
| --- | --- | --- | --- |
| `.vfsignore` in the working folder | **yes**, it is ordinary content | editing the file | plain text, `#` comments |
| `local.ignore` in the `vfs.json` header | no | `node.setLocalIgnore()` | JSON array |
| `VFSNodeOptions.ignore` | no | the caller | predicate |

Composed by **union**: ignored by any one of them, ignored. No `!pattern` negation, so no tie is
possible and there is no precedence to define — the moment negation exists, order becomes observable
and it has to be declared which source wins.

The existing predicate stays as the escape hatch for logic no pattern language expresses. It is not
deprecated by this phase; the two patterns files handle the cases everyone has, and the predicate
handles the rest.

## 2. Syntax: one rule decides which kind a pattern is

Three forms, all at **any depth**, because OS junk appears in every folder and that is the use case
justifying the feature — `.DS_Store`, `Thumbs.db`, `._*`, `@eaDir`.

| Form | Matches | Example |
| --- | --- | --- |
| exact path | that path, and its subtree if it is a directory | `docs/notes.md` |
| directory prefix | the subtree | `.cache/` |
| `*` over the name | that name in any folder | `*.tmp`, `._*` |

The requirements list the three but do not say how to tell them apart. Proposed rule, which covers
every example without ambiguity:

> **A pattern containing `/` is a path rule, anchored at the root. A pattern without `/` is a name
> rule, matched against the basename at any depth.**

So `docs/notes.md` is that one file, `.cache/` is that subtree, and `*.tmp` is any `.tmp` anywhere.
`*` translates to "any run of characters that is not `/`", so it never crosses a folder boundary.

## 3. The matcher has to mirror the walk, not the pattern

Phase 1's walkthrough §2 established this the hard way, and it applies with more force here because
directory-prefix rules become the common form:

> The walk prunes at the directory and never descends, so a rule naming `.cache` also excludes
> `.cache/deep/blob.bin` — but a predicate asked about that child directly says nothing about it.

`excluded()` ([vfs-node.ts:378](../src/vfs-node.ts#L378)) already walks the ancestors for exactly this,
and the new matcher inherits that for free as long as it is reached through the same method. What the
matcher itself must get right: **`.cache/` matches the directory `.cache`**, not only paths beneath
it. Otherwise the walk never prunes, descends, and the rule silently does nothing.

This is a conformance rule, not an implementation detail — a second implementation could get the leaf
case right and the subtree case wrong, and nothing would report it.

## 4. `.vfsignore` cannot be excluded, and *where* that is enforced matters

The requirement says the engine "must reject any rule that excludes it": `.vfsignore` is synced
content and the mesh needs it to converge, so a peer that drops it from the tree makes the others
read a delete.

**Rejecting by throwing is the wrong shape for a rule that arrives over the wire.** A `.vfsignore`
containing `*.vfsignore` would then break every peer that syncs it — a bad line in a text file
becomes a mesh-wide outage, which is worse than the problem. The split:

| Door | Behaviour |
| --- | --- |
| `node.setLocalIgnore(patterns)` — the caller is present | **throws**. Fix it where it was written |
| `.vfsignore` — arrives from a peer | **structurally exempt**: the path is never excluded, whatever any rule says |

The exemption is the same mechanism `.vfs/` already uses in `walk()`: a path the walk always visits.
One line, and it makes the invariant true by construction rather than by everyone remembering.

## 5. Reading `.vfsignore` without paying for it every scan

It is content in the working folder, so reading it is an adapter call — on Drive, a round trip on the
path that exists to avoid them. It should not be read on every scan.

**The hash is already in the tree.** The entry for `.vfsignore` carries one, so the rules can be
cached against it and re-read only when it changes:

```ts
// at the top of scan(), before the walk
const rule = live.find((entry) => entry.path === VFSIGNORE);
if (rule?.hash !== this.ignoreHash) await this.reloadIgnore(rule);
```

Two consequences worth stating because they are not obvious:

- **A change that arrives by sync applies on the next scan, not one pass later.** `apply()` writes the
  file and `adopt()` records the new hash, so the next `scan()` sees the difference before it walks.
  §B.3's "converges on the second pass" is about the sync that *carries* the rule still running under
  the old one — which stays true, and after phase 1 is no longer dangerous.
- **A hand-edited `.vfsignore` costs one extra pass**, because the hash in the tree only changes once
  a scan has hashed it. Acceptable, and the alternative is stat-ing the file on every scan.

## 6. What gets built

| Piece | Where |
| --- | --- |
| `parseIgnore(text)`, `matchIgnore(patterns, path)` | new `src/ignore.ts` — pure, no I/O |
| Cache keyed on the `.vfsignore` hash | `VFSNode` |
| Union of the three sources | `excluded()`, one place |
| `node.setLocalIgnore(patterns)` / reading `file.local.ignore` | `VFSNode`, `types.ts` |
| `.vfsignore` exempt from exclusion | `walk()` |

`src/ignore.ts` is pure on purpose: it is the part a second implementation has to match exactly, and
a pure function with a table of cases is what a conformance suite can be written against.

## 7. Tests

The pattern language first, as a table — every form against paths at the root and nested:

- `docs/notes.md` matches that path and nothing else; `docs/notes.md.bak` does not match.
- `.cache/` matches `.cache` **and** `.cache/deep/blob.bin`.
- `*.tmp` matches `a.tmp` and `deep/nested/a.tmp`; `*` does not cross `/`.
- `._*` matches `._foo` at any depth. `@eaDir` matches the directory anywhere.
- `#` lines and blank lines are ignored; whitespace is trimmed.

Then the engine:

- Union: a path covered only by `local.ignore` is excluded, and so is one covered only by `.vfsignore`.
- A `.vfsignore` that arrives by sync is in force on the next scan, and the tracked file it covers
  **stays live on both peers** — phase 1's guarantee, now exercised through the real distribution
  mechanism rather than a hand-passed predicate.
- `.vfsignore` is never excluded, even by a rule that names it exactly.
- `setLocalIgnore(['.vfsignore'])` throws.
- The rules are not re-read when the hash has not changed — asserted through a counting adapter, the
  way [`gdrive-traffic.test.ts`](../test/gdrive-traffic.test.ts) counts round trips.

## 9. Decisions this needs

1. **The `/` rule of §2** — presence of a slash decides path rule versus name rule. It is the part
   the requirements leave open.
2. **Structural exemption rather than a throw for a rule that arrives over the wire** (§4), with the
   throw kept for the local API where the caller can act on it.
3. **Caching on the hash** (§5), accepting that a hand edit lands one pass later than a synced change.
4. **`setLocalIgnore` as the name** — `local.ignore` is the field; `ignore` alone would collide with
   the constructor option in the reader's head.

## 12. The syntax, settled

One anchor marker, one subtree marker, and everything else floats:

| Pattern | Anchored | Matches |
| --- | --- | --- |
| `/docs/notes.md` | at the root | that one path, and anything under it |
| `docs/notes.md` | no | that run of segments at **any** depth |
| `.cache/` | no | any `.cache` anywhere, and its subtree |
| `/.cache/` | at the root | only the top-level `.cache` |
| `*.tmp` | no | that basename at any depth |
| `._*`, `@eaDir` | no | same |

`*` expands to "any run of characters that is not `/`", so it never crosses a folder boundary.
Blank lines and `#` comments are dropped; whitespace is trimmed.

### 12.1 Where this differs from gitignore, and why it has to be written down

In real gitignore, **a pattern with an interior slash is anchored implicitly** — `docs/notes.md` in a
root `.gitignore` matches only the top-level one. Here it floats, and only a leading `/` anchors.

That is the price of decision 1's shape: one marker, one rule, no "it depends where the slash is".
It is more expressive than gitignore on this point — you can write a floating multi-segment pattern,
which gitignore cannot express at all — but it is a place where someone's gitignore instinct will be
wrong, and wrong **silently**: they will write `docs/notes.md` meaning one file and get every
`docs/notes.md` in the tree.

It goes in the docs as a callout, not a footnote, and it is a conformance row: two implementations
that disagree about anchoring exclude different files and neither reports anything.

### 12.2 The trailing slash is decorative, and pretending otherwise would be worse

In gitignore, trailing `/` means "match directories only". **This engine cannot enforce that**, and
should not pretend to: exclusion is asked about a *path*, by `excluded()` and by `walk()`, and a path
does not say whether it is a directory. Checking the entry kind would give the walk and the
preservation check two different answers to the same question — which is precisely the divergence
phase 1's walkthrough §2 warned about.

There is also nothing for it to do. Subtree coverage already comes for free twice over: the walk
prunes at a matched directory and never descends, and `excluded()` walks a path's ancestors. So
`.cache` and `.cache/` behave identically, and the marker is accepted, normalised away, and reads as
intent.

Documented as exactly that. The alternative — silently accepting a marker that implies a distinction
the engine does not make — is the kind of thing that gets discovered as a bug three phases later.

## 15. Correction to decision 3: the hash is a circular cache key

§5 proposed caching the compiled rules against the `.vfsignore` **entry hash**, and §11 approved it.
It does not work, and the failure is worse than the latency it was trading for.

**The hash lives in the entry, and the entry does not exist until a scan has produced it.** So on the
pass where someone writes a `.vfsignore` by hand, the tree has no entry for it, the cache sees no
change, and the walk runs with no rules. The file the rule was written to exclude is therefore
**tracked in that pass** — and then phase 1 does exactly what it promises: on the next scan the rule
does cover it, so its entry is *preserved* rather than deleted, and it stays in the tree for good.

The rule never excludes what it was written for. §5 called this "one extra pass, the honest price";
it is not a delay, it is the feature not working.

Three of the eighteen tests failed on this, which is the argument for having written them.

**What replaced it**: the walk's own `mtime` + `size`.

```ts
let walked = await walk(this.adapter, listing);
if (await this.refreshShared(walked)) walked = await walk(this.adapter, listing);
```

`.vfsignore` is exempt from exclusion, so the walk always returns it, carrying the stat. If that stat
moved, the file is read, and if its *content* actually changed the rules recompile and the pass is
redone under them. Three properties, and each one is why this shape and not another:

- **It preserves what decision 3 wanted.** No read while the file is untouched, which on Drive is the
  round trip that mattered. The evidence is `mtime`+`size` rather than a hash, which is not a new
  weakening: it is the same evidence `scan()` already trusts to skip re-reading every other file in
  the folder.
- **It preserves pruning.** The obvious alternative — walk everything, filter afterwards — would have
  cost the listing of every excluded subtree, and pruning `@eaDir` folders across a catalogue is the
  use case the feature exists for.
- **The second walk is rare.** Only when the rules genuinely changed. A touched file with identical
  content compares equal on text and does not trigger it.

## 16. What the tests pinned that the plan did not

**A rule and the file it covers, created together, now behave.** The test writes a widened
`.vfsignore` and a file it covers in one pass, and asserts the file is never tracked. Written against
the hash-keyed version it fails, which is §15 in one assertion.

**And the file that was already tracked stays.** The same test asserts it, because the two halves are
easy to conflate and only one is a bug: a rule governs what is *watched*, not what *exists*. Phase 1
settled that; phase 3 is the first code that exercises it through the real distribution mechanism
instead of a hand-passed predicate.

**A `.vfsignore` naming itself is survivable.** A peer can ship `.vfsignore` as a rule inside
`.vfsignore`, and every peer that receives it still walks it and still converges. That is §4's
structural exemption doing its job, and it is the test that justifies not throwing on parse.
