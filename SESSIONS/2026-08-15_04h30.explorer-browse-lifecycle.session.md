## 0. What this is, stated honestly before anything else

**This session is not opened by a defect.** The last two were, and this one is not, so the
justification has to carry its own weight:

Ten methods of `explorer/src/model.ts` are called by **no test at all** — established by grep over
`test/`, not by reading a coverage percentage:

`newBrowseFolder`, `deleteBrowseEntry`, `removeSource`, `regrantSource`, `selectSource`, `closePeer`,
`toggleDir`, `selectRoot`, `toggleLog`, `clearLog`

Two of them destroy things a person cannot get back — `deleteBrowseEntry` removes a folder and
everything inside it, `removeSource` closes every tab of a filesystem and drops the Drive token — and
they are the only destructive operations in this repo with nothing behind them. `model.ts` stands at
**72.25 % of statements and 81.30 % of functions**.

**What the reading did *not* find**, said plainly so nobody expects a fix in the walkthrough: the
prefix hazard a reviewer reaches for first is already handled. `deleteBrowseEntry` matches tabs with
`p.key === k || p.key.startsWith(`${k}/`)` ([model.ts:1206](../explorer/src/model.ts#L1206)), and
`forgetSubtree` carries the same guard with the comment *"`one` must not take `one-b`"*
([model.ts:991](../explorer/src/model.ts#L991)). So this is a **regression lock**, and the risk it
carries is this repo's own §6 rule: tests that pass for the wrong reason. That is why §5 is not
optional here.

One thing the reading *did* find is a real behavioural asymmetry, and it is a question for review
rather than a defect — §4.

## 1. Why this and not `eol` or `location`

`eol` (§2.3 of the capitulation) and `location` (§2.4) both widen a contract for a consumer who has
not asked, which is the speculative work this project keeps refusing. This one adds no contract at
all: it is test-only, in a folder that does not ship, over the last paths a person drives by hand.

The browser pickers (§2.2) stay deferred: they need a stand-in for Google Identity Services and one
for the File System Access picker, which is a different problem and a separate session.

## 3. What has to hold

Thirteen properties, one test each unless noted.

**Deleting a folder** — [`deleteBrowseEntry`](../explorer/src/model.ts#L1194)

1. The tab open on the deleted folder closes, **and so does a tab open on a folder inside it**, and a
   sibling whose name shares the prefix (`one` beside `one-b`) stays open.
2. Cancelling the confirm deletes nothing, closes no tab, and leaves the cached listing intact.
3. The confirm says which path it is about — it is the last thing a person reads before losing a
   folder, so its `message` is asserted, not just its existence.

**Closing a tab** — [`closePeer`](../explorer/src/model.ts#L851)

4. Closing the **active** tab activates a neighbour and clears `selection`, `details` and `dirty` —
   the three that would otherwise describe a root that is gone.
5. Closing a **non-active** tab leaves `active` where it was.
6. Closing the last tab leaves `active === ''`, which is the new-tab view.

**Forgetting a filesystem** — [`removeSource`](../explorer/src/model.ts#L1227)

7. Every tab of that source closes, the source leaves `sources`, and `activeSource` and `browseSel`
   stop naming it.
8. Tabs of *another* source are untouched — the sibling case again, one level up.

**Creating a folder** — [`newBrowseFolder`](../explorer/src/model.ts#L1152)

9. It creates inside the selection: a selected directory is the parent, a selected file contributes
   its folder, nothing selected means the root. Three assertions, one test.
10. The new folder is revealed (every ancestor unfolds) and **is not probed for a `.vfs` store** —
    the model seeds it as known-empty ([model.ts:1176](../explorer/src/model.ts#L1176)), which
    `counting()` makes visible as one fewer read.
11. Cancelling the prompt creates nothing.

**The rest**

12. `selectSource` re-clicked on the **already active** source drops its cached listings and re-reads;
    selecting a different one does not re-read the first. (`counting()`.)
13. `regrantSource` reports both outcomes — granted and denied — through the log. Driven with
    `FSAAdapter.fromHandle` over a `FakeDirectoryHandle` with a stubbed `requestPermission`, the
    pattern `handleWith()` already uses at
    [browser-adapters.test.ts:125](../test/browser-adapters.test.ts#L125).
14. `toggleLog(true)` on a model booted with `activityLog: false` **stays closed** — the `wantsLog`
    gate ([model.ts:2107](../explorer/src/model.ts#L2107)) — and opening it resets the unread count;
    `clearLog()` empties the entries and the count. One test.
15. `toggleDir` folds and unfolds without reading the backend, and `selectRoot` clears the file
    selection. One test, the two cheapest methods on the list.

## 4. For review: the one asymmetry the reading found

`deleteBrowseEntry` closes the tabs **before** it calls `adapter.delete(path)`
([model.ts:1204-1210](../explorer/src/model.ts#L1204-L1210)). If the delete throws — a Drive request
that fails, a permission that lapsed — the folder is still there and its tab is already gone. The
`catch` logs the error and the person is left looking at a filesystem that still holds the folder
they thought they deleted, with no tab on it.

The order is not obviously wrong: closing after the delete would leave tabs pointing at a folder that
no longer exists for as long as the delete takes, which is the worse failure. **The proposal is to
pin the current behaviour with a test and say so in a comment**, rather than change it. Reopening the
tab is one click and the log names the error.

Say so if you would rather the tabs were reopened on failure — it is a few lines, but it is a
behaviour change and it belongs to you, not to a test.

## 10. Where `deleteBrowseEntry` is called from, and the one that was not planned for

Two sites, both in the new-tab browse column — the view that browses a backend *before* anything is
opened as a tab:

| Call site | Reaches it with |
| --- | --- |
| the `×` on a **directory row** of the browse tree ([NewTabView.tsx:199](../explorer/src/components/NewTabView.tsx#L199)) | a folder, always — the file branch of `BrowseRowItem` paints no button |
| the **Delete** button in the details pane's header ([NewTabView.tsx:298](../explorer/src/components/NewTabView.tsx#L298)) | **whatever is selected — file or folder** |

The second one was not in the plan's model of this method. The header block that holds the button is
rendered before the `data.kind === 'file' ? …` that decides the body, so it is there for a selected
file too.

For contrast, and because it is the distinction that keeps this method small: deleting inside an
**open root** is `deleteFile(peer, path)`
([PeerDetails.tsx:179](../explorer/src/components/PeerDetails.tsx#L179)), which goes through the node,
leaves a tombstone and travels. `deleteBrowseEntry` calls `source.adapter.delete(path)` — the
backend, with no store in the path.

## 11. The defect

The confirm is written for folders only ([model.ts:1196-1201](../explorer/src/model.ts#L1196-L1201)):

```ts
title: 'Delete folder',
message: `Delete ${path} and everything inside it?`,
```

So selecting `notes.md` in the browse pane and pressing Delete asks **"Delete folder — Delete
notes.md and everything inside it?"**.

The deletion itself is correct for a file: `adapter.delete` handles both kinds, `forgetSubtree` over
a file path matches its own key and nothing else, `expanded.delete` is a no-op, and no tab can be
open on a file. **What is wrong is the only sentence a person reads before losing something**, and it
describes a recursive delete that is not happening. Two consequences, opposite directions: somebody
who wanted the file hesitates, and somebody who misreads which entry is selected is told it is a
folder and believes it.

This is the same class as the dialog `71c7803` rewrote in the explorer — *"a destructive action
described as a merge is the one place this change could hurt somebody who read the button"*.

## 12. The fix, and why the parameter is required rather than defaulted

`deleteBrowseEntry(source, path, kind: 'file' | 'directory')`, with the two texts:

| `kind` | title | message |
| --- | --- | --- |
| `directory` | `Delete folder` | `Delete ${path} and everything inside it?` |
| `file` | `Delete file` | `Delete ${path}?` |

The tree row passes `'directory'` — it can be nothing else — and the details pane passes `data.kind`.

**Not defaulted to `'directory'`.** A default is what let this happen: the method reads as if its
argument could only be a folder, and a call site that did not think about it compiled. Required, the
compiler asks every future caller the question. The explorer does not ship in the package's `files`,
so there is no consumer to break.

Deriving it from `browseSel` instead would be wrong: the row's `×` deletes without selecting, so the
selection can name a different entry than the one being deleted — a worse version of the same bug.

## 17. What the plan got wrong: its own mutant list was not a cover

§5 listed nine mutants and called them mandatory. Mapping them against the tests afterwards showed
they pinned **12 of the 18 tests** the plan asked for. Six would have been decoration by the plan's
own definition — the folder confirm's wording, the cancelled prompt, the non-active close, the log
badge, `toggleDir` and `selectRoot`.

Mutants 11–18 exist for exactly those six. That is the correction worth carrying: **a mutant list
written from the code is not the same as one written from the tests.** The first asks *what could
break*; only the second asks *what would notice*. Write the list, then map it back onto the tests and
fill the holes — the holes are where the decoration is.

Mutant 13 also needed a second attempt: its first anchor matched two places in the file, and a
mutation applied to the wrong one proves nothing. Anchors are now asserted unique before they run.
