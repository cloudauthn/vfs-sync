## 0. The plan calls this "mostly documentation", and two thirds of it is

Three rows in the plan's table. Two are prose. The third — *open up `MergeOptions`' `text?` so the app
can pass its own, the extension point already exists* — is a two-line change if the extension point is
where it looks. §1 is why it is not where it looks.

## 1. `text` is a write-time decision wearing a merge-time mask

| Site | When | What it decides |
| --- | --- | --- |
| [sync.ts:191](../src/sync.ts#L191), [sync.ts:378](../src/sync.ts#L378) | merge | `ConflictReport.text` |
| [vfs-node.ts:751](../src/vfs-node.ts#L751) `keepText()` | commit | whether `base/<hash>` gets the bytes |
| [vfs-node.ts:269](../src/vfs-node.ts#L269) `isText()` | any time | the public answer to the same question |

A three-way merge needs base + A + B. A and B are the two working files and are free. The base exists
only because `keepText()` wrote it **when the version was recorded** — by the time a scan notices the
edit, the previous bytes are gone. `keepText()` is the reason the merge works at all.

So a predicate injected at merge time alone is inert on exactly the paths it was added for. The path
was not on the list three commits ago, no base was written, and `baseOf()` has nothing to hand back
([sync.ts:902-904](../src/sync.ts#L902-L904)) — `diff3` is never called, the conflict copy is parked
as before, and `report.text` still says `true`. The caller gets a flag claiming a text conflict over a
merge that never had a chance.

That is worse than not shipping the option: it reports the feature working. **The predicate has to
reach the place where the base is kept**, and that is what makes this row code.

## 2. Where it lives: `open()`, beside `materialize`

```ts
VFSNode.open(fs, { text: (path) => path.startsWith('catalog/') });
```

Local, never travels, the engine stores nothing about it — the `materialize` contract word for word
([vfs-node.ts:33-56](../src/vfs-node.ts#L33-L56)). Consulted at all three sites of §1, so what is
merged and what is retained can never drift apart.

**Rejected: `SyncOptions.text`.** §1 is the whole reason. A predicate handed to `sync()` cannot reach
back and keep a base three commits ago, and one sync call is not the scope of a decision that has to
hold at every commit.

## 3. It adds; it does not subtract

A path is text when the converged list covers its extension **or** this node's predicate says so.

That is not a corner cut. `sync()` computes one merge with one predicate, and for two nodes the honest
one is the union of their answers — `autoMergeText` already takes the base from whichever peer kept
it, `(await a.baseOf(ancestor)) ?? (await b.baseOf(ancestor))`, so one side retaining is enough for
both. Under union, a subtraction on one side is overruled by the other side's list. Offering it would
be offering a switch that works only when the peer happens to agree, which is the worst of the three
available behaviours. The switch that does work is `autoMerge: false`: per call, total, already there.

## 4. What this deliberately does not open: the travelling list

`file.text` is seeded once at creation from `DEFAULT_TEXT_EXTENSIONS`
([store.ts:144](../src/store.ts#L144)) and written afterwards only by convergence
([sync.ts:685-686](../src/sync.ts#L685-L686)). **There is no supported way to add an extension to it**,
and phase 4 does not add one.

A decision, not an oversight: the list converges by union and nothing ever removes an entry, so an
`addTextExtension('json')` would be a one-line, one-way door for the entire mesh — every `.json` on
every peer, permanently, from one call on one device. The local predicate gives the node that asked
for it the same reach and imposes nothing on anybody else.

A consumer who genuinely wants the mesh-wide widening can still do it through the exported file
primitives; it is simply not a convenience method. That is the right ratio for something with no undo.
Written down here so it is not re-opened later as a gap.

## 5. The prose rows

### 5.1 CRLF vs LF (`reason: 'eol'`)

Already a returned reason ([conflicts.md:372](../docs/conflicts.md#L372),
[api.md:590](../docs/api.md#L590)) and pinned by a test
([diff3.test.ts:60](../test/diff3.test.ts#L60)). What is missing is the consequence, stated where the
person hitting it will be looking: a mesh writing the same file from Windows and from macOS never
merges anything, collects a conflict copy every single time, and is told nothing — because `diff3`'s
reason dies inside `autoMergeText` and never reaches the caller.

Normalising is not the fix and never will be: it would change the content, and with it the hash and
the identity. The terminator is the consumer's to settle, and the documentation has to say so plainly
rather than list `'eol'` among three enum values.

### 5.2 The reason a merge did not happen (the one item beyond the plan)

`ConflictReport.text` is `true` both for "merged" and for "was eligible and refused", and the caller
cannot tell which. Proposal, one field:

```ts
/** Why the three-way merge did not settle this one. Absent when it did. */
textReason?: 'block' | 'size' | 'eol' | 'no-base';
```

Set in `autoMergeText` from the `diff3` result, plus `'no-base'` for the case §1 describes. It costs a
field and four assignments, and it turns 5.1 from a documented caveat into something the consumer can
see. It is also the same shape as the last session: we already have the diagnosis and are throwing it
away one stack frame before the caller.

**Cut it if the scope is unwelcome** — the rest of the session stands without it.

### 5.3 Line-based, so a minified file merges nothing

Not a bug, a condition of the technique: whoever wants a field-level merge serialises one field per
line. This is worth stating loudly precisely because `json` ships in the defaults — the default list
promises a merge that a one-line document will never get.

### 5.4 Union convergence of the list

One peer adding `json` makes every `.json` in the mesh attempt a merge. With §4 no caller can cause
this by accident, which is most of the risk; documenting it stays worthwhile for the peer that arrives
with an older list and finds it widened by someone else.

## 6. Tests

- A path only the predicate covers keeps a base at commit, and merges at sync.
- The same path with no predicate: no base, conflict copy, `merged: 0`. The negative is the one that
  shows the base is what does the work, and without it §1 is an assertion in a session file.
- Predicate on one node only still merges — union, with the base coming from the peer that kept it.
- An extension on the list merges even though the predicate returns `false` (it adds, §3).
- `isText()` answers the same as the merge does.
- With 5.2: `textReason` is `'eol'` for a CRLF/LF pair and `'no-base'` when nothing was retained.

- `docs/conflicts.md`: 5.1, 5.3 and 5.4 as consequences a consumer plans around, not as caveats.

## 10. What landed

[`keepText()`](../src/vfs-node.ts#L795) at commit, [`isText()`](../src/vfs-node.ts#L297) as the full
public answer, and the merge through [`textPredicate()`](../src/sync.ts#L687), which folds the
converged list together with both nodes' policies into the one predicate `mergeEntries` takes.

`marksText(path)` is new and public for the same reason `wants(entry)` is: `sync()` has to ask both
nodes a question the pure merge cannot ask, and the union has to be visible rather than reconstructed.
It answers about this node's policy alone; `isText()` is the union with the list.

## 11. The fifth reason

The approved enum was four values. It shipped as five: `'unreadable'`, for a peer that holds the entry
and not the bytes.

The case is not hypothetical and phase 2 is what made it common — a node with selective materialisation
relaying a file it never fetched hits it on the first conflict. Before this session it was
`if (!mine || !theirs) continue`, silent; leaving it silent while adding a field whose entire purpose
is to end silent skips would have left the hole in exactly the place someone would look first. It is
covered by a three-peer test with a non-materialising relay in the middle.

## 12. The test that was wrong, and what it taught

§6 planned a negative: *the same path with no predicate → `no-base`*. It fails, and correctly. Without
a policy, `catalog/index` has no extension on the list, so the conflict is never flagged as text and
`autoMergeText` never looks at it — there is no refusal to explain. `textReason` is for "eligible and
refused", not for "not text".

The honest reproduction of §1 is **a policy that arrives after the versions were written**: open the
folder without it, diverge, reopen with it. The conflict is now text, and there is nothing to merge it
against — `no-base`. That is not a corner case, it is precisely what `SyncOptions.text` would have
produced for every path it named, on every sync, forever. The rejected alternative of §2 is now a test
that passes, which is a better argument than the paragraph.
