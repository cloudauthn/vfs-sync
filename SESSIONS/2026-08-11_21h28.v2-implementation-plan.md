# Implementation plan — vfs-sync v2

**Date**: 2026-08-11 21:28
**Base**: `main` @ `9ab43ec` (v0.1.24)
**Status**: B.1 reproduced and confirmed locally; everything else is design, not yet written.

**Origin of the requirements**:
[`2026-08-11_21h12.musikmatch-driven-requirements.md`](./2026-08-11_21h12.musikmatch-driven-requirements.md),
the request of one specific consumer.

**How that origin is used.** A consumer serves to *discover* a gap, never to justify it. Every point
in this plan stands on library terms — which primitive is missing, which invariant breaks — and
concrete use cases appear only as illustration, marked as such. If a priority can only be defended by
saying "this consumer does not need it", it is badly argued: the correct statement is that **no
consumer has asked for it yet**, which is revisable the moment a second one shows up. See §6, where
that distinction changes the conclusion.

---

## 0. The finding that reorders the plan

The requirements document asks for two things it treats as independent:

- **B.1** — ignoring an already-tracked file emits a tombstone and deletes it mesh-wide.
- **A** — selective materialisation: a peer with the entry but without the bytes.

**They are the same bug on the same line.** `scan()` infers what was deleted from absence:

```ts
const alive = new Set(seen.map((item) => item.path));            // vfs-node.ts:332
const vanished = live.filter((entry) => !alive.has(entry.path)); // vfs-node.ts:333
```

`alive` comes from the walk. Everything the walk does not return is declared vanished and gets a
tombstone at [vfs-node.ts:427-455](../src/vfs-node.ts#L427-L455). There are at least three different
reasons a walk does not return a path, and the engine only considers one:

| The walk does not return it because… | Today | It should be |
| --- | --- | --- |
| the user deleted it | tombstone | tombstone |
| an `ignore` rule filters it | tombstone ← **B.1** | untouched |
| this node never materialised the bytes | tombstone ← **A** | untouched |

The engine has no concept of **"absence is not always evidence"**. B.1 and A are two consumers of the
same missing primitive. That changes the order of the plan: they are not two competing high-priority
tasks, they are one task from which both fall out.

### B.1 reproduced

Run against `main`, two in-memory peers, a tracked and synced file that a `*.tmp` rule later covers:

| Scenario | Peer that ignores | Peer that does not ignore yet |
| --- | --- | --- |
| both apply the rule | bytes on disk ✓, entry = tombstone | — |
| only A applies the rule | bytes on disk ✓, entry = tombstone | **bytes deleted from disk** ✗ |

**Correction to the requirements document**: the tombstone does not "delete it on every peer". The
peer that ignores *keeps* the bytes — by accident, because its own walk no longer touches that path —
and is left with an orphaned file: present on disk, dead in the mesh. The one that loses data is
**the peer that does not have the rule yet**.

That asymmetry makes the bug worse rather than milder, for two reasons:

1. **The losing case is the normal path.** §B.3 of the requirements document says `.vfsignore` is
   synced content, so it reaches peers in a staggered fashion. During that window there is always
   someone without the rule, and that someone deletes.
2. **The bug is invisible from where it is caused.** Whoever writes the rule keeps their bytes and
   sees nothing odd; the loss happens on another machine. In the symmetric scenario the tombstone was
   moreover attributed to peer `b`, not to the one that introduced the rule, so there is not a single
   trace pointing at the cause.

## 1. Phase 1 — Absence stops being evidence of deletion

**Priority: maximum. It is data loss, and everything else depends on this primitive.**

### 1.1 The rule

A path absent from the walk only produces a tombstone if **both** conditions hold:

- **(a)** the current `ignore` rule does **not** cover it, and
- **(b)** this node has observed that file on disk at some point.

### 1.2 (b) comes for free: the marker already exists

No state has to be invented for (b). `adopt()` already establishes exactly that invariant:

```ts
const next: VFSEntry = { ...entry };
delete next.native;
delete next.mtime;                                    // vfs-node.ts:701-702
// …
} else if (!entry.deleted && !(entry.held && entry.held !== this.id)) {
  const stat = await this.adapter.stat(entry.path);
  if (stat) next.mtime = stat.mtime;                  // vfs-node.ts:710-712
}
```

`mtime` is always deleted and only re-set from a real `stat()` of the disk. And note the guard on line
710: a `held` entry — whose bytes deliberately did not travel — skips the `stat` entirely and ends up
**without `mtime`**. So the invariant is already exactly

> **`mtime` present ⟺ this node has seen the file on disk.**

It is the property (b) needs, already upheld by the code, and upheld precisely by the "the entry
travels, the bytes do not" case that the requirements document points to as precedent. It also fails
on the safe side: if a transient `stat` returns `null`, the `mtime` is lost and at worst a real
deletion goes undetected — recoverable on the next pass. The opposite, a false deletion, is what
cannot be allowed.

### 1.3 The change

In `scan()`, between lines 332 and 334, split `live` in two instead of filtering:

```ts
const alive = new Set(seen.map((item) => item.path));
// A path the walk did not return is not necessarily deleted: it may be
// filtered by the current rule, or never have been materialised here.
const absent = live.filter((entry) => !alive.has(entry.path));
const preserved = absent.filter((entry) => this.ignore?.(entry.path) || entry.mtime === undefined);
const vanished = absent.filter((entry) => !preserved.includes(entry));
```

And three details that are not optional:

- **`preserved` must not enter `vanishedByHash`** ([vfs-node.ts:334](../src/vfs-node.ts#L334)). That
  map is the pool against which moves made outside the VFS are matched. If a preserved entry is still
  in it, a new file with the same content at another path would read as a *move* of the preserved
  entry, and would displace it.
- **Their uuids are added to `used`** before the tombstone loop. That way the loop at
  [vfs-node.ts:427](../src/vfs-node.ts#L427) skips them, and they are also left out of the rename
  claim (`if (prior && used.has(prior.uuid)) prior = undefined`).
- **The entry is copied verbatim into `entries`**, without touching `updated` or `peer`. Any
  re-stamping would let it win a tiebreak by date that it has not won.

**Zero log rows.** Preserving is not an operation; it is the absence of one.

### 1.4 What `ignore` explicitly does NOT do

The preserved entry stays **live and inside the `state` digest**. This deserves an argument because
intuition asks for the opposite:

If ignored entries dropped out of the tree, two peers with different rules would never agree on
`state`. And `state` is precisely the comparison that answers "is there anything to sync?" — the sync
would enter a permanent loop between a node that filters a subtree and one that does not. **The digest
has to describe the mesh, not each node's local policy.**

So the semantics settle as: **`ignore` means "I do not watch this path", not "this path does not
exist".** It is git's model, where `.gitignore` only governs the *untracked*.

A consequence that has to be documented: **there is no way to untrack without deleting.** If you want
an already-tracked file to disappear from the mesh, you delete it deliberately and *then* the rule
keeps it from coming back. Git forces the same with `git rm --cached`. We are not adding a local
`forget()` because it would not be coherent: the other peer has it live and the next sync would bring
it back.

### 1.5 Tests

- **Asymmetric regression** (the one that lost bytes): A ignores a tracked file, B does not yet; B
  keeps the file on disk and its entry live. *This is the variant that matters* — with both peers
  ignoring, the file survives on disk and the bug goes unnoticed.
- **Symmetric regression**: both ignore; entry live on both, no `delete` rows in the log.
- **Real deletion still works**: a file covered by no rule and carrying `mtime` still emits a
  tombstone. The safety net against overcorrecting.
- **An entry without `mtime` is not tombstoned**: adopted from a peer, bytes never written, the scan
  respects it.
- **`preserved` does not steal renames**: an ignored file at `a.tmp`, `b.txt` appears with the same
  content → `b.txt` is a new file, not a move.

## 2. Phase 2 — Selective materialisation (A)

**Depends on phase 1.** With the primitive in place, what is left is small.

### 2.1 The precedent, and how far it reaches

`held` already implements "the entry travels, the bytes do not", honoured in two places:

```ts
if (entry.held && entry.held !== nodeId) continue;   // sync.ts:459  — planChanges
if (entry.held && entry.held !== this.id) continue;  // vfs-node.ts:588 — apply
```

Generalising means adding the new condition in those same two places. There is no third place where a
transfer is decided.

### 2.2 The policy is a predicate, not state

**The engine stores nothing.** Just like `ignore`, the application passes a predicate:

```ts
/** Bytes this node keeps on disk. Everything else: the entry yes, the bytes no. */
materialize?: (entry: VFSEntry) => boolean;
```

That is what keeps it agnostic. The engine does not store a list of 200,000 dematerialised paths nor
does it have to maintain it across renames: the policy is evaluated by whoever knows it, and it can be
anything — by path prefix, by size, by what the user has pinned — without the engine knowing what it
is based on.

*Illustration*: a client with the library on the desktop and a phone that can only host the metadata
would pass a predicate on directory prefix. Another with a size threshold would pass
`(entry) => entry.size < 10_000_000`. The engine does not care which.

Ruled out: a per-entry field like `mtime`/`native`. It would travel in `canonicalEntry`, and a stale
marker from another peer is actively harmful — B would adopt A's mark and stop syncing a file it does
have. `adopt()` would have to clear it, which is more surface for the same result.

### 2.3 Distribution of effects

| Effect | Where | How |
| --- | --- | --- |
| reconciliation does not tombstone it | `scan()` | **already covered by phase 1**: no bytes on disk means no `mtime` |
| sync does not fetch them | `sync.ts:459`, `vfs-node.ts:588` | a condition alongside the `held` one |
| other peers neither know nor care | — | free: nothing that could travel is stored |

That the first row comes for free is the sign that phase 1's primitive was well chosen.

### 2.4 Fetching the bytes on demand

`node.materialize(path)` — asks a peer that has it for the content and writes it, with the same hash
verification as `apply()` ([vfs-node.ts:661-676](../src/vfs-node.ts#L661-L676)). The app's predicate
does not have to change its mind first: as soon as the bytes are on disk, the next scan stamps the
`mtime` and the entry becomes ordinary.

**Open question**: `materialize()` needs a source. Today `ContentSource` is built by `sync()` for the
duration of a sync. It has to be decided whether the API asks for an explicit peer
(`node.materialize(path, from)`) or the node holds a provider. The former is simpler and invents no
lifecycle; the latter is more convenient for the caller. **Recommendation: explicit peer**, and let
the consumer wrap it if it wants something more ergonomic.

## 3. Phase 3 — Exclusion rules with a file format (B.2, B.3)

**Depends on phase 1**, and not only for ordering: without it, distributing a `.vfsignore` *is* the
mechanism that triggers the data loss.

It is implemented exactly as §B.2/B.3 of the requirements document specifies, which is settled. A
summary of what is accepted unchanged:

- Two places: `.vfsignore` in the working folder (travels, plain text, `#` comments) and an `ignore`
  field in the `vfs.json` header (local, JSON array, set through the API).
- Composition by **union**, with no `!pattern` negation — without negation no tie is possible and
  there is no precedence to define.
- Syntax subset: exact path, directory prefix `.cache/`, and `*` over the name, all three **at any
  depth**.
- `.vfsignore` cannot ignore itself; the engine rejects the rule.

Two implementation notes:

- **The header's `ignore` field goes in `local`**, next to `verifiedAt` and `pendingRenames`
  ([types.ts:243](../src/types.ts#L243)). That object is already described as "travels in the file but
  is ignored by whoever reads it", which is exactly the contract needed.
- **Startup order**: the sync that brings new rules still runs with the old ones, and converges on the
  second pass via `syncUntilStable`. With phase 1 in place this stops being dangerous and becomes just
  one extra pass.

And [`docs/recipes.md:196-197`](../docs/recipes.md#L196-L197) has to be corrected: today it claims
ignored paths "never appear as deletes on the other side" — true only for paths that were **never**
tracked, and it is the sentence that gives the bug cover.

## 4. Phase 4 — Closing the text-merge contract

Not in the requirements document: it comes out of reviewing `diff3.ts` prompted by the question of
whether we were using diff. The answer is that we are, and that it is well built — the base kept in
`base/<hash>` captured on write ([vfs-node.ts:499](../src/vfs-node.ts#L499)), all-or-nothing with no
`<<<<<<<` markers, and identical edits not counting as a conflict. What is missing is contract, not
code:

| Limit | Today | What to do |
| --- | --- | --- |
| Selection by extension, not by path | `sync()` always instantiates `text: (path) => text.includes(extensionOf(path))` ([sync.ts:177](../src/sync.ts#L177), [364](../src/sync.ts#L364)) | open up `MergeOptions`' `text?` so the app can pass its own — the extension point already exists in `merge.ts`, it is just that `sync()` does not let it through |
| CRLF vs LF gives up (`reason: 'eol'`) | correct: normalising would change the hash and with it the identity | **document it**: a consumer writing text from several platforms has to fix the terminator, or it will never see a merge and will not know why |
| It is line-based | a one-line JSON merges nothing | **out of the library's scope**: whoever wants a field-level merge has to serialise one field per line. Document it as the condition it is |

The first row is the only real friction, and it is small. A design note: the `text` list converges **by
union** between peers ([sync.ts:127](../src/sync.ts#L127)), so if one peer adds `json`, *every* `.json`
in the mesh starts attempting a merge. That may be exactly what is wanted, but it has to be decided
knowingly.

Low priority. It blocks nothing.

## 5. Phase 5 — Native transfer fast path (C)

Medium priority, with no dependency on the above. There is a single site:

```ts
const handle = await source.open(hash, entry);   // vfs-node.ts:661
```

That is where a stream is opened today and the bytes are pumped over the wire. The fast path is a
branch before it: if source and destination share a backend, one call to the backend's API and zero
bytes through the process.

It fits the optional-method-with-emulation pattern of §8, alongside `append?` and `changes?`
([types.ts:112-136](../src/types.ts#L112-L136)):

```ts
/** Copy within the same backend. `null` when it cannot — the caller pumps the bytes. */
copyFrom?(source: VFSAdapter, from: string, to: string): Promise<boolean>;
```

Two conditions that cannot be relaxed:

- **Backend identity, not backend type.** Two Drive adapters against different accounts do not share a
  fast path. Something stronger than `adapter.name` is needed.
- **The hash verification is not skipped.** Today everything that arrives is re-hashed against what
  `vfs.json` declares, and the comment on `apply()` explains why: without it, a truncated upload lands
  as "the newest version". A native copy is not trustworthy by definition either. If the backend
  returns its own checksum (Drive does), that counts as verification; if not, the fast path only
  applies where the backend guarantees integrity, and that has to be written down.

It rises in priority with v2 because §9 gives up deduplication: there will be more real transfers.

## 6. D — Delta transfer: out of scope for now, and why the nuance matters

Today a one-byte change resends the whole file. The requirements document marks it low priority with
this argument: *heavy content is immutable, so large files are not rewritten in the normal editing
cycle*.

**That argument is not the library's, it is a consumer's.** And the distinction is not pedantic,
because it changes what the decision means:

| Formulation | What it implies |
| --- | --- |
| "heavy content is immutable" | a **law of the domain**: delta transfer will never be needed |
| "no current consumer rewrites large files" | a **revisable observation**: it is needed as soon as one appears that does |

The second is the true one. Any consumer whose large files are mutated in place — VM images, SQLite
databases, growing logs, video or CAD projects — would pay for the whole file on every change, and for
that profile this goes from "low priority" to being the reason the library does not serve.

It is also worth marking that **v2 §0's premise — immutable heavy content — is a scoping hypothesis
inherited from the current consumers**, not a property of the problem. Building on it is fine;
forgetting that it was chosen is not.

**Decision**: it does not enter this plan. It is the largest piece of work on the list and nobody has
asked for it yet. But it gets revisited with the second consumer, not with the first complaint.

**What does have to be done now**: do not close the door on it. The point where sending a delta would
be decided is exactly the one where phase 5 puts the native fast path —
[vfs-node.ts:661](../src/vfs-node.ts#L661), `source.open(hash, entry)` — so that seam should be left
clean and should not assume in its shape that what arrives is always the complete file. It is zero
cost to get it right while phase 5 is touching it, and expensive afterwards.

If it is ever taken on: content-defined chunking (FastCDC) rather than fixed blocks, because the
typical shape of the problem is a *shifting prefix* — a header that grows and displaces everything
after it — and fixed blocks reuse nothing there. And there is a consequence of v2 that complicates it:
without content addressing (§9), a delta is applied by writing **inside the working file**, not by
assembling a new object, so the subsequent hash verification stops being optional.

## 7. Phase 6 — Identity and the pairing guard

**Not from the requirements document**: it comes out of asking what mechanism decides today which
content rules. It does not depend on phase 1 and can be done in parallel. It is not data loss like
B.1, but the merge it prevents is just as irreversible: there is no `unmerge`.

It is also the only phase that **changes the format**, so its migration cost grows with every deployed
installation.

### 7.1 The gap

`storeId` **is not read anywhere**. It is written in the header
([vfs-file.ts:100](../src/vfs-file.ts#L100)) and converged on the smaller
([sync.ts:126](../src/sync.ts#L126)), and that is it: it indexes nothing, authorises nothing, is the
key to no lookup. Nothing prevents pairing two folders that have nothing to do with each other.

### 7.2 Two identities, not three

The engine needs to answer exactly two identity questions: **who am I** and **which group do I belong
to**. Today there are three fields for that, and one is redundant.

| | Identifies | Born | Converges |
| --- | --- | --- | --- |
| `peerId` | **the node** | `init()`, UUIDv4 | never |
| `syncId` | **the group** | first sync | yes, on the smaller, *after* the guard |
| ~~`storeId`~~ | — | — | **removed** |

`peer` already existed and already was the node's identity — born in `init()` with `randomId()` and
with no convergence rule in `sync()`. `storeId`, if it stopped converging, would have exactly the same
properties: born in `init()` and never converging. **Two fields with the same behaviour and a single
job between them.**

And of the two, `storeId` was the weaker: as a detector of duplicated nodes it only sees the case
where the whole `.vfs` is copied, whereas comparing `peerId` also sees the case where the caller
imposes a non-unique id (§7.4). It is removed — but not just discarded: on migration it **seeds the
`syncId`**, which is what keeps a legitimate v2 mesh from fracturing on upgrade (§7.9).

**Rename (decided)**: `peer` → `peerId` everywhere it appears — the `vfs.json` header, `VFSEntry.peer`,
`LogRow.peer` and `MergeSide.peer`, plus `node.id`. Since it is in the log rows, **the `commits` format
changes too**, not just `vfs.json`'s; how that is absorbed without rewriting immutable segments is in
§7.9.

### 7.3 `syncId`: `null` until the first sync

The initial value is an **explicit `null`**, not an absent key. Two reasons:

1. **The encoder already does it.** `encodeVFSFile` writes a fixed list of keys and
   `canonicalJSON(undefined)` returns `'null'` for a top-level value
   ([hash.ts:37](../src/hash.ts#L37)). Omitting the key would require changing the encoder.
2. **The `null` buys information**, and it is the information the migration needs:

| In `vfs.json` | Means |
| --- | --- |
| key absent | written by old code — **unknown** whether it ever synced |
| `"syncId": null` | written by new code — has never synced |
| `"syncId": "g-3f9c"` | affiliated to that group |

Without the `null`, the first two are indistinguishable and the guard cannot tell a virgin folder from
a pre-existing one.

**It is set only on sync**, and the place is `close()`
([sync.ts:571-585](../src/sync.ts#L571-L585)), alongside the `peers` marks — not in the guard:

```ts
fileA.peers[b.id] = { lastSync: at, ... };
fileB.peers[a.id] = { lastSync: at, ... };
fileA.syncId = fileB.syncId = syncId;    // ← here
await a.store.write(fileA);
await b.store.write(fileB);
```

Two reasons for that place: **both files are written in the same pass**, so there is no window in
which one is affiliated and the other is not; and **if the sync fails before reaching it**, neither
ends up affiliated — affiliation records a sync that happened, not one that was attempted.

Minting it poses no coordination problem: `sync(a, b)` has both files in front of it, so it is one
`randomId()` given to both. It is worth writing down in the spec, because a reader might assume it has
to be derived from the two `peerId`s so that both implementations agree, and it does not.

`init()` stops minting two ids: it mints one (`peerId`) and writes `syncId: null`.

### 7.4 The guard: two checks

| Check | Means | Code |
| --- | --- | --- |
| `a.peerId === b.peerId` | not two nodes: one duplicated | `peer-collision` |
| both `syncId` non-null and different | two established groups | `foreign-mesh` |

The remaining `syncId` combinations are not errors:

| A | B | What it is | What it does |
| --- | --- | --- | --- |
| equal | equal | normal state, every sync after the first | carry on |
| `null` | `null` | two virgin folders | mint a `syncId` and set it on both |
| `g-3f9c` | `null` | one joins an existing group | propagate the affiliated one's |

The third row needs no tiebreak: the folder without a `syncId` has no affiliation to lose.

#### Why `peer-collision` is not a net against chance

`randomId()` uses `crypto.randomUUID()` ([hash.ts:95](../src/hash.ts#L95)), so a random collision is
negligible. But that is not the collision that occurs:

| Path | Probability | Role of UUIDv4 |
| --- | --- | --- |
| random collision | ~0 | it prevents it — here it does |
| **the caller imposes the id** via `options.id` | **100%** between two installations that derive it the same way | none: `randomId()` is never even called |
| **the `.vfs` is copied** | **100%** | none: an already-generated value is duplicated |

The last two are certainties. The check costs one string comparison and catches deterministic failure
modes, not statistical oddities.

**Prevention, on top of the guard**: `options.id` overwrites the stored id
([vfs-node.ts:92-95](../src/vfs-node.ts#L92)) and its documentation does not say it requires global
uniqueness. It should say so, and say that **the normal thing in production is to omit it** — the
default is already a UUIDv4 per folder. It stays because the tests use it everywhere
(`VFSNode.open(new MemoryAdapter('a'), { id: 'a' })`), but as it stands its shape invites deriving it
from something non-unique, which is the most likely path to the bug.

#### What a duplicated `peerId` breaks

Concretely: `fileA.peers` is **keyed by `peerId`**, so two nodes with the same one share a single slot
and each sync with one overwrites the other's mark. And that mark feeds the log offset:

```ts
if (mark && mark.digest === file.log.digest) return peer.store.logRows();
if (!mark || mark.segment !== file.log.segment) return peer.store.logRows();
return peer.store.rowsSince(mark.offset);          // sync.ts:649 — byte offset
```

Applying one node's offset to another's log reads from a byte that does not correspond. If it lands
past the end, `rowsSince` returns `[]` and **not a single row is read**; if it lands mid-line,
`parseRows` discards it silently (`catch {}` at [log.ts:70](../src/log.ts#L70), a tolerance intended
for reading a log's tail while an append is half-landed).

Incomplete history has two consequences, and only one is benign:

- **Extra conflict copies** — `descends()` cannot prove ancestry and a propagation reads as a
  conflict. It is what `MergeOptions.history` describes as *"legal and merely pessimistic"*.
- **Deleted files that resurrect** — `solo()` decides whether an entry present on only one side is a
  delete whose tombstone was pruned, by looking at `history.last(uuid)`
  ([merge.ts:287](../src/merge.ts#L287)). If the `delete` row was among the unread bytes, the file
  comes back. This one is genuinely incorrect.

What it does **not** break, so as not to overstate the scope: the `pickNewer` tiebreak
([merge.ts:407](../src/merge.ts#L407)) simply falls through to the `uuid` and stays deterministic.

### 7.5 The library does not ask

The decision belongs to whoever uses it. The library detects, describes and stops — coherent with not
interpreting content: it does not interpret intent either.

A design correction comes with it: **the question is not "which one rules"**. There is no "this folder
wins wholesale" mode; resolution is per file and per version, with ancestry above the clock
([merge.ts:186-200](../src/merge.ts#L186-L200)). The only thing the guard decides is **whether to merge
at all**. Once the merge is authorised, it is the ordinary merge and the smaller `syncId` survives. A
forced mirror is a different, considerably larger operation, and it must not sneak in here.

### 7.6 Shape of the error

Today the engine's errors are strings for humans. A caller cannot build a decision from that: it needs
the case and the data to frame it.

```ts
class PairingError extends Error {
  code: 'peer-collision' | 'foreign-mesh';
  a: { peerId: string; syncId: string | null; entries: number; log: { segment: number; digest: string } };
  b: { peerId: string; syncId: string | null; entries: number; log: { segment: number; digest: string } };
}
```

The entry counts make it possible to present *"1,240 files against 890"* instead of two uuids.

**One code for the collision, deliberately.** It would be tempting to separate "this is a clone" from
"the caller imposes ids", because the remedies differ — regenerating the `peerId` does not fix the
second, since the caller would impose it again. But the library **cannot tell them apart reliably**: a
clone predating the first sync and an imposed id present identically (same `peerId`, `syncId: null` on
both). Deducing it would require comparing the logs, which the guard does not open. The log digests
travel in the payload precisely so the caller can distinguish them if it cares, **without the library
committing to a conclusion it would be guessing at**.

### 7.7 Authorisation is specific, not a switch

`{ adopt: true }` would turn the guard off forever at that call site, including a different collision
months later. Whoever authorises returns what they were told:

```ts
sync(a, b, { adopt: { syncId } })   // the one the error reported
```

If the collision found is not that one, it fails again. It is the idiom the library already uses for
"prove you knew the prior state": `writeIf(path, data, tag)` only lands if the file still carries
`tag` ([types.ts:129](../src/types.ts#L129)).

`peer-collision` **is not authorisable this way**: merging two nodes with the same identity is not a
decision anyone can make well, and the remedy lies outside sync.

### 7.8 Where it goes, and what it breaks

**Site**: in `sync()`, after reading both files ([sync.ts:122-123](../src/sync.ts#L122-L123)) and
before the config convergence. Nothing of the merge has been written at that point, so throwing leaves
both folders untouched — that is the property that makes throwing safe here.

A wrinkle to document: `sync()` calls `a.commit()` and `b.commit()` before
([sync.ts:116-117](../src/sync.ts#L116-L117)), and that does write. It is not a merge and it crosses
nothing between folders — each node consolidates its own state — but it should not come as a surprise.

**What it breaks**: `syncMesh` walks the edges in sequence and an exception aborts the whole loop,
losing the results of the ones already done ([sync.ts:817](../src/sync.ts#L817)). In a mesh of five
folders with one badly paired, today none of them would sync; `syncUntilStable` inherits it. Both ways
out are needed:

- **Collect per edge**: `MeshResult` carries `result | error` and the loop continues. It stops one bad
  edge from paralysing the mesh.
- **The guard in `syncDryRun` too**, which is read-only: the case is detected without attempting
  anything, which is the healthy sequence — ask first, do not rescue afterwards.

**Before touching anything**: the config convergence is duplicated at
[sync.ts:126-135](../src/sync.ts#L126-L135) and [sync.ts:333-339](../src/sync.ts#L333-L339), one copy
for `sync()` and another for `syncDryRun()`. Adding the guard without extracting that leaves three
duplicated rules that have to agree.

### 7.9 Migration: a map, and `storeId` seeding the `syncId`

Three incompatible format changes pile up — `peer` → `peerId`, `storeId` out, `syncId` in — and the
rename touches `commits` as well. A new reader has to know what it is reading before interpreting it,
so `version` goes up to 3; today it is typed as a literal ([types.ts:253](../src/types.ts#L253)) and
becomes `2 | 3`.

#### The map

Declarative and step-by-step, applied in sequence from the file's version up to the current one. It is
also the shape the second implementation can conform to without ambiguity (§8):

```ts
const MIGRATIONS: Record<number, (file: AnyVFSFile) => AnyVFSFile> = {
  2: (f) => ({
    ...f,
    version: 3,
    peerId: f.peer,
    syncId: Object.keys(f.peers).length > 0 ? f.storeId : null,
    peer: undefined,
    storeId: undefined,
  }),
};
```

#### Why `syncId` is seeded and not minted

It is the decision that keeps the migration from breaking what the guard protects. If every folder
minted a fresh `syncId` on migration, **two peers of a legitimate mesh would end up with different
values** and the next sync would declare them `foreign-mesh`.

Seeding it from `storeId` avoids that because in v2 `storeId` **converges on the smaller and is
transitive**: the whole mesh already shares one value. Each peer derives it on its own and they arrive
at the same `syncId` without coordinating.

| v2 case | `syncId` after migrating | Correct? |
| --- | --- | --- |
| A and B, established mesh | the common `storeId` | yes, they keep syncing |
| C, never synced (`peers` empty) | `null` | yes, it adopts on its first sync |
| Foreign meshes M1 and M2 | different | yes, `foreign-mesh` — the case meant to be caught |

So `storeId` is not deleted: **it is transformed**. Its last act is to become the `syncId` of the group
it was already identifying. And the "`peers` empty = virgin" heuristic stops being a permanent bridge:
it lives inside the map, runs once per folder and disappears.

*Known window*: a mesh that has just formed may not have converged its `storeId` yet, and migrating at
that instant would give different `syncId`s. It is narrow and already exists today with `storeId`; it
does not justify extra machinery, but it does justify a line in the spec.

#### `commits` migrates differently

`vfs.json` is one file, small, rewritten on every commit: **eager migration**, the map converts it on
open.

The log cannot do that. Closed segments are **immutable and cached forever**
([store.ts:63](../src/store.ts#L63), [sync.ts:630](../src/sync.ts#L630)), and rewriting them to rename
a field would break that invariant and the cache that rests on it. They can also be many and large.

**Lazy migration**: the reader accepts both shapes and normalises on parse.

```ts
const peerId = row.peerId ?? row.peer;   // in parseRows
```

A permanent one-line cost, in exchange for not touching immutable data. The general rule that comes
out of this and is worth writing in the spec: **what is mutable migrates eagerly, what is immutable
migrates in the reader.**

#### The format-change registry

The map above is one case of something more general: **a table of format changes**, where each step
declares whether it can be reconciled or not.

```ts
type FormatChange =
  | { version: number; kind: 'additive'; note: string }
  | { version: number; kind: 'migratable'; migrate: (f: AnyVFSFile) => AnyVFSFile; note: string }
  | { version: number; kind: 'breaking'; note: string };
```

Three classes, not two, and the distinction is not cosmetic — it decides whether the change can be
released in one go:

| `kind` | The new engine reads the old | **The old engine reads the new** |
| --- | --- | --- |
| `additive` | yes, nothing to do | **yes** — new fields it ignores |
| `migratable` | yes, via `migrate` | **no** |
| `breaking` | no | no |

The column that matters is the second, because on shared storage the old engine **is going to read**
what the new one writes. A `migratable` step is not safe to release all at once even if its `migrate`
is perfect: migration solves reading forward, not the one behind surviving.

"Can I reconcile with a peer on version X?" is then: **every step from X+1 to the current one has a
`migrate`**. If there is a `breaking` in between, no.

#### The higher-version engine raises the error

It is the correct asymmetry, for a concrete reason: **only the new engine has the table**. An old one
cannot diagnose a version it does not know exists.

It goes alongside the guard of §7.4, and **before** it:

```
1. version   → can I interpret this file?         → 'version-unreconcilable'
2. identity  → should I merge with this group?    → 'peer-collision' | 'foreign-mesh'
```

The order is not arbitrary: reading `peerId` and `syncId` requires knowing which version they are
written in, so the identity check means nothing until the version check has passed. The other side's
version comes from the `version` in its header, which `sync()` reads anyway.

#### v2 → v3 is a hard cut, on purpose

**Scoping decision**: there are no third-party installations today, so there is nobody to protect from
a rewrite. The jump to v3 is released in one go, without the expand/contract manoeuvre that would be
needed with deployed consumers.

What that rules out and what it does not:

| | Status | Why |
| --- | --- | --- |
| Two-step release (`peer` and `peerId` at once) | **dropped** | it protects other people's old engines; there are none |
| `PeerMark.version` | **deferred** | its job was deciding when to contract; with no contraction it has no job |
| Migration map (§7.9) | **kept** | our own v2 folders carry real data and the map costs ten lines |
| Version check | **kept** | see below — it is the cheapest piece and the one that prevents the most |

**The version check stays even with no third parties**, and it is the piece not to trim. Without it,
the failure is not "I cannot sync": it is the silent corruption above, `node.id = undefined` and
`peers[undefined]` as a key. Turning that into an explicit error is worth it between two of your own
machines mid-upgrade, which is a state you pass through anyway.

*When it reopens*: as soon as there is a second installation you do not control — another consumer, or
a machine you cannot upgrade at the same time as the rest — `PeerMark.version` and the two-step
release become necessary again. Written here so it does not have to be derived twice.

#### Migrate or reinitialise

With a single user there is an alternative to the map worth keeping in mind: **delete `.vfs` and
reinitialise**. It is free and it converges — the folders end up virgin, adopt a `syncId` on the first
sync and the content is rescanned.

What it costs: the log is lost, so the first sync afterwards cannot prove ancestry and every
divergence reads as a real conflict — extra conflict copies, not data loss. And the `uuid`s change, so
entries pair through the path fallback ([merge.ts:104](../src/merge.ts#L104)), which works for what is
live.

**Recommendation: the map.** It costs ten lines, preserves history and is what the spec will have to
describe for the second implementation anyway. Reinitialising remains the emergency exit if something
about the map goes wrong.

### 7.12 Tests

- The three benign rows of §7.4 and the two error ones, one each.
- `adopt` with the reported `syncId` merges; with a different one, it fails again.
- `peer-collision` cannot be authorised with `adopt`.
- `syncMesh` with one conflicting edge syncs the rest and reports that one.
- `syncDryRun` reports the case **without writing anything** in either folder.
- **Migration, the test that protects the mesh**: two `version: 2` folders with the same `storeId` and
  a populated `peers` migrate, sync and do **not** give `foreign-mesh`. It is the regression that
  justifies seeding rather than minting.
- Migration: `version: 2` with `peers` empty → `syncId: null`, and it adopts on its first sync.
- Migration: two v2 meshes with different `storeId` → `foreign-mesh` after migrating.
- Mixed `commits`: a log with `peer` (v2) and `peerId` (v3) rows is read whole with no rows lost.
- Format round trip: a v3 `vfs.json` is re-read identical, with `peerId` in the header and entries.

## 8. Parallel track — Spec and conformance suite (§4)

It blocks nothing above and should not wait until there are two codebases to reconcile.

This plan adds two rows to the table in §4 of the requirements document and **voids one**:

| Area | What has to match exactly |
| --- | --- |
| **Absence** (phase 1) | what counts as evidence of deletion: current exclusion rules + "observed on disk" |
| **Pairing** (phase 6) | the five rows of §7.4, the minting of the `syncId` and when it is written |
| ~~`storeId`: adoption of the lexicographically smaller~~ | **obsolete**: `storeId` disappears; the smaller rule moves to `syncId` and only after the guard |

And one row that was already there gets cheaper: **Identity** becomes `peerId` + `syncId`, two fields
with one rule each, instead of three fields with overlapping semantics.

The two new rows are exactly the kind of rule that has to be pinned down in writing, and for the same
reason: **a divergence between TypeScript and Rust would not raise an error**. In the first, the two
implementations would infer different tombstones from the same folder — silent deletion. In the
second, one would merge foreign meshes where the other stops — and that has no way back either.

## 10. Open questions

1. **Signature of `materialize`**: does it receive the whole entry or just the path? The entry gives
   size and kind, which is exactly what a mobile policy wants to look at ("nothing above 10 MB"). It
   leans towards the entry on its own, but the asymmetry with `ignore` — which receives paths — has to
   be accepted explicitly.
2. **Source for `materialize()`**: explicit peer or a provider held by the node (§2.4).
3. **Already-corrupted state**: a peer that starts out with tombstones caused by this bug is not fixed
   by phase 1, which only prevents new ones. Is a recovery path needed, or is it enough that the mesh
   has no users with exclusion rules in production yet? It depends on how many real installations
   there are; worth answering before publishing the fix.
4. **Backend identity for the fast path** (§5): what "the same backend" means such that two different
   Drive accounts do not produce a false positive.
5. **Remedy for `peer-collision`** (§7.4): the library reports, but the fix is a write to one of the
   two folders and which one has to be decided. And it depends on the cause, which the library cannot
   determine: regenerating the `peerId` fixes a copied `.vfs` and **fixes nothing** if the caller
   imposes the id, because it would impose it again on the next `open()`. What is coherent with §7.5
   is to expose the operation (`node.reidentify()`) and let the caller decide. Still to be confirmed.
6. **Expiry of `version: 2`**: is it read indefinitely, or is there a version from which reading a v2
   is an error requiring explicit migration? It mostly affects how long the `?? row.peer` in the log
   reader lives, which is the lazy half of the migration.

*Closed by scope*: the cross-version upgrade policy and `PeerMark.version` (§7.9). There are no
third-party installations, so v2 → v3 is a hard cut. It reopens with the second installation that is
not under your control.
