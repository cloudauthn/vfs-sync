## 1. The rename hits the two digests differently

The plan treats `peer` → `peerId` as one rename across `vfs.json`, `VFSEntry`, `LogRow` and
`MergeSide`. In terms of *digests* it is two changes, and they behave in opposite ways:

| Digest | Under the rename | Why |
| --- | --- | --- |
| `log.digest` — XOR of op ids | **unchanged** | `opId` hashes **values**, joined by `\|`: `[row.peer, row.uuid, row.at, row.type, row.path, row.hash]` ([log.ts:22](../src/log.ts#L22)). No key name enters the hash |
| `state` — hash of the canonical entries | **changes for every folder** | `canonicalEntry` emits the key name, and `canonicalJSON` hashes the object ([vfs-file.ts:43](../src/vfs-file.ts#L43)) |

The first is a gift and makes the lazy log migration genuinely one line: op ids survive the rename,
so history stays comparable across the cut, and a v2 row read as v3 is the same operation with the
same identity. `canonicalRow` does write the key name, so segments written after the cut differ in
bytes — but they are only ever appended to, so the byte offsets the `peers` marks hold stay valid.

**The second is the real reason the version check cannot be trimmed**, and it is a better reason
than the one the plan gives (`node.id = undefined` and `peers[undefined]` as a key). Consider a v2
peer and a v3 peer with byte-identical trees:

- their `state` digests differ, because one wrote `peer` and the other `peerId`;
- their `log.digest` values **match**, because op ids are name-independent.

So the fast path is skipped, a full merge runs, the merge finds nothing to do, and the next pass does
it all again. Not a crash and not corruption — **a mesh that never converges and never says why**.
`syncUntilStable` would burn `maxRounds` on every call, forever. That is a worse failure than the one
the plan describes, because nothing about it looks like an error.

The version check turns it into one sentence. It stays.

## 2. `version` is written as a literal, not read from the file

```ts
const header: Array<[string, unknown]> = [
  ['version', 2],                                  // vfs-file.ts:99
```

`encodeVFSFile` hardcodes the number rather than writing `file.version`. Harmless while there is one
version; the moment there are two it means a migrated v3 file is written back out claiming to be v2,
and the next reader migrates it again. It has to read from the file, and `emptyFile` becomes the one
place the current version is minted.

## 3. Two constructor signatures carry `storeId`

```ts
emptyFile(peer: string, storeId: string, segment: number, text: string[])   // vfs-file.ts:145
store.init(options: { peer?: string; storeId?: string })                    // store.ts:137
```

Both are public. `storeId` comes out of each and `syncId: null` takes its place in the shape
`emptyFile` produces — the plan's §7.3 argument for an explicit `null` rather than an absent key
lands here, and `encodeVFSFile`'s fixed key list is what makes it free.

## 4. What is being built

Unchanged from the plan §7.2–§7.9, so this is a summary rather than a re-derivation:

- **`peerId`** identifies the node — born in `init()`, never converges. **`syncId`** identifies the
  group — `null` until the first sync, then minted once and given to both files in `close()`
  ([sync.ts:624](../src/sync.ts#L624)), where the two headers are already written in one pass.
  **`storeId` is removed**, and on migration it seeds the `syncId`.
- **The guard**, in `sync()` after both files are read and before config convergence: identical
  `peerId` is `peer-collision`; two non-null different `syncId`s are `foreign-mesh`. The other three
  combinations are ordinary and one of them (`g-3f9c` against `null`) is how a folder joins a group.
- **`PairingError`** carries the code and both sides' data — `peerId`, `syncId`, entry count, log
  segment and digest — so a caller can present "1,240 files against 890" instead of two uuids.
- **Authorisation is specific**: `sync(a, b, { adopt: { syncId } })`, the same "prove you knew the
  prior state" idiom as `writeIf`. `peer-collision` is not authorisable.
- **Migration**: a declarative map applied in sequence, `version` becomes `2 | 3`. `vfs.json`
  migrates eagerly on read; the log migrates in the reader (`row.peerId ?? row.peer`), because closed
  segments are immutable and cached forever.
- **The version check runs before the identity check**, because reading `peerId` and `syncId` means
  nothing until you know which version wrote them.

### 4.1 One refinement: `node.id` keeps its name

The plan's §7.2 lists `node.id` among the things to rename. I would leave it.

The ambiguity being fixed is in the **file format** — a field called `peer` that has to be told apart
from a field called `storeId`. On the node object there is no such ambiguity, and there is about to
be even less of one: once `storeId` is gone, `node.id` is the only id a node has. Renaming it touches
every test and both consumers to remove a confusion that no longer exists at that layer.

`VFSHeader.peer` → `peerId`, `VFSEntry.peer` → `peerId`, `LogRow.peer` → `peerId`,
`MergeSide.peer` → `peerId`. `node.id` stays.

### 4.2 Extract the config convergence first

[sync.ts:127-135](../src/sync.ts#L127-L135) and [:339-346](../src/sync.ts#L339-L346) are the same
rules written twice, one for `sync()` and one for `syncDryRun()`. Adding the guard without extracting
them leaves three copies that have to agree, and the third is the one that decides whether folders
merge. This comes before anything else in the phase.

### 4.3 `syncMesh` has to survive a bad edge

```ts
for (const edge of edges) results.push({ edge, result: await sync(edge.a, edge.b, options) });
```

One throw aborts the loop and loses every result already collected. In a mesh of five folders with
one badly paired, none of them would sync. `MeshResult` gains `result | error` and the loop
continues; `syncUntilStable` inherits it, and needs one decision of its own: **an edge that errored
does not count as "changed"**, or the fixed-point loop would never terminate.

That last point is not in the plan and is a real trap — the loop stops when nothing changed, and an
edge that throws on every pass would otherwise look like progress that never lands.

## 5. Tests

The plan's §7.12 list stands. Two additions from §1 of this document:

- **A v2 and a v3 file are not merged silently.** Two folders whose only difference is the format
  produce `version-unreconcilable`, not a sync that runs forever. This is the regression that
  protects the argument in §1, and it is worth writing as a *loop* test — call `syncUntilStable` and
  assert it stops — rather than only asserting the error.
- **Op ids survive the migration.** A row written as v2 and the same row written as v3 have the same
  `op`. That is what keeps history comparable across the cut, and it is a property of `opId`'s
  implementation that nothing currently pins.

**Existing tests to expect churn in**: seven files touch `storeId` — `store.test.ts`,

### On decision 1

§4.1 argued that the ambiguity being fixed lives in the file format and not on the node object. The
call is to rename everywhere anyway: one name for the concept at every layer. The cost is a wide
diff — every test constructs nodes and reads `node.id`, and both consumers use it — and that cost is
paid once, now, rather than left as a seam where two names for one thing meet.

It also removes the thing §4.1 was implicitly relying on: that a reader would know `node.id` means
the peer and not the group. That is true today only because you know `storeId` was never used for
anything.

Scope of the rename, complete:

| From | To |
| --- | --- |
| `VFSHeader.peer` | `peerId` |
| `VFSEntry.peer` | `peerId` |
| `LogRow.peer` | `peerId` |
| `MergeSide.peer` | `peerId` |
| `VFSNode.id` | `VFSNode.peerId` |
| `VFSNodeOptions.id` | unchanged — it is the *option*, and §7.4 of the plan wants its documentation to say it is normally omitted |

`PendingConflict.peer` ([types.ts:283](../src/types.ts#L283)) is in the same family and is renamed
with them; it reports which peer wrote the losing version, which is a `peerId` by any other name.

### On decision 4

`?? row.peer` in the log reader is a permanent one-line cost. Worth stating why that is not laziness:
closed log segments are immutable and cached forever, so the alternative is rewriting history to
change a key name — which breaks the invariant the cache rests on, for no gain. The general rule the
plan draws from this stands: **what is mutable migrates eagerly, what is immutable migrates in the
reader.**

## 10. Order of work

The extraction comes first because the guard has to land in one place, not three (§4.2). The rename
comes early because everything after it would otherwise be written twice.

1. Extract the config convergence shared by `sync()` and `syncDryRun()`
2. `peer` → `peerId` across the format and `node.id` → `node.peerId`, no behaviour change
3. `version: 2 | 3`, `syncId`, `storeId` removed; `emptyFile`, `encodeVFSFile`, `store.init`
4. The migration map, eager for `vfs.json` and lazy in `parseRows`
5. `close()` mints and writes the `syncId`
6. The version check, then the guard, then `PairingError` and `adopt`
7. `syncMesh` collects per edge; `syncUntilStable` does not count an errored edge as progress
8. Explorer, then docs

Steps 2 and 3 are format changes with no new behaviour, so the suite should stay green through both
— a rename that breaks a test means the test was pinning something else.

## 12. Two decisions the plan left implicit

### 12.1 What `adopt` has to name

The plan says `sync(a, b, { adopt: { syncId } })` with "the one the error reported", and the error
reports two. Three readings were available: the survivor (the smaller), the one being abandoned, or
either.

**Implemented: either of the two.** The guard's only job is *whether to merge* (§7.5 of the plan) —
it is not choosing a winner, so making the caller compute which id survives would be asking them to
express a decision the guard does not make. Naming either one proves what the idiom is there to
prove: that the caller saw *this* collision and not a different one. A stale token from another
pairing still fails, which is the property that matters, and there is a test for it.

Once authorised the merge is ordinary and the smaller `syncId` survives — the caller's choice of
token does not influence that.

### 12.2 `syncUntilStable` needed a termination rule

§4.3 flagged this and it turned out to be exactly as sharp as it looked. `syncMesh` collecting
errors instead of throwing means a failing edge appears in every round, and the fixed-point loop
stops when *nothing changed*. An error is not a change, so `result?.changed` treats a failing edge
as quiet and the loop settles instead of burning `maxRounds` on a failure that repeats identically.

The test asserts the round count, not just the error: a version of this that "works" by throwing
would pass an error-only assertion.

## 13. What the rename cost, and the one thing it did not

Decision 1 was the wide one — 30 files. Worth recording what it actually broke, because the answer
is narrow and specific: **five tests, all of them pinning the wire format.** The header key written
as a string literal (`['peer', file.peerId]`) was the single point where the type system could not
help, and those five tests are what caught it. Everything else was compile errors, which is the
outcome you want from a rename of typed fields.

Two traps that a regex-driven rename finds and a careful reading might not:

- **`readPeerLog(peer: VFSNode)`** — a parameter *annotation* matching `peer:`. Renamed to `peerId`
  while its body still said `peer`. Compile error, caught immediately, but it is the shape of the
  mistake that would slip through in a language without one.
- **`model.peer(key)`** in the demo — a lookup *method*, not a field. `.peer` → `.peerId` renamed the
  call site into a method that does not exist. Same rescue.

**And the thing it did not cost**: the log digest, exactly as §1 predicted. `opId` hashes values
joined by `|`, so op ids are name-independent and closed segments stay comparable across the cut.
There is now a test pinning that (`keeps op ids stable across the rename`) — it was a property of
the implementation that nothing had ever asserted, and the entire lazy-migration strategy rests on
it.
