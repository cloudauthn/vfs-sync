## 0. What was asked for

> A draft of the sync, which can then be executed. The draft carries the possible conflicts, and when
> you ask to apply what the draft describes, you hand it the decisions for those conflicts too. The UI
> handles that.

## 1. Most of it is already built, and nothing can execute it

`syncDryRun(a, b)` scans both folders without writing, runs the pairing guard, computes the merged
tree, **actually attempts every text merge** ([sync.ts:397](../src/sync.ts#L397) — the merged bytes are
computed and then thrown away), plans the exact file-system actions for each side, predicts the
transfers, and returns the digest both folders would land on.

So the draft exists. What does not exist is any way to *run* it. The caller looks at the preview and
then calls `sync()`, which **recomputes the whole thing from scratch** and may reach a different
answer, because the folders moved in between. The only bridge is `approveMerge`, a hook that receives
the same preview *inside* `sync()` and can veto — which is not draft-then-apply, it is one sync with a
human wedged in the middle, unable to say anything except no.

And the decisions themselves have no shape. The one channel is `resolveText`, a callback the engine
invokes mid-pass, for text only. A binary conflict cannot be decided at all before the fact: the copy
is always parked, and the caller resolves it afterwards with `node.resolve()`.

## 2. The seam is already in the code

`sync()` has exactly one line where planning ends and writing begins — everything above it is pure
computation over two scans, everything below touches disk:

```ts
const previewState = await stateDigest(target);   // sync.ts:243  <- the seam
...
await a.apply(target, chain(...));                // sync.ts:276  first write
```

Above the seam, `sync()` and `syncDryRun()` are **the same ninety lines twice**, and the preview
payload handed to `approveMerge` is a third copy of the same object literal. Nothing enforces that the
three agree. A dry run that predicts a sync the engine will not perform is not a bug anyone would
notice until it mattered.

Splitting at the seam is therefore not only what the consumer asked for. It deletes a duplication that
is one refactor away from lying.

## 3. Shape

```ts
const draft = await syncDraft(a, b, options);     // nothing is written
draft.changed        // false when the two folders already agree
draft.conflicts      // what needs deciding, with both versions and why it did not merge
draft.actions        // literal writes/deletes/renames per side
draft.transferred    // how many files would move, each way
draft.state          // the digest both would land on

const result = await draft.apply({ decisions });  // this writes
```

`sync(a, b, options)` stays exactly as it is, and becomes sugar for
`(await syncDraft(a, b, options)).apply()` — same signature, same result, one implementation
underneath instead of two.

**The draft is an in-memory object, not a document.** It holds the merged bytes and both node handles,
so it cannot be serialised or sent anywhere. What crosses a boundary is `conflicts` and `actions`,
which are plain data, and what comes back is `decisions`, also plain data. Worth stating because the
name invites the opposite assumption.

## 4. Decisions are data, and a decision mints a version with two parents

```ts
type Decision = 'a' | 'b' | Uint8Array;
await draft.apply({ decisions: { [uuid]: decision } });
```

**`'a' | 'b'`, not `'mine' | 'theirs'`.** A draft is between two peers and belongs to neither;
`node.resolve()` keeps `'mine' | 'theirs'` because it is local to one node and there the words mean
something.

The part that is not obvious: **choosing a side cannot mean adopting that side's entry.** Say A won by
last-writer-wins and the user picks B. B's version carries an older `updated`, so a third peer that
meets this mesh tomorrow re-runs the same comparison, reaches the same conclusion as the engine did,
and puts A's version back. The decision would silently undo itself.

So a decision mints a **new version**: the chosen content, `updated` above both, and **two parents** —
`prev` the winner's hash, `prev2` the loser's. That is precisely what the automatic text merge already
does, for exactly this reason, and there is already a test pinning it (*"record both parents, so a
third peer does not re-raise them"*). A decision is a merge performed by a person, and it has to leave
the same trace as one performed by `diff3`.

Handing back bytes is the same operation with content the caller supplied, which is also what makes
"the user edited both versions together in a three-column view" expressible.

## 5. A partially decided draft is the normal case

The user resolves two of five conflicts and gets on with their day. Undecided conflicts fall through
to exactly today's behaviour: last-writer-wins, the loser parked as a copy, a pending decision left in
`vfs.json`. Nothing about `apply()` requires a complete decision set, and nothing warns about an
incomplete one — a sync that refuses to proceed until every conflict is settled would be worse than the
one we have.

## 6. Staleness: check what you are about to touch, not the folder

Between drafting and applying, a user can save a file. Writing a plan built on a picture that has
moved is how a sync tool eats an edit.

The check is **not** a second scan. A full re-scan on every apply would double the cost of every sync
in the mesh, and on Drive the scan is most of what a sync costs. What the apply verifies is the paths
its own actions name: `mtime` and `size` against what the draft recorded, which is O(actions) stats
instead of O(tree). A file that changed somewhere the draft was not going to touch does not invalidate
anything — the next pass will pick it up, which is what the next pass is for.

A mismatch throws `StaleDraftError` carrying the paths that moved, so a UI can re-draft and show the
user what changed under them rather than a spinner and a shrug.

`sync()` passes `{ verify: false }`, because it applies a draft it made three microseconds earlier and
there is nothing to have changed in between.

## 7. What goes, what stays

| | |
| --- | --- |
| `approveMerge` | **Removed.** The draft is the approval, and a hook whose only vocabulary is "no" cannot express what the consumer needs. |
| `resolveText` | **Kept**, and re-documented as the *headless* path: a rule that resolves without a person (always take the longer one, always take the server's). Interactive resolution is decisions now. |
| `node.resolve()` | **Kept.** Copies parked by a background sync — the phone syncing at 4am with nobody watching — still have to be resolvable after the fact. This is also why `reason` on the durable copy still matters, though less. |
| `syncDryRun()` | **Becomes `syncDraft()`.** A thin deprecated alias is possible but pointless: no third-party consumers, and the plan already treats v2 → v3 as a hard cut. |
| `syncMesh` / `syncUntilStable` | Unchanged. They drive `sync()` per edge, which still exists. |

## 8. What this is not

- **Not a transaction.** `apply()` writes content, then logs, then the two headers, in that order, and
  an interruption leaves the same recoverable state it leaves today. A draft does not make two folders
  atomic and nothing here pretends otherwise.
- **Not multi-peer.** A draft is one edge, like a sync. Deciding a conflict across three peers at once
  is a different problem and nobody has it yet.
- **Not a queue.** Drafts are not stored, not resumable, and do not survive a reload. Re-draft.

## 9. Tests

- A draft writes nothing: both folders byte-identical afterwards, including `vfs.json` and the log.
- `sync(a, b)` and `draft.apply()` reach the same state, the same conflicts, the same transfers — the
  test that keeps the sugar honest.
- A decision for `'b'` when A won: B's content lands on both sides, and the entry carries both hashes
  as parents. Then a third peer holding A's version syncs and **does not re-raise it** — the same
  property the auto-merge has, driven by the same fixture.
- A decision handing back bytes: that content lands, with both parents.
- An undecided conflict in a partly decided draft still parks its copy.
- Editing a file the draft was going to write, then applying: `StaleDraftError` naming that path, and
  **both folders untouched**.
- Editing a file the draft was *not* going to touch: the apply proceeds.
- A `PairingError` surfaces from `syncDraft()`, before anything is written — it already does, and the
  split must not lose it.

## 10. Documentation

`docs/api.md`: `syncDraft`/`apply`/`decisions` replacing the `syncDryRun` section, with `sync()`
described as the one-shot form rather than as the primary. `docs/conflicts.md`: the decision flow
becomes the main story and `node.resolve()` the after-the-fact one. `README.md` if the headline
example changes — it should, because "look, then decide, then apply" is the honest shape of this
library.

## 11. Open questions

1. **`draft.apply()` versus `VFSNode.apply()`.** Two different objects, two different meanings — the
   node's takes a target tree and content, the draft's takes decisions. Live with the collision, or
   name one of them something else?
2. **Does a decision need to travel as *why*?** A version minted by a person and one minted by `diff3`
   are indistinguishable in the log. Recording which is which is cheap, and it is the same question as
   `'block'` (§15 of the phase 4 session) one layer up. Deliberately left open until the flow exists.

## 13. The shape, revised

```ts
const result = await sync(a, b);
if (result.pending.length > 0) {
  // nothing was written. result.pending is what the UI shows.
  const decisions = await ui.decide(result.pending);
  await sync(a, b, { decisions });
}

await sync(a, b, { dryRun: true });   // plans and reports, never writes
```

One function, one return type, one seam. `syncDryRun()` collapses into `sync(a, b, { dryRun: true })`
and stops existing — with it goes the ninety-line duplicate of §2 and the third copy of the preview
literal inside `approveMerge`.

`decisions` is an **array**, mirroring `pending` one for one, because that is the shape a form
produces and the shape that survives a round trip through a UI:

```ts
type Decision = { uuid: string; choice: 'a' | 'b' | Uint8Array };
```

§4 above still holds in full and is the load-bearing part of this session: a decision **mints a new
version with two parents**, or it undoes itself the next time a third peer does the arithmetic.

## 14. "Conflict" is too broad to abort on. The word is *pending*

Not everything the merge reports as a conflict needs a person, and aborting on all of them would stop
a sync for things the engine settled by itself:

| Reported | Needs a person? |
| --- | --- |
| a text conflict the three-way merge settled | **no** — it is resolved, and the report survives only so the caller can see it happened |
| `location` — the same file renamed differently on each side | **no** — one path wins, deterministically, and no content is at risk |
| `content` — two different versions of the same file | **yes** |
| `delete-edit` — one side deleted, the other edited | **yes**, and it is the sharpest of the three |
| `kind` — a file on one side, a folder on the other | **yes** |

So the result carries both: `conflicts` (everything that diverged, as today) and **`pending`** (the
subset a person has to settle). `sync()` aborts on `pending`, never on `conflicts`.

## 15. The consequence: a peer with nobody watching stops converging

This is the price of the rule and it has to be stated, not discovered.

Today a conflict never blocks a sync: the engine picks the newer version, parks the loser as a copy,
and **everything else keeps flowing**. Under the new rule, one disputed `gamelist.xml` between the
laptop and the NAS aborts that edge — and the 900 photos that have nothing to do with it do not
travel either, on every pass, until a human resolves the one file. The phone syncing at 4am has no
human, so it never resolves anything and never converges again.

The escape hatch is one option, and naming it is the whole point:

```ts
await sync(a, b, { onConflict: 'park' });   // today's behaviour: pick a winner, park the loser
```

Default `'abort'`. **The abort path is for an edge with a person on it; the park path is for an edge
without one.** A background sync passes `park` and keeps the mesh converging; the copies it leaves
behind are pending conflicts in `vfs.json`, which the UI resolves later through `node.resolve()` — the
mechanism that already exists and is exactly what it is for.

That also settles where `'block'` matters (§15 of the phase 4 session): on the parked path, which is
the one nobody was watching.

## 16. What atomic can and cannot mean here

What is being asked for is achievable and worth having: **the plan is complete before the first byte
is written, and no write happens at all when the plan needs a human.** Every conflict is known before
the seam, so the abort costs two scans and touches nothing.

What it cannot mean is a transaction. `apply` writes content, then log rows, then the two headers, in
that order, across two folders that may be on different machines. A network drop mid-write leaves the
partial state it leaves today, and the ordering is designed so the next pass heals it. No API shape
changes that, and this session does not claim to.

## 17. What this deletes from the session above

- **The draft object** (§3) — there is none. Nothing is held between calls.
- **`StaleDraftError` and verify-what-you-touch** (§6) — with no plan carried across calls there is
  nothing to go stale. The second `sync()` re-plans from scratch.
- **The `draft.apply()` naming collision** (§11.1) — moot.

One risk survives the simplification: a decision is made about a dispute, and the dispute changes
before the second `sync()` lands. The decision is keyed by `uuid`, so it would apply to a version the
user never saw. Cheap fix, and it stays optional: a decision may carry the two hashes it was made
about — the UI already received them in the report — and the engine ignores any decision whose hashes
no longer match, leaving that conflict pending and reporting it again.

## 18. Open question

`sync(a, b, options)` as a free function, or `a.sync(b, options)` as a method on the node? The request
was written as `.sync({ decisions })`, which reads like a method. The free function is symmetric —
neither peer owns the operation — and that symmetry is real: `sync` drives both sides equally. A
method would put one of them in charge in a way the engine does not.

## 20. The surface, settled

```ts
export interface SyncOptions {
  /**
   * What to do about a conflict a person has to settle.
   *
   * `'abort'` (default) writes nothing at all and reports them in `pending`.
   * `'park'` is the old behaviour — newer version wins, loser kept as a copy —
   * and it is what an edge with nobody on it wants, because an aborting sync
   * that nobody can unblock never converges again.
   */
  conflictBehavior?: 'abort' | 'park';
  /** Settles a reported conflict. Ignored when it names a dispute that no longer exists. */
  decisions?: Array<{ uuid: string; choice: 'a' | 'b' | Uint8Array }>;
  /** Plans and reports without writing either folder. */
  dryRun?: boolean;
  // ... conflictCopies, conflictName, now, heldAt, autoMerge, archives, resolveText, adopt
}
```

**`onConflict` was rejected as a name**: the `on` prefix reads as a callback, and everything else in
these options that starts that way *is* one. `conflictBehavior` says it is a policy.

It sits next to the option it is not: `conflictCopies` decides whether the loser is kept once a
conflict is being parked; `conflictBehavior` decides whether parking happens at all.
`{ conflictBehavior: 'park', conflictCopies: false }` is the existing "pick a winner and drop the
loser silently", unchanged.

**`sync(a, b, options)` stays a free function.** The symmetry is not cosmetic: `sync` drives both
sides, commits both, writes both headers in one pass. `a.sync(b)` would put one peer in charge of an
operation in which neither is.

## 22. No `park`, and therefore no option at all

The option of §20 does not ship. A conflict a person has to settle aborts the sync, and that is the
whole rule. Fewer things to explain, one path to specify for the second implementation, and one shape
to validate against a real consumer before deciding it was right.

**It is cheap to revisit**, which is what makes this the right way round: adding `conflictBehavior`
later, defaulting to `'abort'`, is additive — no caller changes, nothing breaks. Removing an option
that turned out to be a mistake is not. So the ordering is: ship the strict thing, learn, and widen
only if the mesh actually needs it.

## 23. What this leaves dormant, on purpose

Conflict copies are how a conflict has been *survived* until now: the loser parked beside the winner
so nothing is destroyed. With nothing parking, the machinery around them stops being reached from
`sync()`:

| | Status |
| --- | --- |
| `conflictCopy()` inside the merge | **still runs** — the merge describes the copy, and that description is most of what `pending` shows the user |
| copies actually written to disk | never, from a sync — the abort happens before the seam |
| `node.conflicts()` | answers empty, because nothing parks any more |
| `node.resolve()` | reachable, unused — it resolves copies that this version no longer creates |
| `conflictCopies` / `conflictName` options | inert until something parks again |

None of it is deleted. It is tested, it is correct, and it is exactly what a future
`decisions: [{ uuid, choice: 'later' }]` would need — the per-conflict version of `park`, decided by
the person instead of by a flag, which is a better shape than the option this extension is dropping.

## 24. The consequence, accepted rather than mitigated (superseded by §29)

An edge with nobody on it does not converge past a conflict. The phone syncing at 4am aborts, and
aborts again tomorrow, and the files that have nothing to do with the dispute wait with it. That is
known, it is the price of validating the strict rule first, and it is one option away from being
fixed on the day it hurts.

## 25. The seam, and the duplication it deleted

`sync()` is now `planSync()` + `applyPlan()`, split exactly where §2 said the line already was.
`syncDryRun()` is gone; `sync(a, b, { dryRun: true })` returns the plan at the seam. One result type
(`SyncResult`) replaces the two, so a preview and a sync can no longer describe different work.

`planSync` takes one parameter the two paths do not share: whether to persist the scan. A real pass
commits, a dry run scans and carries the rows a commit *would* have appended into the history, where
they answer the same questions. That is the only asymmetry left, and it is the reason `dryRun` is a
parameter instead of a second function.

## 26. `pending` is a classification, and `settled` is what makes it possible

`ConflictReport.settled` is set by the auto-merge when it produces content both sides adopt. Without
it, "a conflict occurred" and "a conflict is waiting for a person" are the same list, and the abort
rule would stop syncs over merges that already worked.

`needsDeciding()` is then two lines and the whole policy: not settled, and not `location`.

## 27. A decision mints a version with two parents

`applyDecisions()` runs after the auto-merge, over the same `merge` object, and mints the chosen
version exactly as `autoMergeText` mints a merged one: `updated` above both, `prev` the winner's
hash, `prev2` the loser's, a log row, and the parked copy removed.

The test that matters is *"mint a version with both parents, so nobody re-decides it later"*: a third
peer holding the losing version syncs afterwards and adopts the decision instead of re-raising it.
Without `prev2` that peer redoes the engine's arithmetic, reaches the engine's original answer, and
undoes the user's choice days later on a machine nobody is looking at.

Hash pinning landed as planned and has its own test: a decision naming a dispute that moved on is
ignored and reported again rather than applied to a version the user never saw.

## 28. What the abort rule actually cost, measured

Implementing it turned **28 tests red**, and none of them was a bug in the refactor. They were one
fact: nothing could park a conflict any more, so nothing could get past one.

| | |
| --- | --- |
| 13 | convergence — random histories no longer reach one state, because `syncUntilStable` stops at the first conflict |
| 2 | chains — "settles a conflict identically across the whole chain", "does not re-raise a settled conflict" |
| 13 | conflict copies, `node.resolve()`, held copies, cold archives |

The 13 convergence failures are the finding. It is not that an unattended peer stops converging
(§24); it is that **a mesh cannot converge through a conflict at all**, and the suite proving the
central property of the design cannot run.

## 29. So `park` came back — as a decision, not as an option

Reported, and the call was to keep `abort` as the only behaviour and rewrite the tests. That is what
happened, and rewriting them needed one addition: **`choice: 'both'`**, which keeps the winner and
parks the loser.

This is the per-conflict form §23 predicted, and it is better than the option this session dropped:
the answer comes from the person, per file, instead of from a flag that decides for every file in
advance. It is also the only path that now reaches the parking machinery, so nothing is dormant after
all — `node.conflicts()` and `node.resolve()` are reached again, by a user who said "keep both".

Two test helpers carry the new shape: `settle(a, b, choice)` — sync, answer whatever came back,
sync again — and `stabilise(edges)` for a mesh. The convergence suite now proves something stronger
than it did: the mesh converges **when decisions are supplied**, which is the workflow, rather than
when the engine decides silently.

## 30. `approveMerge` survived, against §7

§7 removed it because the draft was the approval. There is no draft any more, and without one
`approveMerge` is the only way to confirm-then-write in a **single pass**: the `dryRun` route costs
two, and the second one is another scan of both folders — which on Drive is most of what a sync
costs.

It is now fed the same `SyncResult` everything else uses, so the third copy of the preview literal
died with the duplication. It runs only when nothing is pending: there is nothing to approve about a
pass that is not going to write.

## 31. A dry run's `state` is a prediction with one caveat

`actions`, `transferred` and `pending` match the real pass exactly. `state` matches **only once both
sides have recorded their edits** — a version is stamped when it is recorded, and a dry run records
nothing, so the timestamps it invents for uncommitted edits are not the ones the real pass will
invent. Verified both ways and pinned by a test.

Not worth fixing: the fix is for a dry run to commit, which trades a documented caveat about a digest
nobody eyeballs for a "dry run" that writes.

## 32. Left out on purpose

- **The explorer** still confirms through `approveMerge` and does not show `pending`. It compiles and
  syncs; it just does not offer the new flow yet. That is app work, and it is the first honest test

- **`'block'` on the durable copy** (§15 of the phase 4 session) is still open, and this session
  moved where it matters: with a person in front of it, nothing is parked and `pending` carries the
  reason; the durable `reason` only matters for what `'both'` leaves behind.

# Extension — 2026-08-13 04h20

**Summary**: the catalogue asked for — every conflict the engine can raise, the data each one needs
before anyone can decide it, and the answers that are legal for it. Proposes one callback across both
levels (§35), and records what is missing from today's payloads (§38). Design only; no code.

## 34. Why one callback over two levels

A pairing refusal (`foreign-mesh`) and a file conflict (`content`) are different in every mechanical
way: the first is **one per pass** and settled before the merge is even computed, the second is **N
per pass** and settled after. Nothing forces them into one hook.

What does is the caller's side of it. Both are *"the engine stopped, and only a person can say what
happens next"*, both must be answered before anything is written, and both abort the pass when the
answer does not come. A consumer that has to learn two vocabularies for that has to learn two.

So: one callback, one discriminator, two cardinalities.

```ts
await sync(a, b, {
  decide: async ({ reason, ctxA, ctxB }) => {
    if (reason === 'foreign-mesh') return { action: 'adopt', wins: 'a' };
    if (reason === 'content') return { action: 'take', wins: 'b' };
    return null;            // no answer for this one — the pass writes nothing
  },
});
```

**Returning nothing aborts everything.** Not this conflict — the pass. That is the rule already in
place and the callback inherits it: all of them answered, or none of it happens.

**`wins: 'a' | 'b'`, not the context object.** The sketch passed `ctxA` back, which reads well and
works in one process, but a decision has to survive a trip through a UI — the same answers arrive as
`decisions` data today. A side is a string; an object is not.

## 35. The catalogue

### Level 1 — the two folders, before any file is looked at

One of these at most, per pass, and it is asked before the merge is computed: a `foreign-mesh` means
the merge must not happen at all.

| `reason` | What happened | Data needed to decide | Legal answers |
| --- | --- | --- | --- |
| `foreign-mesh` | Two different `syncId`s: separate meshes | both `syncId`s, live entry counts (*"1,240 files against 890"*), `peerId`s, log digests | `{ action: 'adopt', wins }` — both take that side's `syncId` · nothing → abort |
| `peer-collision` | One `peerId` on two folders: a copied `.vfs`, or a non-unique `options.id` | both sides' entry counts and log positions; whether either has ever synced | `{ action: 'reidentify', wins }` — the loser mints a fresh id · nothing → abort |
| `version-unreconcilable` | `vfs.json` formats that cannot be read as one | both `version` numbers, entry counts | `{ action: 'override', wins }` — that side's format is authoritative and the other migrates · nothing → abort |

`adopt: { syncId }` is today's answer to the first, as data. The second has a remedy that exists and
is unreachable from `sync()`: `node.reidentify()`. The third has none — `override` would mean writing
a migration, and until that exists the only honest answer is to abort.

### Level 2 — one file, after the merge and the auto-merges

| `reason` | What happened | Data needed to decide | Legal answers |
| --- | --- | --- | --- |
| `content` | Two versions, neither descended from the other | per side: `path`, `hash`, `size`, `updated`, `peerId`, and **whether the bytes can be read here**; plus `base` when an ancestor was found, and `textReason` when a merge was tried and refused | `take` (`wins`) · `both` · `content` (bytes the caller composed) |
| `delete-edit` | One side deleted, the other edited | which side is the deletion, when and by whom; the surviving version's `size`/`updated`; whether its bytes are here | `take` (`wins`) · `both` — resurrect *and* keep a copy · `content` |
| `kind` | A file on one side, a directory on the other, one path | both `kind`s, the path, and **how many entries live under the directory** — moving it aside moves its subtree | `take` (`wins`) — the loser is renamed aside, never deleted |
| `location` | The same file renamed differently on each side | both paths, who moved when | `take` (`wins`) — which path it keeps |

`location` is **not** raised by default and stays out of `pending`: one path wins deterministically
and no content is at risk. It is in the catalogue because a consumer may want to be asked anyway, and
because leaving it undocumented invites the question every time.

### Not a conflict, and worth stating

- The same edit on both sides — one hash, nothing to decide.
- One version descended from the other — propagation, not divergence.
- A rename only one side made — the mover wins, no report.
- A text conflict the three-way merge settled — reported as history, never `pending`.

## 36. `textReason` is context, not a conflict

`block`, `size`, `eol`, `no-base`, `unreadable` describe why an eligible text conflict was not settled
by `diff3`. They are fields **on** a `content` conflict, and each one changes what a UI should offer:

| | What the user should be offered |
| --- | --- |
| `block` | a three-column view — there is a base, and the edits are real |
| `eol` | *"the line endings differ; normalise them and this merges itself"* — the only one that never fixes itself |
| `size` | pick a side; a merge was never going to happen |
| `no-base` | pick a side, and say why: nobody kept the ancestor |
| `unreadable` | fetch the content first, then decide |

## 37. What today's payloads are missing

Most of the data above already travels. Three gaps, all small:

1. **"Can I read this version here?"** — a UI cannot offer a diff for bytes this peer does not hold.
   Derivable from `held` and `mtime` today, which means every consumer derives it independently.
2. **Subtree size on a `kind` conflict** — "this renames 412 files" is the whole decision, and it is
   not in the report.
3. **The pairing payload has no `decide` shape at all** — it arrives as a thrown `PairingError`.
   Turning a throw into a callback is the actual work of level 1.

## 38. Open

- The name. `approveMerge` described a hook that could only say no; this one decides. `decide` is the
  proposal.
- Whether `decide` and `decisions` both live, and they should: the callback is for a UI that answers
  in the moment (one pass), the array for a UI that goes away and comes back (two).

# Extension — 2026-08-13 05h10

**Summary**: the catalogue of §35 becomes a contract and moves to
[`docs/conflicts.yaml`](../docs/conflicts.yaml), audited against every site that raises a conflict.
The audit found one case missing (§39) and two payloads that were wrong about their own shape (§40).

## 39. `path-collision` was missing, and it was hiding inside `content`

[`resolvePathCollisions`](../src/merge.ts#L420) reports two **different files** claiming one path —
two uuids, two histories — with `kind: 'content'`, the same word `mergeEntries` uses for two versions
of **one** file.

They are not the same question:

| | two versions of one file | two files on one path |
| --- | --- | --- |
| uuids | one, shared | two |
| At risk | one version overwrites the other | nothing — the loser is renamed aside |
| The question | which version survives | which one keeps the name |

A consumer switching on `reason` gets `content` for both and has to notice that `a.uuid !== b.uuid`
to tell them apart. The contract names it `path-collision`, and keeps `kind` separate for the case
where a directory is involved — not for symmetry, but because a directory losing its name takes its
whole subtree along, and `subtree` is the number that decides it.

## 40. Two payloads that were wrong

- **`version-unreconcilable` is raised per side**, so it fires when *both* folders are behind — two
  v2 folders meeting a v3 engine. The earlier sketch assumed a choice between two formats, and there
  is often no other side to pick. The payload now carries `engine` and a per-side `readable`, which
  is what tells "could be read, no migration covers it" from "cannot be read at all".
- **`peer-collision` needed `everSynced`.** Choosing which folder reidentifies is otherwise blind,
  and the one that has never synced is the safe one.

## 41. What the contract deliberately refuses to offer

`version-unreconcilable` admits only `abort`. `migrate` and `override` would both mean rewriting a
folder into another format, and no such migration exists — an action in a contract is a promise, and
that one cannot be kept today.

## 42. Two sections that are not conflicts, and are in the file anyway

`not_conflicts` (what the engine settles alone) and `not_decisions` (what it throws, because no answer
would be safe: content arriving at the wrong hash, resolving with bytes held on another peer,
dematerialising the last copy). Both are there so the catalogue can be read as complete rather than
as a list someone stopped writing.

# Extension — 2026-08-13 05h40

**Summary**: settles how a conflict reaches the caller. Without a decision callback, `sync()`
**throws** with every conflict it found; with one, the callback is asked about them one at a time.
This absorbs `PairingError`, gives the two levels one vocabulary, and is planned here — not written.

## 43. Why a throw, when `pending` already worked

`result.pending` can be ignored by accident, and what it looks like when it is ignored is the
problem: a pass that stopped for a conflict returns `applied: false` and writes nothing, which is
indistinguishable at a glance from a pass that had nothing to do. A caller who never reads `pending`
has a sync that silently stops working the first time two devices disagree.

An exception cannot be ignored by accident. For the one library in the stack whose job is to not lose
files, that asymmetry decides it.

Two things in the code already lean this way:

- **Level 1 has always thrown.** `PairingError` obliges the caller to look; `pending` asks them
  nicely. Two grammars for "the engine stopped and only a person can say what happens next".
- **`syncMesh` already treats a throwing edge correctly** ([sync.ts:1218](../src/sync.ts#L1218)): the
  error goes in `MeshResult.error`, the other edges still run, and `syncUntilStable` does not count it
  as progress. An unanswered conflict *is* an edge that made no progress. Nothing there changes.

## 44. The shape

```ts
try {
  await sync(a, b);                    // no callback: it applies, or it throws
} catch (error) {
  if (error instanceof ConflictError) error.conflicts;   // every one, in the contract's payload
}

await sync(a, b, { decide: async (conflict) => answer });   // callback: one at a time
```

**One error, one list, one payload.** `ConflictError.conflicts` is an array of the payloads in
[`docs/conflicts.yaml`](../docs/conflicts.yaml), and a pairing refusal is simply an array of one with
`level: 'pairing'`. `PairingError` is absorbed: it is public API and this is a breaking change, but
keeping both is keeping the double grammar this exists to remove, and the plan already treats v2 → v3
as a hard cut with no third-party consumers.

## 45. Three edges, settled

- **`dryRun` never throws.** Its job is to report, and it has to stay additive — delete the flag and
  nothing else changes. It returns the conflicts in the result, as it does now.
- **Declining is not throwing.** A `decide` that answers `abort` returns normally with
  `applied: false`. The throw is for *"nobody could decide"*; a person cancelling a dialog answered
  the question, and a cancelled sync is an outcome, not a failure.
- **`decisions` and `decide` both live.** The array is for a UI that goes away and comes back, the
  callback for one that answers in the moment. A conflict answered by both takes the array's answer:
  it is the one the user has already seen and confirmed, and the callback may be a policy that never
  saw it. Anything left unanswered by both throws.

## 46. What it costs elsewhere

- `sync()` returning now means it applied — except under `dryRun`, which is the only reason `applied`
  survives as a field.
- The test helpers (`settle`, `stabilise`) wrap the throw, which is what a consumer will do too, so
  they stop being test scaffolding and start being the reference for what a caller writes.
- Every test that asserts on `pending` becomes a `rejects.toThrow` or a catch. That diff is again the
  honest measure of how much behaviour this moves.

## 47. Order

1. `ConflictError`, absorbing `PairingError`, with the payload shape of the contract.
2. Throw on unanswered conflicts; `dryRun` exempt.
3. `decide`, level 2 first — it is the same code path `decisions` already goes through.
4. `decide` for level 1, which is the part that turns a `throw` site into a question.
5. `path-collision` split out of `content` in `ConflictKind` (open decision 1), and the payload
   fields `readable` and `subtree` (open decision 3).

The harness clock (open decision 6) comes before all of it: `delete-edit` is the sharpest conflict in
the catalogue and no test has ever produced one.
