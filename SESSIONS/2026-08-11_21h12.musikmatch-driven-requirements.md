# vfs-sync requirements arising from Musikmatch

**Date**: 2026-08-11 21:12
**Origin**: the design of Musikmatch — a multi-source music manager/player that uses vfs-sync as its
sync layer.
**Verified against**: `main` @ `9ab43ec` (v0.1.24), with the v2 plumbing already landed (`log.ts`,
`history.ts`, `vfs-file.ts`, `diff3.ts`) and [`docs/design-v2.md`](../docs/design-v2.md).

This document is a consumer's request. Everything it asks for is **content-agnostic**: the scope of
vfs-sync remains syncing N peer folders without interpreting what is inside them. The design test
applied to every point: **if vfs-sync would need to know what an MP3 is, the request is
badly framed** and it belongs to the layer above.

---

## 0. What is already solved

Listed so it is not proposed again. Reading v2 and the code on `main` knocks five items off the
initial list:

| Initial request | Status |
| --- | --- |
| Garbage collection over `objects/` | **The problem disappears**: v2 removes `objects/`, the working file is the content |
| Backend change cursor | **Designed**: `changes?(token)` in §8, the Drive feed in §7 |
| Reading without walking the folder | **Designed**: §6, `vfs.json` as the mirror |
| `mtime`+`size` filter as a fast path | Still current, and v2 §0 promotes it from optimisation to essential |
| **Resolution hook in the merge** | **Already there**, see below |

### The merge hook is no longer needed

It was the request to be able to change resolution without reimplementing `commonAncestorTree`.
`MergeOptions` on `main` already covers it two ways:

```ts
history?: History;              // ancestry is supplied by the caller
text?: (path: string) => boolean;   // which paths get a three-way text merge
```

`history` is optional and its comment makes it clear — *"An empty history is legal and merely
pessimistic"* — so nothing has to be reconstructed in order to intervene. And `text?` with `diff3.ts`
is a per-path extension point that already exists: `merge.ts:259` marks `report.text`, `sync.ts:697`
runs the `diff3`, and `store.ts` keeps `base/<hash>` locally to feed it.

**And that gives us for free what we were about to ask for.** We wanted a merge by fields of our
metadata JSON. It is enough to serialise them as canonical JSON **with one field per line** and mark
them via `text?`: two peers editing different fields of the same track merge on their own, without
the engine knowing what a tag is. That is a better division of labour than the hook we were going to
ask for. All that is left is checking our sidecars fit within `MAX_TEXT_MERGE`, which they do easily.

## 1. Requirements not covered

### A. Selective materialisation — a peer with metadata and no content

**The most important one: it unblocks an entire target.**

A phone cannot host a 200 GB library, but it can host its metadata. A peer needs to be able to have a
file's entry without having the file on disk, browse the full catalogue and fetch the bytes on
demand.

In v2, where the working file *is* the content, this collides with the reconciliation of §6: a file
absent from disk is indistinguishable from a deleted one, so it would read as deleted and propagate
the tombstone.

**There is already precedent in the code**, and that is the best sign the concept fits:

```ts
/** Above this, a conflict copy does not travel — the entry does, the bytes do not. */
export const HELD_AT = 64 * 1024 * 1024;
```

"The entry travels, the bytes do not" is exactly the primitive that is needed, today applied only to
conflict copies by size. What is being asked for is to generalise it: a **local** per-entry marker —
the natural place being the `local` section of the header, next to `verifiedAt` and `pendingRenames` —
meaning "known and deliberately not materialised here", with three effects:

- Reconciliation skips them instead of treating them as vanished.
- Sync does not try to transfer them to this peer.
- It stays local: the other peers neither know nor care.

Being local is what keeps it agnostic. The policy of *what* gets materialised — in Musikmatch: the
whole metadata directory, no audio until requested — is decided by the application with a predicate,
just as `ignore` is passed today.

### B. Exclusion rules with a file format

The predicate exists (`WalkOptions.ignore`, `walk.ts:11`, applied at `walk.ts:33`) and
`docs/recipes.md:216` already sketches reading it from a `.vfsignore`. What is missing is settling the
format, and **there is a data-loss bug first**.

#### B.1 — Prerequisite: ignoring an already-tracked file deletes it mesh-wide

Verified on `main`. `scan()` infers what vanished from the paths the walk returned, and the walk
applies `ignore`:

```ts
const walked = await walk(this.adapter, {          // vfs-node.ts:309
  directories: true,
  ...(this.ignore ? { ignore: this.ignore } : {}),
});
// …
const alive = new Set(seen.map((item) => item.path));          // vfs-node.ts:332
const vanished = live.filter((entry) => !alive.has(entry.path)); // vfs-node.ts:333
```

An already-tracked file that becomes ignored does not appear in `walked`, so it is not in `alive`, so
it falls into `vanished`: it gets a tombstone, the tombstone travels and it is deleted on every peer.
`docs/recipes.md` claims that ignored paths *"never appear as deletes on the other side"*, and that
only holds for paths that were **never** tracked.

**"I did not walk it" and "it is not there" have to be different things.** The scan must exclude from
the vanished calculation those paths the current rule ignores, and leave their entries intact. Git
solves the same problem by refusing to ignore already-tracked files.

It deserves its own test, of the same kind as the rotate-before-prune invariant of §10.2: add a rule
that covers a live file and check the other peer keeps it.

#### B.2 — Where the rules live

Two mechanisms, with git's split between `.gitignore` and `info/exclude`. The location does not change
**what** they govern — always the working folder — but whether the rules **travel**, because the walk
skips the control directory entirely:

| | Place | Travels? | Format |
| --- | --- | --- | --- |
| Shared | `.vfsignore`, working folder | Yes, it is ordinary content | Plain text, `#` comments |
| Local | `ignore` field in the `vfs.json` header | No | JSON array |

The local ones go in the header rather than a separate file for the reason argued in §Cost on Drive:
one file fewer is one request fewer per open. The trade-off is that the header is rewritten by the
engine, so these rules are set through the API and not by hand — which is exactly our case, the
application distributes them.

#### B.3 — Composition and syntax

**Union**: ignored by either one, ignored. Just as git applies `.gitignore` and `info/exclude` at the
same time. There is no precedence to define because no tie is possible — and that stops being true as
soon as negation rules `!pattern` exist, where order becomes observable and it has to be declared
which file wins. Recommendation: ship without negation.

The full gitignore semantics is a lot of surface. A subset that covers every real case:

| Form | Matches | Example |
| --- | --- | --- |
| exact path | that path | `docs/notes.md` |
| directory prefix | the subtree | `.cache/` |
| `*` over the name | in any folder | `*.tmp`, `.DS_Store` |

All three at **any depth**: OS junk shows up in every folder, not just the root. It is the use case
that justifies the feature — `.DS_Store`, `Thumbs.db`, `._*`, `@eaDir`, `.Trashes` — and in a
catalogue with one folder per album that is hundreds of binary files that change on their own and are
in permanent conflict.

**`.vfsignore` cannot ignore itself.** It is synced content and the mesh needs it to converge, so the
engine must reject any rule that excludes it, just as git always tracks `.gitignore`. Otherwise one
peer takes it out of the tree and the others read that as a delete.

**Startup order**: `.vfsignore` is content, so the sync that brings new rules still runs with the old
ones. It converges on the second pass, which is what `syncUntilStable` already provides.

### C. Native backend transfer fast path

When source and destination share a backend, the copy should not go through the engine:
Drive→Drive is one API call with zero bytes over the wire.

It rises in priority with v2, because §9 gives up deduplication: there will be more real transfers and
it is worth detecting the cheap ones as such. It fits the optional-method-with-emulation pattern of
§8, alongside `append?` and `changes?`.

### D. Delta transfer

A one-byte change resends the whole file. Listed for completeness, but **for us it is low priority**,
and for the same reason that underpins the premise of v2 §0: heavy content is immutable. Musikmatch
keeps the canonical tags in its metadata files and writing them into the audio is an explicit
operation, so large files are not rewritten in the normal editing cycle.

If it is ever tackled: the shape of the problem here is a *shifting prefix* — the tags go at the head
of the file — so content-defined chunking (FastCDC) fits better than fixed blocks.

## 2. Consequences of v2 we accept

These are not requests.

**Deduplication is lost** (§9). Musikmatch names its images by the hash of their content, so the same
cover art embedded in twelve tracks collapses into one file **by application design**, without
depending on the engine. The only cost is the rare case of the same bytes under two different roles:
before, one blob and one transfer; now, two. Acceptable, and our role-precedence rule makes it
deterministic and infrequent.

**The mirror can be stale** (§6, §10.1). The app has to show "verified X ago" and not take a file's
state as given without reconciling.

**The hash is declared by whoever writes** (§0). That fits: musical identity is computed by us over
the audio payload, not over the whole file, and we do not expect the engine to know it.

---

## 3. What we explicitly do NOT ask for

So that it is written down which side each thing falls on:

- Nothing that interprets audio formats, tags, cover art or durations.
- No concept of "track", "album" or "artist" in the engine.
- No identity based on audio content: our payload hash is our business.
- No music-specific exclusion rules. Default OS-junk rules are distributed by the application, not by
  the library.

## 4. Versioned spec and conformance suite

Musikmatch is going to need the engine in Rust as well (native on desktop and mobile, without pushing
bytes across IPC). The decision taken is **two implementations, TypeScript and Rust**, not a single
one compiled to wasm, so that vfs-sync stays a pure-TS npm package.

That turns the `.vfs` format and the engine's semantics into a public contract between two codebases.
A divergence does not give an error: it gives silent data loss. The real deliverable is not the second
implementation but **the spec and a shared conformance suite**.

Every rule the documentation describes as "deterministic so that both peers compute it the same way"
is a failure point and has to be pinned down. In v2, at least:

| Area | What has to match exactly |
| --- | --- |
| `vfs.json` | Canonical order of `entries` and computation of the `state` digest |
| Log | Union of operations, dedup by `op`, XOR of the segment digest |
| Rotation | Threshold, segment name, rotate-before-prune invariant (§10.2) |
| Merge | Two-dimensional resolution, `prev`/`prevPath`, tiebreak by date |
| Conflict copies | Name derived from the content, and the `HELD_AT` threshold |
| Text merge | What counts as text, `MAX_TEXT_MERGE`, and `diff3` itself |
| Identity | Assignment of `uuid`, use of the backend's `native`, first encounter between peers |
| `storeId` | Adoption of the lexicographically smaller |

Suggested shape: scenarios in a language-neutral format — initial state of N peers, operations,
expected tree and digest — executed by both implementations, plus property tests that generate random
sequences and check every peer converges without losing data. A sync engine is exactly the kind of
code where that pays for itself.

It blocks nothing in section 1: the second implementation comes later, but the spec is best written
while v2 stabilises, not once there are two codebases to reconcile.
